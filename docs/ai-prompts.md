# Задания кодовым ИИ

**Перед запуском любого задания:** дать агенту этот репозиторий, `docs/requirements.md`, `docs/contracts.md`, область файлов и ветку. Контракт v0.1 сначала утвердить с командой. Если данных не хватает, агент фиксирует допущения и не придумывает промышленную валидацию. Кодовых агентов запускать на отдельных ветках; пересечения файлов согласовывать.

## 1. Backend — капитан проверяет и сливает

> Реализуй ядро MVP для задачи из `docs/requirements.md` по `docs/contracts.md`. В зоне работы: backend, схемы, БД и необходимые тесты. Сделай приём и валидацию событий, несовместимые версии и понятные ошибки, идемпотентность `source_id + event_id`, конфликт одинакового ID с разным содержимым, хранение исходников отдельно от проекций, оба времени события. Построй историю изделия с компонентами и операциями, карточку несоответствия с сигналом, состоянием до/после, действиями и станком. Гипотеза о причине не равна подтверждению; решение контролёра — отдельная добавляемая запись с автором и основанием. Позднее событие меняет производные показатели без утраты истории. Добавь тесты для повтора, задержки, плохого наблюдения, входного брака, неизменности исходника и пересчёта аналитики. Предложи миграции и команду запуска. Не реализуй CV-распознавание. Выдай краткий отчёт по фактически прошедшим проверкам и ограничениям.

## 2. Синтетические данные и эмулятор — второй участник проверяет

> Прочитай `docs/requirements.md`, `docs/contracts.md`, `docs/demo.md`. В зоне работы: `data/`, `emulator/`, описание интеграций. Создай воспроизводимый генератор событий с фиксированным seed для нескольких изделий, минимум двух участков и операторов. Покрой нормальное изделие, входной дефект, дефект после операции, неполные сведения, станок, повтор, позднее событие, повторную операцию, решение контролёра и контроль изменения записи. Ожидаемые состояния и показатели держи в отдельных файлах. Реализуй двусторонний обмен эмулятора: входное задание/справочник, исходящий результат, ACK и ошибку. Дай примеры маппинга ID и контрактов целевых 1С, Галактика:ERP, MES и КОМПАС-3D; не называй их работающими подключениями. Не меняй общую модель без согласования.

## 3. Frontend — второй участник проверяет и сливает

> Сделай UI по `docs/contracts.md` и реально работающему API. В зоне работы: frontend и его тесты. Экраны: линия; изделие с хронологией, составом и операциями; карточка несоответствия с исходным наблюдением, состоянием до/после, основаниями, альтернативами и отдельным решением контролёра; аналитика с чёткими знаменателями и фильтрами. Входной брак, неподтверждённая гипотеза и ошибка оператора визуально различимы. Плохое качество наблюдения показывает «оценка невозможна». Не показывай фиктивные фото и численные метрики, которых не вернул API. Подготовь путь кликов для `docs/demo.md`. Если backend ещё не готов, используй временный контрактный мок и явно перечисли его; перед сдачей убери подмену из продемонстрированного сценария.

## 4. Архитектура, QA и защита — после появления P1

> Проверь репозиторий и `docs/requirements.md`. Подготовь README с командами установки, запуска, заполнения данными и проверок на чистой машине. Оформи схему данных/API, диаграмму потока событий и архитектуру проекта камер и внешнего анализатора (точки, свет, калибровка, границы метода, edge/центр, качество, потеря связи). Опиши адаптацию к закрытым данным, экспертное подтверждение, версионирование и откат. Для 1С, Галактика:ERP, MES и КОМПАС-3D укажи направления, владельцев данных, маппинг ID и ошибки. Опиши права, шифрование, целостность, хранение ключей, границы и восстановление. Подготовь презентацию и скринкаст строго по фактически работающим возможностям. Отдельно выпиши требования ТЗ, которые пока не выполнены, и план их закрытия; не маскируй их текстом.

## Правила приёмки любого результата

- Показать изменённые файлы и команды запуска/проверки.
- Не менять контракт тайком; изменения требуют одновременного обновления схемы, примеров и потребителей.
- Проверить реальный end-to-end, а не только мок интерфейса.
- Не добавлять ключи, реальные персональные данные и секреты в репозиторий.
- Называть проектные предположения предположениями.
