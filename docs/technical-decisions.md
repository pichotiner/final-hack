# Технические решения P0

Дата: 25 сентября 2026 года. Рабочая база для начала разработки; это выбор команды проекта, а не требование организаторов. Изменения общих решений отражаются здесь и в контракте до изменения потребителей.

## 1. Стек

| Область | Выбор | Причина |
| --- | --- | --- |
| Backend | Python 3.11, FastAPI, Pydantic 2 | Быстрый API, строгая валидация, удобная реализация сценариев и проверок |
| Хранение | PostgreSQL 17, SQLAlchemy 2, Alembic, psycopg 3 | Транзакции, уникальность событий, конкурентная обработка и миграции |
| Frontend | React 19, TypeScript, Vite, TanStack Query | Интерфейс по API, переиспользуемые компоненты и управление запросами |
| Среда frontend | Node.js 24 LTS, npm | Доступна в рабочем окружении; lock-файл коммитится |
| Спецификация | OpenAPI 3.1, contract-first | Единый источник транспортных DTO для клиента и сервера |
| Генерация | datamodel-code-generator → Pydantic; openapi-typescript → TypeScript | Повторяемые структуры происходят из одной спецификации |
| Проверки | pytest, интеграционные проверки с PostgreSQL; Vitest и сквозной Playwright | Проверка бизнес-правил и одного реального пользовательского пути |
| Запуск | Docker Compose: PostgreSQL, backend, frontend, emulator | Воспроизводимая среда для демонстрации |

Точные версии библиотек, генераторов и базовых образов фиксируются при первой установке и успешной проверке совместимости. Python-зависимости — через `pip` и фиксированный lock-файл; дополнительный менеджер `uv` для запуска не требуется. Для MVP достаточно обычного HTTP API с опросом состояния интерфейсом; streaming добавляется только при необходимости.

На локальной машине проверены Python 3.11.9, Node.js 24.12.0, npm 11.6.2, Docker CLI 29.2.0 и Compose 5.0.2. Наличие Docker CLI не подтверждает работу Docker Engine; запуск контейнеров ещё предстоит проверить.

## 2. Архитектура: модульное ядро с адаптерами

```text
Симулятор наблюдений ──HTTP──> API приёма ──> Прикладные сценарии
                                               │
React UI ──────────────HTTP──> API чтения/решений ─┤
                                               │
                      Производственная модель и правила
                         │              │
                 Порты хранения     Порты интеграции
                         │              │
                     PostgreSQL     ERP/MES/CAD adapters
                                        │
                                    ERP emulator
```

Один backend с модулями, одна БД. Доменная модель не импортирует FastAPI, SQLAlchemy и внешние форматы ERP. Предлагаемая структура `backend/app/`: `domain/`, `application/`, `ports/`, `adapters/`, `api/`, `generated/`. Транспортные DTO генерируются; доменные сущности написаны вручную и не выдаются за сгенерированные.

Основные модули: ingestion, traceability, quality, analysis, analytics, audit, integrations. Реальный визуальный анализ является внешним источником. Predictive и MobileOps описываются как будущие подключения, не входят в первый срез.

## 3. Состояние, порядок и конкурентность

- PostgreSQL — единственный источник состояния ядра. In-memory словари не обеспечивают идемпотентность и не используются как авторитетное хранилище.
- Уникальный индекс `(source_id, event_id)` защищает от дублей между экземплярами backend. Повтор с тем же содержимым возвращает исходную квитанцию; другое содержимое даёт конфликт.
- В первой реализации принятый исходник, производные записи и сообщение outbox сохраняются одной транзакцией. При rollback квитанция об успешном приёме не выдаётся.
- Изменения одного изделия сериализуются транзакционной блокировкой. Операции, затрагивающие несколько экземпляров, захватывают блокировки в стабильном порядке ID. Без подтверждения этого правила несколько обработчиков не считаются проверенным масштабированием.
- История хранит порядок приёма; представление сортируется по времени возникновения с детерминированным разрешением равенства. Порядок сортировки не является доказательством причинности.
- Позднее событие пересчитывает затронутое представление; решения людей и предыдущие версии анализа остаются в истории. Если изменились основания решения, выставляется признак повторного рассмотрения.
- Исходящие результаты используют transactional outbox: отдельный обработчик забирает задания с блокировкой, повторяет доставку с тем же ID, сохраняет ACK/ошибку. Сбой между отправкой и ACK закрывается идемпотентностью принимающей стороны.
- Событие без известного справочника/связи сохраняется как `unresolved`, не теряется и не привязывается к придуманному объекту. После появления связи выполняется повторная обработка.

## 4. Контракт и генерация

Роль №1 определяет производственную семантику в [contracts.md](contracts.md), роль №2 переносит её в `contracts/openapi.yaml` и подключает генерацию. После появления формальной спецификации она является источником истины для транспортных полей, типов и enum; Markdown объясняет семантику, а не создаёт вторую независимую схему.

Правила генерации:

1. Зафиксировать версию обоих генераторов и команды.
2. Сгенерировать реально используемые backend DTO и frontend types.
3. Проверять синтаксис спецификации, повторную генерацию и отсутствие diff в артефактах.
4. Сверять маршруты и модели запущенного FastAPI с выбранным контрактом; одного отсутствия diff недостаточно для проверки реализации.
5. Показать совместимое изменение и несовместимое изменение с автоматическим обнаружением. Версии сообщения, API и анализатора различать.

Формальная спецификация и генерация пока не реализованы. До их подключения первый срез не считается контрактно согласованным.

## 5. Базовая защита

- Пользователи: controller, master, technologist, manager, admin; источники событий имеют отдельные служебные учётные данные и привязку к `source_id`.
- Автор решения и момент его принятия определяются серверной аутентификацией и часами сервера. Внешний источник не может выдать себя за контролёра.
- Исходный payload шифруется AEAD, например AES-256-GCM, с уникальным nonce и аутентифицированными метаданными. Это проектный выбор, а не уже реализованный механизм.
- Пакет содержит версию формата, `crypto_profile_id`, `key_id`, версию ключа, nonce, ciphertext/tag и связь с событием. Ключи монтируются как secrets, не входят в исходники, образы и демонстрационные данные.
- Учётная запись приложения не обновляет и не удаляет исходные события и аудит. Контроль вмешательства и ограничения доступа проверяются отдельно от шифрования.
- TLS защищает разнесённые компоненты. Индексы и проекции могут содержать открытые производственные метаданные: их границы защиты необходимо явно описать.
- Модель угроз, резервирование ключей и проверка восстановления обязательны перед финальной сдачей. Постквантовая/гибридная защита — отдельная последующая реализация.

## 6. Граница первого среза и передача работы

Первый сценарий и ожидаемые показатели определены в [first-slice.md](first-slice.md).

**Роль №1 начинает:** доменная модель, миграции исходных событий/проекций/решений/outbox, сервисы приёма и истории, слой API, конфигурация запуска и предметные проверки.

**Роль №2 начинает:** формальная OpenAPI-спецификация по семантике v0.2, генерация DTO/types, события и expected results для первого сценария, внешний эмулятор и экраны паспорта/карточки/решения.

Общий способ запуска и параметры компонентов согласуются через роль №1. Секреты и локальные настройки берутся из примера окружения при реализации. Команда запуска приложения появится после проверенной конфигурации, а не как обещание в документации.
