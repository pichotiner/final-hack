Для технолога формулировка пути должна быть: «этот сигнал относится к вставке; журнал установки связывает её со сборкой; решение было принято без этого сигнала». ## 3. Ответы на вопросы роли №1

| Вопрос | Ответ/предложение роли №2 | Статус |

| Кто владеет обязательными точками и новой применимостью? | Технолог/утверждённая система технологических данных. ERP или MES может передавать версию, но не становится владельцем автоматически. Область изменения по заказам/серийным экземплярам явная; старый B закрепляет прежнюю версию | Производственное предложение; подтвердить на G0 |
| Как стабилен mark-001 между входом и финалом? | В эмуляторе это допустимое синтетическое соглашение одного источника. Между реальными камерами/сменами/после переустановки стабильность не доказана; один сервис CV её не создаёт. Локальный track либо отдельное решение ОТК о тождестве, без слияния по типу | Ограничение принято ролью №2; нужен ответ №1 по CP-08 |
| Кто владеет фактическим составом? | MES/производственный учёт с назначенным мастером. Комплектование, установка/снятие и исправление ошибочной записи — разные утверждения. CAD владеет проектным составом | CP-01, модель пока не принята совместно |
| Как доказать полноту состава? | Снимок/курсор выгрузки + сверка серийного комплекта и журнала установки/снятия + подтверждение владельца с областью/исключениями. reliable одного наблюдения не доказывает полноту всех связей | Формат подтверждения предложен, реальной сверки нет |
| Кто ограничивает выпуск при unknown? | Начальник качества/делегированный ОТК задаёт область, мастер физически удерживает/локализует изделия. При неизвестной границе — весь пилот и известные связанные сборки; ограничение применяется и к будущим изделиям области | CP-02; до реализации используется штатный регламент, не фиктивный автоматический запрет |

Review после released запускает отдельную локализацию, а не переписывание прошлого | CP-05; поддержка ERP неизвестна |
| Сроки, RPO/RTO и review? | Д пилота: 8 h offline; 24 h подтверждённая recovery-копия edge; 90 суток raw/B/решений, 30 суток обычных медиа с продлением по основаниям; central RPO 15 min/RTO 4 h. ## 4. Разбор F1/F2/F4/F6/F7 и производственные контрпримеры

| Вход роли №1 | Результат документарного review | Что требуется до проверки/допуска |
| --- | --- | --- |
| F1: R11 с item=assembly-001 до установки | При закреплённом комплекте смысл допустим; это назначение вставки будущей сборке, не факт нахождения в ней. Один дефект только по синтетическому стабильному ключу | Отделить reservation/assignment от фактического PART_OF; явно указать источник принадлежности R11 |
| F2: наблюдение insert-001 до установки | Поиск должен дойти до будущей assembly-001 через фактическую связь, даже если occurred_at раньше valid_from. Это оценка влияния, не автоматическое слияние кандидатов | Проверить позднюю доставку самой установки и повторный поиск без повторной отправки RC |
| F4: снятие и перестановка в assembly-003 | Обе сборки остаются в оценке: снятие не доказывает устранение повреждения сопряжения или ошибочности старого решения | История снятия, нового монтажа и repair/контроля; отсутствие текущего ребра недостаточно для исключения |
| F6: возможны две сборки, потом установлен один ID | До разрешения обе имеют кандидатную неопределённость; после — пересчёт старого ∪ нового охвата. Другую сборку нельзя автоматически объявлять released | Утверждение владельца связи и отдельная проверка остальных причин review/ограничений |
| F7: неизвестный ID, только участок, потом новое изделие | Предикат ограничения должен действовать на новую регистрацию/решение, а не только на уже перечисленные ID | Процесс локализации вне EFQA, полномочия, границы по последней надёжной сверке и обработка уже переданной продукции |

Дополнительный контрпример: при ручной доработке старая CP-F остаётся хорошей, но относится к предыдущему run. Система не должна закрыть контроль новой операции старым наблюдением. Владелец маршрута задаёт применимость контроля к циклу; новый run ссылается на предыдущий, а решение rework само run не создаёт.

## 5. Замечания к архитектуре и открытые разногласия

Здесь «согласен» означает позицию роли №2, а не совместное принятие ADR.

| ID | Позиция роли №2 / серьёзность | Требуемый ответ или изменение |
| --- | --- | --- |
| R2-01 | Согласен: typed SQL + неизменяемые основания; сильная QMS остаётся альтернативой | Проверить установленную QMS тем же сценарием; выбрать по стоимости внедрения/сопровождения |
| R2-02 | Блокирует промышленную интерпретацию: общий mark-001 между CP не обоснован | Сохранить synthetic label; отдельно проектировать linking. Не расширять source namespace, чтобы обойти v0.2 |
| R2-03 | Блокирует автоматический narrow review: неизвестна физическая полнота состава | Принять CP-01 и видимый признак области/полноты. До этого широкий fallback, а не «нет пути — независимо» |
| R2-04 | Блокирует реальный выпуск при unknown: отсутствует согласованный lifecycle ограничения области | Принять CP-02, включая будущие изделия, владельца, независимое снятие причин и внешнюю локализацию |
| R2-05 | Условно согласен с общим guard как эталоном корректности; throughput не известен | Измерить μe с B/историческим обходом. Буфер рассчитан на 20 commit/s при λ=2, а не на число HTTP-запросов. Лимит replay → явный отказ, пакет остаётся на edge |
| R2-06 | Не согласовано: одного business ACK недостаточно, если ERP различает receipt/application/containment | CP-05: snapshot/delta, версия, ACK применения и отдельное подтверждение физического действия; не добавлять поля без общего решения |
| R2-07 | Не согласовано: событие и доступность медиа коммитятся в разных ресурсах | CP-03: manifest/receipt/recovery, честное incomplete; raw accepted не доказательство сохранности изображения |
| R2-08 | Блокирует обещание полного восстановления: edge replay не восстанавливает потерянные человеческие решения | Согласовать центральный RPO и сверку outbox/ERP после restore; не использовать RPO=0 канала как RPO=0 всей системы |
| R2-09 | Согласен с B, включающим противоречия и неизвестность, и stale_revision по всему контексту | Зафиксировать ID ссылок, pinned versions, межиздельные/общие справочники и единый writer protocol |
| R2-10 | Не согласовано: имеющегося time_quality мало для строгого межстанционного порядка | CP-04: предел точности метода/часов; до этого uncertain при недоказанном порядке, без исправления raw |

Новые предложения записаны в §12 enterprise-pilot. Старые контрактные замечания роли №1 по nullable/allOf, неизвестному типу компонента, нескольким измерениям длительности и публичным ошибкам остаются открытыми: эта сессия не запускала OpenAPI-валидацию и не приписывает себе прежние результаты роли №2. Архитектурная позиция: тип не выводить из ID; reported/calculated интервалы различать; null допустим по v0.2; публичные ссылки должны однозначно включать источник либо серверный record ID с отображением.
