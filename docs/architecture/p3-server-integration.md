# P3: серверная интеграция роли №1

26 сентября 2026. **Реализовано в текущем рабочем дереве роли №1 и проверено.** Поручение владельца: продолжить незавершённую реализацию,
не останавливать серверную поставку на ожидании роли №2.

## Решение и граница согласования

Проблема: внутренний P2 уже проверяется на PostgreSQL, но его нельзя вызвать
по HTTP и доставить сохранённый outbox отдельным worker.

Варианты: ждать спецификацию №2; подключить несовместимый v1; подготовить
проверяемый **проект общего v2-контракта** вместе с тонким сервером.
Выбран третий вариант. Это уточнение порядка поставки §6 DP-01 по новому
поручению, а не заявление о согласовании со вторым разработчиком.

`backend/app/api/contract.json` — единственный машинный источник схем запросов
этого серверного эксперимента. Сервер валидирует его непосредственно и
публикует OpenAPI на `/openapi.json` (добавляя стандартные responses и requestBody).
Маршруты и роли также строятся из этого файла. Рукописных дублирующих Pydantic DTO нет. Статус версии —
`0.3.0-draft`, до review №2 она не объявляется общей принятой `0.3.0`.
При поставке №2 заменяем этот источник согласованной спецификацией, подключаем
генерацию и проверяем совместимость по фактическим HTTP-сценариям.

Предметные правила DP-01 сохраняются. Автор назначается по bearer credential;
ID нового цикла назначает сервер детерминированно для повтора команды.
Импорт принимает уже сопоставленный производственный контекст; преобразование
формата внешней ERP выполняет её адаптер. Все данные демонстрационные.

## Доставка

Worker выбирает сообщения с устойчивой арендой в PostgreSQL, затем завершает
транзакцию перед HTTP. При обрыве или падении повторяется каноническое тело
того же сообщения. HTTP 429/5xx и ошибки сети получают ограниченный backoff;
контрактные ошибки и неверный ACK сохраняются для разбора. ACK проверяется
ядром. Истечение аренды допускает повторную отправку, поэтому идемпотентность
ERP обязательна. Состояние доставки не повышает context_revision/result_version.

Цена: временный draft и последующее согласование названий, статическая registry
учётных записей для пилота, сериализованный guard предметных writers. TLS и
жизненный цикл учётных записей остаются задачами развёртывания предприятия.

Проверка: HTTP → настоящая PostgreSQL → отдельный worker/HTTP-получатель;
ошибки прав, stale B, повтор команды, rollback, потеря ACK и перезапуск worker.
UI и persistent ERP-процесс остаются поставкой №2; тестовый HTTP-получатель
не выдаётся за её эмулятор.

Доставка хранит попытки/ошибку/аренду в `quality_deliveries`, отдельно от
immutable payload `quality_outbox` и предметной версии изделия. Обычная запись
проекции не стирает аренду. Ошибки не маскируются фиктивным ACK, сообщения не
удаляются после числа попыток. При 429/5xx/потере сети задержка растёт до 300 с;
при 4xx/невалидном ACK требуется retry после исправления. ERP-ответы/секреты не
копируются в текст ошибки. Canonical JSON пересоздаётся из сохранённого тела
детерминированно; digest проверяется перед отправкой.

## Точная передача роли №2

1. Получить `/openapi.json`, прочитать `app/api/contract.json` и провести review.
   `0.3.0-draft` ещё не общая согласованная `0.3.0`. Схемы **ответов пока открытые
   объекты**, не полный contract gate/codegen. Расписать response DTO и все
   условные поля payload; сервер уже проверяет типовые правила DP-01 отдельно.
2. Использовать `POST /items/{id}/bases` для явного закрепления просмотра.
   `target_id` нужен для карточки; GET `/bases/{id}` возвращает исторический B.
   Команды используют `action`, `reason`, `expected_revision`,
   `expected_basis_id`, `idempotency_key`. ID цикла клиент не назначает.
   Текущие внутренние проекции пока содержат `cycle_id`; внешний outbox —
   `control_cycle_id`. Нормализацию read DTO сделать в общем контракте.
3. Условные source-поля: `payload.control_session_id`, `control_cycle_id`,
   `replaces_observation_id`; область и метод должны совпадать с импортированным
   `ProductionContext`. Один переданный ID цикла не делает привязку доказанной.
4. ERP получает **только payload**, не объект доставки с digest/status.
   Digest ACK = SHA-256 RFC 8785 этого payload. `201/accepted` и `200/duplicate`
   должны соответствовать статусу HTTP и полному ACK DP-01. Поставить SQLite
   inbox/state/original receipt и входной GET заданий; server import принимает
   уже сопоставленный контекст. Сквозное преобразование реального формата ERP
   не заявляется.
5. UI и независимые сценарии A01–A14 подключать к этому работающему серверу.
   Scope resolution пока доступен внутренним сервисом, не отдельным endpoint.

## Ограничения этой поставки

Проверяется малый пилот. Списки имеют стабильный cursor/limit, но read-model
пока сканируется в памяти перед пагинацией. Полные аналитические срезы,
разрешённый перенос отдельных проверок между циклами, binding resolution UI,
эксплуатационная ротация/backup ключей, TLS и промышленный restore остаются
отдельными задачами. Swagger UI загружает внешние ресурсы; для закрытого контура
есть прямой JSON API и терминальное демо. Локальный Compose/API слушает loopback.
