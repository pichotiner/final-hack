## 3. Собственные изменения №2

### R2-P5-01: запоздалый B повторно открывает закрытый просмотр — исправлено

Воспроизведение: открыть B → запросить повторное открытие, задержать ответ B →
нажать «Завершить просмотр и сменить цель» → завершить задержанный ответ.
В исходной P5 закрытая форма снова появлялась. При смене изделия аналогичный
запрос мог закрепить предыдущий контекст. Команда при этом всё ещё проверялась
сервером, но намерение пользователя и экран расходились.

В `frontend/src/App.tsx` введён номер запроса рассмотрения: закрытие, смена
пользователя/изделия/цели и отправка команды отменяют применение старого ответа.
Поздние ошибки такого запроса тоже игнорируются. Несовпадение B/item/revision/
cycle/target отображается как ошибка вместо ложного сообщения «Закреплено».
Тест `a delayed basis cannot reopen a review after the user closed it` сначала
упал на исходном коде и прошёл после поправки.

### Наблюдаемость для показа

Добавлены чтения существующего API: состояние выбранной линии и первая страница
доставок ERP. На экране различимы возраст данных, незавершённые операции и отказ
прав; доставки требуют integration/admin. ACK не назван физическим действием.
Нет нового endpoint или изменения прав/контракта. Это ручные снимки, не обещание
непрерывно актуального экрана или полного списка при наличии next_cursor.

### Дополнительные предметные проверки

`backend/tests/integration/test_role2_shared_acceptance.py`:

1. Дубль final не меняет состояние; второе наблюдение того же полного ключа
   сохраняется отдельно в одной карточке; новая команда по старому B отклоняется
   без изменения решений/outbox; старый B прежний (A01/A08).
2. Poor + no_defect_signs сохраняется как исходник, эффективный результат
   not_assessable, release получает 409 без частичной записи (подслучай A07).
3. Принятая команда → отзыв доступа → восстановление → late → exact retry
   возвращает прежнее решение; другое тело с тем же ключом конфликтует (ядро A03).

HTTP здесь использует ASGI transport и реальную PostgreSQL; это не браузер/TCP.
Реальные TCP/отдельный worker/ERP покрывает повторно пройденный A04 роли №1.

## 4. Где уже требуется роль №1

Эти пункты не закрываются правкой UI без предметных команд и форматов ответа:

1. **A06 — перенос контроля:** публичная авторизованная команда, правило допустимого
   переноса и сохраняемая ссылка на старый контроль. Старую проверку нельзя просто
   отправить с новым cycle ID.
2. **A13 — разрешение scope:** общий endpoint для снятия одной из нескольких причин
   неизвестного охвата, с B/revision/idempotency; новый item остаётся под остальными
   ограничениями. Внутренний сервис не заменяет публичный workflow.
3. **Disputed/A14:** согласовать доступное действие при противоречии и повторном
   рассмотрении устранения. Нужна передача конкретной последовательности команд
   и допустимых входов; «отправить ещё один хороший сигнал» не универсальное решение.
4. **Межиздельное влияние:** фактическая/историческая установка и версия links,
   пересмотр после поздней установки. Наличие путей в старом UnifiedChain не
   переносит гарантию в P4/P5; нужны штатный вход и проверка транзакций.
5. **Аналитика PDF §2.4:** shared getAnalytics сейчас отдаёт агрегат kpi, timeline —
   события. Для длительностей с происхождением, разрезов участок/смена/оператор и
   сопоставимых работ нужен согласованный read DTO из ядра. №2 подключит его к UI;
   самостоятельно считать новую предметную статистику в браузере не следует.

Эти задачи следует передавать по одной: сначала минимальные public scope/carry/
disputed команды с примерами и проверками, затем graph/аналитика. Нормативное
уточнение DP-01 по raw control_record_ids и версии транспорта тоже нужно закрепить
редактору общего протокола; прежний текст §6 ещё описывает observation ID.

## 5. Что остаётся роли №2

- Полный браузерный проход A04 на общей развёрнутой среде и скринкаст; component
  tests не подменяют его. После серверных расширений — UI и runner A06/A13/A14.
- Исполняемая общая матрица всех A01–A14: нынешние tests покрывают части в разных
  слоях, это не единый полный отчёт по приёмочной карте.
- Отдельный normal release → ERP ACK, сверка read-страниц/пагинации и прав, сценарий
  восстановления учётных данных для неизвестной команды в пользовательском процессе.
- Реальные параметры камер/Edge и владельцы систем требуют предприятия; остаются
  проектными предположениями. Disaster restore M0-R не входит в подтверждённый A04.

Вывод: **прежняя блокировка «вообще нет общего ACK» снята**. Теперь нужны конкретные
остаточные команды ядра и полный пользовательский показ, а не ещё один coordinator.
