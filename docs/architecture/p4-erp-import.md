# P4. Входной адаптер задания ERP

26 сентября 2026. Владелец — роль №1. Проверочный эксперимент по поручению
пользователя после review PR №6.

## Решение до реализации

Проблема: `/external/v2/work-orders` роли №2 задаёт заказ и точки, но ещё не
содержит всех run/session/authority/ID привязок, необходимых P3. В PR №7 есть
другой coordinator на базе до P3; его объединение требует отдельного review.

Варианты: угадывать привязки по строкам ID (неприемлемо); остановить импорт до
новой OpenAPI; использовать явный версионированный локальный профиль адаптера.
Выбран профиль для ограниченного demonstrator. Это конфигурация владельца
маршрута/интегратора, не новый публичный ERP DTO и не доказательство установки.

- Машинная проверка внешних WorkOrder/WorkOrderPage использует **переданный файл
  OpenAPI роли №2**, без копии схемы в backend. Оба PR №6/№7 сохраняют этот
  внешний контракт. Профиль не может ослабить его валидацию.
- Профиль явно закрепляет ERP/producer, внешний заказ, тип/версию маршрута и
  контрольного плана, отображение каждого external item → internal item,
  компонентов, источников, требуемых run и контрольных сессий.
- Проверяются полное совпадение набора изделий/точек/компонентов с профилем,
  область/метод каждой точки и все обязательные привязки. Неизвестный профиль
  или `repeat_after_rework=false` отклоняется: перенос контроля ещё не реализован.
- ERP владеет номером revision заказа; профиль — недостающими привязками.
  Новая revision не переписывает прежний snapshot. Импорт не создаёт source event,
  фактическую установку, завершённую операцию или решение released.
- HTTP выполняется до транзакции. **Один заказ со всеми его изделиями**:
  production_guard → durable dedupe/revision → map/проверки → все контексты,
  B/review/outbox и квитанция импорта → один commit. Несколько заказов потока
  имеют отдельные транзакции; повтор после частичного прогона безопасен.
- Ключ импорта `(external_system,message_id)`, digest полного канонического JSON
  заказа и профиля. Точный повтор возвращает первоначальную квитанцию до проверки
  текущей revision. Другое тело/профиль с тем же message ID — конфликт.
  Новый message ID с занятой либо более старой revision заказа — конфликт.
  Опубликованный profile ID/version нельзя повторно использовать с другим телом.
- Права integration проверяются при каждом импорте и повторе; автор первоначального
  приёма сохраняется. Ключ сообщения принадлежит ERP, не текущему actor.
- Сохраняются исходный JSON заказа, профиль, digest и первоначальная квитанция.
  Это открытые метаданные производственного контекста, как quality_context_versions;
  шифрование исходных observation events не выдаётся за шифрование этих метаданных.

Цена: локальный профиль нужно утверждать/версионировать отдельно; строгий отказ
может остановить новый маршрут. Контрактный 4xx, плохой JSON, превышение размера,
цикл пагинации и ошибка схемы не дают успешной квитанции. Секреты/тела ответов
не попадают в диагностические сообщения.

Проверки: настоящее ERP HTTP → PostgreSQL; exact retry после restart, изменённое
тело, старая revision, запрет прав, ошибка на втором изделии с rollback первого,
конкурентный повтор. Пересмотр решения — после появления полного общего DTO
плана: профиль станет адаптером этого DTO, предметная транзакция сохранится.

## Реализовано и проверено после восстановления сессии

Поставка подготовлена в `feat/role1-erp-import` от базы `ab18333` для публикации в `main`.
Проверка использует отдельный checkout PR №7 `e508868` (его внешний контракт 0.3.0).
Данные синтетические, ERP — persistent SQLite-эмулятор роли №2.

- `backend/app/import_erp.py`: CLI читает задания по настоящему HTTP; bearer ERP
  и bearer integration передаются файлами. Успешная строка JSON выдаётся после
  commit конкретного заказа; итог `completed=false` и ненулевой exit code означают
  остановку, а уже закоммиченные заказы можно безопасно повторить.
- `backend/app/adapters/erp_orders.py`: строгий JSON, валидация переданной внешней
  OpenAPI, закреплённый профиль, ограничение страницы 1 MiB, пагинация без перехода
  на чужой URL. Timeout/HTTP-ошибка требуют повторного запуска с прежним профилем.
- `PostgresProductionJournal.import_work_order`: одна транзакция для всех изделий
  заказа. `0006_erp_imports` сохраняет исходный заказ, профиль и квитанцию append-only;
  deployment и test-роль получают SELECT/INSERT.
- `route_id` и `control_plan_version` сохраняются в каноническом контексте и B.
  Это дополнение внутреннего draft роли №1, не новая редакция общей OpenAPI.

Результат: **160 passed без БД + 64 passed с PostgreSQL**, без skipped в этих
двух прогонах. Входят 22 новых изолированных проверки и 6 интеграционных.
Полный PostgreSQL-прогон применяет шесть миграций и проверяет соответствие metadata.
Использованные изолированные контейнеры/тома удалены скриптом.

Проверено отдельно:

1. HTTP настоящего эмулятора → CLI в отдельном процессе → три контекста и outbox;
   второй процесс возвращает первоначальную квитанцию с `status=duplicate`.
2. Сбой после записи второго изделия откатывает контексты, B, stream mappings,
   outbox и квитанцию всего заказа. Повтор затем успешно импортирует заказ.
3. Конкурентные одинаковые команды дают accepted + duplicate, по одному эффекту.
4. Изменённое тело/профиль с прежним message ID, повторная/старая revision и мутация
   опубликованной версии профиля отклоняются. Права проверяются и на повторе.
5. UPDATE/DELETE/TRUNCATE истории импорта запрещены триггерами.
6. `test_erp_import_a04.py`: ERP HTTP → импорт → живой Uvicorn/TCP → PostgreSQL →
   confirm → rework → серверный новый цикл → завершённая доработка → три повторных
   контроля → resolve → released. Перед resolve выпуск получает 409. Поздний
   входной контроль со старой сессией не закрывает точку нового цикла.

Финал проверки №6: `confirmed_defects=1`, `resolved_confirmed_defects=1`,
`open_confirmed_defects=0`, `rework_operations=1`, `disposition=released`, blockers
пусты. Confirm и resolve остались в истории, первоначальный B неизменен, точный
повтор confirm возвращает прежнее решение. В сохранённом outbox есть ссылка
на решение released. **Сообщение pending; ACK ERP этой проверкой не получен.**
Команды здесь ещё draft P3 (`observation_ids`, явные sessions/run bindings), а не
DTO PR №7. Поэтому это проверенный серверный участок A04, не общая приёмка A04.

## Адресные транспортные решения для подтверждения №2

Следующие пункты — предложение №1 после опубликованного review. Ответного
подтверждения №2 и обновлённых схем в PR №6/№7 на момент проверки нет.

1. **Вход задания:** для текущего demonstrator сохранить внешний WorkOrder 0.3.0,
   недостающий план получать из версионированного профиля, пример —
   `backend/examples/erp-import-profile.json`. Поля external item/component ID,
   внутренние ID, source authorities, checkpoint/phase/method/run/session явные.
   Используем `producer_id=efqa-demo`, `external_system=erp-demo`. События должны
   нести зарегистрированные `control_session_id`; incoming без run, повтор после
   доработки имеет новую сессию. Утвердить профиль или дать полный DTO плана.
2. **Новый цикл:** `rework_disposition_id` проверяется по последнему решению;
   ответ должен отдавать `control_cycle_id` и зарегистрированные привязки
   checkpoint → session/run. Если их назначает сервер, нужен выбранный профиль
   повторного плана; одних planned run IDs недостаточно.
3. **Resolve:** поддерживается предложенный `control_record_ids` со ссылками
   на принятые raw records. №1 выполнит lookup внутри guard после проверки
   успешного повтора; ни UI, ни runner не должны собирать `record_id + ':0'`.
4. **ERP:** добавить обязательное nullable `disposition_decision` со снимком
   `decision_id`, `basis_id`, `action`, `reviewed_revision`, `actor_id`, `reason`;
   null — только до первого disposition. `review_required` включает необходимость
   пересмотра disposition, исторический released сохраняет прежние ссылки.
   `confirmed_nonconformities` включает resolved карточки, их decision/resolution
   IDs и B. Необязательное удаление дефекта из списка после resolve недопустимо.
5. **После подтверждения ERP DTO:** №1 формирует этот wire payload внутри
   транзакции, затем digest и outbox. Worker отправляет уже сохранённое тело.
   Старый draft-outbox не переписывается. Для синтетической приёмки — новая
   изолированная БД/stream; старые данные сохраняются. Миграция действующего stream
   требует отдельного плана совместимости, не повторной отправки изменённых тел.
6. **Общий B/API:** №2 типизирует snapshot анализа, наблюдения/индексы признаков,
   checkpoint scope/method/run/effective result и обязательные pinned versions;
   №1 отображает сохранённый B и команды и вводит gate фактических HTTP-ответов.
   UI unknown-retry/poll race и причина established/operator — остаются пунктами
   опубликованного review, текущий импорт их не закрывает.

Следующий результат №2 — ответ по этим шести пунктам, версия общей схемы и codegen.
Следующий результат №1 — адаптация к подтверждённым DTO и полный A04 с проверкой
сохранённого ERP snapshot и ACK для того же digest. Согласованность transport и
