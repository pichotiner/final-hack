По прямому указанию участника текущая позиция роли №1 — [ответ R2-02–R2-10 на коммите 3b45401](https://github.com/pichotiner/final-hack/blob/3b45401/docs/architecture/role1-response-to-role2-review.md). Воспроизводимое чтение: `git show 3b45401:docs/architecture/role1-response-to-role2-review.md`, аналогично для `decision-protocol.md` и остальных файлов `docs/architecture/`. Это чтение удалённой ветки, не её интеграция в текущую. Позиция роли №1 не пересоздаётся вторым документом.

**Вывод роли №2:** базовые выборы принимаются для ограниченного demonstrator. Повторного выбора между QMS/SQL/ES, guard-альтернативами или способами ACK не требуется. Найдены два расхождения документов и одно недоопределённое поле ссылок, требующие адресного ответа перед фиксацией соответствующих проверок/DTO. Есть два уточнения сценария, которые роль №2 может оформить в fixture по уже заданным правилам.

Это согласие с проектной семантикой, не заявление об успешной реализации, общем architecture freeze или промышленном допуске. DP-01 называет свои пять решений принятыми по поручению владельца; здесь это учитывается как текущая база работы, а не заново ставится на голосование.

## 2. Что принимаем без возражений

| Исходный пункт | Позиция роли №2 и предел |

Производственный смысл проходит основной пример: контролёр видит прежние основания, новые сведения, отдельную доработку и повторный контроль; отсутствие подтверждённой причины не мешает признать устранение по достаточным основаниям. При этом `resolve` не подтверждает автоматически причину и не заменяет выпуск.

## 3. Адресные возражения и предлагаемые изменения

### R2-F01 — слово «цикл» объединяет разные случаи

**Пункт:** ответ №1 §5, «Если лимит превышен, обнаружен цикл … транзакция откатывается целиком». Сопоставление: Evidence Graph §2.1 и §5, T11 из impact-review-cases, impact-experiment §«Допущения» различают текущий конфликт и цикл только в историческом объединении.

**Контрпример 1:** в один период A входила в B; затем её сняли. Позже B входит в A. Каждый одновременный состав ацикличен, но объединённые исторические рёбра содержат A↔B. Политика impact-v1 обходит историю; безусловный отказ за цикл заблокирует корректный запрос и последующие события.

**Контрпример 2:** получено сообщение о конфликтном одновременном составе. Полный rollback сохраняет прежнюю внешне полную проекцию. Если сведения о конфликте остаются только на edge и не открывают ограничение в ядре, следующая команда released может пройти по устаревшему основанию. Сообщение оператору об ошибке само по себе не меняет `release_allowed_now`.

**Предложение:**

- Исторический цикл: конечный обход с visited и объяснением пути, без отказа только из-за повторного посещения.
- Противоречивый **одновременный** состав: сохранить валидное по форме исходное утверждение как unresolved/conflict, не устанавливая его как достоверную текущую связь; вместе с ним сохранить неизвестность/ограничение, revision/review/outbox. Это предпочтение роли №2, согласующееся с прежним T11; роль №1 должна определить, к какой команде/импорту оно применяется.
- Исчерпание бюджета обхода или отсутствие технической возможности целиком обработать команду: rollback без accepted по существующему правилу. До восстановления безопасного охвата используется явный производственный регламент ограничения передачи; такую ситуацию не показывать как успешно сохранённый scope constraint.

**Цена альтернатив:** хранение конфликтного утверждения требует состояния unresolved и команды исправления, но уже укладывается в модель неизвестности. Полный отказ импорта проще для БД, однако требует отдельного устойчивого запрета выпуска/разбора, который нельзя потерять с той же откатившейся транзакцией; иначе второй контрпример остаётся. Асинхронный replay ради этого не предлагается.

**Что изменить / проверить:** уточнить §5 ответа №1, привести T11 и выбранный атомарный путь к одному правилу. Отдельные входы: валидная история с циклом в объединении; текущий конфликт; превышение лимита. Ожидания этих трёх проверок не должны совпадать.

### R2-F02 — разная граница M0 для восстановления центра

**Пункт:** DP-01 §0 исключает восстановление после потери центра из первого эксперимента; ответ №1 §11 включает его в «Обязательные инъекции» M0.

**Контрпример:** команда прошла A01–A14, включая рестарт ERP/worker и потерю ACK, но не поднимала центральную БД из старого backup с потерянным решением. По DP-01 граница выполнена, по ответу №1 M0 ещё не принят. Это разные проверки: рестарт процесса не равен disaster restore.

**Предложение:** M0 = A01–A14, согласованные проверки состава/гонок и rollback до commit; восстановление центральной истории — отдельный M0-R/следующий эксперимент. Описание восстановления и его пределов сохраняется в архитектуре. Если роль №1 намеренно расширяет M0, явно обновить DP-01 и добавить самостоятельный fixture потери центральной истории с оракулом сверки ERP/версий.

**Цена альтернатив:** вынесение restore сокращает объём первого стенда, но не даёт права заявлять его проверенное восстановление. Включение требует backup/WAL/ключей, фиксации границы потери, сверки номеров результата и остаточных пробелов — заметно больше, чем restart SQLite/worker.

**Что изменить / проверить:** выбрать одну границу и согласовать DP-01 §0/§7 с ответом §11. В отчёте отдельные статусы: restart проверен / central restore не проверен либо отдельный фактический результат M0-R.

### R2-F03 — как сослаться на контроль без признаков при resolve

**Пункт:** DP-01 §2 и §6 требуют ссылок на повторные observation ID; contracts v0.2 §3 явно назначает observation_id каждому элементу `defects`. Для `no_defect_signs` этот массив пуст.

**Контрпример:** после доработки пришло корректное `inspection_observed`, `no_defect_signs`, `good`, `defects=[]`. Есть raw record, но модель, создающая Observation только по элементам defects, не выдаёт ID для команды resolve. UI не может сослаться на успешный контроль, либо вынужден создать фиктивный дефект.

**Предложение:** до генерации согласовать один тип ссылки на **результат контроля целиком**, независимо от числа дефектов. Минимальный вариант M0 — ссылка на record_id события контроля с проверкой типа/цикла/области/метода; observation_id элементов оставить для отдельных признаков. Альтернатива — отдельный InspectionObservation на каждое событие с дочерними наблюдениями признаков. Новое имя DTO здесь не утверждается единолично.

**Цена альтернатив:** record_id требует серверной проверки предметного типа ссылки, зато не создаёт новый класс ID; InspectionObservation чище разделяет уровни, но требует новой сущности и явного маппинга существующих ID. Обе альтернативы лучше ссылки на «последний хороший контроль» или подстановки фиктивного defect.

**Что изменить / проверить:** точный тип ссылки в resolution DTO и модели B; позитивный resolve с `defects=[]`, негативные ссылки на machine_state, чужое изделие и старый/неподходящий цикл. Если роль №1 уже подразумевает Observation для каждого контроля, достаточно явно закрепить это и отличить ID признака в документах.

## 4. Уточнения M0, не требующие нового архитектурного выбора

### R2-F04 — явный просмотр после позднего события и основания каждой команды

Ответ №1 §11 сокращает путь до «B2/review → новый цикл → resolve → released». DP-01, напротив, требует разрешить зависимые review и закреплять новую пару B/revision после изменений контекста. Основной fixture роли №2 должен раскрыть шаги:

1. D1 подтверждает дефект по B1; получить новый контекст и отдельный B для P1=rework. Не отправлять P1 со старой ревизией D1.
2. После R11 показать stale старой команды; явно рассмотреть новые основания и противоречия. Зафиксировать, каким авторизованным решением и на каких входах разрешено каждое противоречие. Один повторный confirm не делает disputed-точку автоматически assessable.
3. По актуальному контексту подтвердить решение о доработке при необходимости; открыть ровно один новый цикл по выбранному rework-основанию, выполнить run и применимые проверки.
4. Получить отдельные актуальные B для resolve, затем released. Рассмотрение disposition снимает только соответствующий ему review согласно DP-01 §3.3, а не оставшиеся причины дефекта/полноты.

**Контрпример:** автоматическое снятие всех review при resolve позволяет обойти второе противоречие. **Цена уточнения:** дополнительные fixture-команды/основания; это цена уже принятого процесса, не новый механизм. В M0 можно повторять все применимые проверки нового цикла вместо реализации сложных правил переноса; A06 с разрешённым переносом при этом остаётся отдельной заявленной проверкой и требует собственного fixture.

### R2-F05 — V1/V2 для перестановки не должны подменять финальный результат

В ответе §11 V2 обозначает результат после R11, а затем идут новый цикл, resolve и released. Они изменяют публикуемое состояние и порождают последующие версии. Поэтому «V2 остаётся актуальной» верно только для отдельного префикса, в котором получателю ещё не доставлены более новые версии.

**Предложение fixture:** остановить доставку, предъявить две соседние реально сформированные версии (`v`, `v+1`) в обратном порядке, потерять ACK и повторить пакет. Затем продолжить полный маршрут и доставить все последующие версии; актуальная версия ERP должна совпасть с финальным snapshot ядра. Либо выполнить A09 на отдельной базе эмулятора. Номера версий не равны R-ID исходников или context_revision и не сбрасываются ради показа.

**Контрпример:** после released в ядре оставить в ERP ранний rework/review V2 и объявить весь сквозной путь завершённым. **Цена альтернатив:** отдельная изолированная проверка доставки проще, но сама не доказывает финальную синхронизацию; продолжение общей трассы требует последней сверки, не нового протокола.
