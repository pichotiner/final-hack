### R1-PR6-01 · P1 · Отказ повтору ошибочно снимает неизвестность первой команды

**Где:** `frontend/src/api.ts:51–53`, `frontend/src/App.tsx:68–77`,
`frontend/src/review-state.ts:42–47`.

Контрпример: решение закоммичено, ответ потерян; до точного повтора у пользователя
отозваны права. Повтор получает 403 **до поиска успешного ключа**, как требует DP-01.
Клиент считает любой 4xx окончательным отказом, переводит `unknown → rejected`,
после чего разрешает clear/новое рассмотрение и теряет первоначальную команду.
403 повтору не доказывает, что первая попытка не была принята. Аналогичная проблема
есть с 401 и отказом до обработки команды на промежуточном HTTP-узле.

**Исправление №2:** различать окончательный отказ первой попытке и невозможность
узнать результат ранее неизвестной команды. Сохранять исходные body/key/actor/target
до квитанции исходного результата или авторизованной сверки. Восстановление
учётных данных не должно автоматически менять автора/ключ операции.

**Проверка:** commit → потеря ответа → отзыв прав → retry 403; pending сохраняется,
изменённая новая команда не предлагается как безопасная замена. После восстановления
прав исходный retry возвращает 200 и прежний decision ID. Ошибка воспроизведена
на реальных `request`/`reviewReducer` с подставленным HTTP 403, без backend commit.

### R1-PR6-02 · P1 · Контракт цикла не передаёт доказанную привязку контроля

**Где:** `contracts/openapi.yaml:204–217,394–407`,
`contracts/external-openapi.yaml:118–141`, `emulator/generate.py:61–80,190–195`;
сопоставление: `backend/app/domain/quality.py:1627–1641`.

`CycleCommand` содержит только planned run IDs, ответ — ID цикла и revision.
Задание не описывает обязательные операции, фазу/источник/компонент каждой проверки
и её привязку к run/сессии. У входного контроля run отсутствует; fixture отправляет
только заявленный `control_cycle_id`. В P3 такой вход без зарегистрированной сессии
остаётся `observation_cycle_unresolved`: одного заявления источника о цикле мало.
Прямой вызов текущего ядра с неизменным `incoming-1` подтвердил unresolved и missing.

Есть и отдельное расхождение повторного входного контроля: fixture
`incoming-recheck` связывает фазу incoming с rework run, тогда как текущая `_usable`
принимает incoming без run. Подмена названий DTO этого не исправит.

**Исправление обеих ролей:** закрепить версионированный план операций/точек и
отображение checkpoint → run/control session. Для проверки без run нужен явный
зарегистрированный идентификатор сессии. Сервер назначает цикл, формирует/проверяет
привязки по плану и делает их доступными источнику/runner. Уточнить область и
семантику incoming-recheck. №2 формализует схемы и входы; №1 реализует импорт и
отображение в ядро. Поля могут поступать из закреплённого адаптерного профиля,
но не угадываться по строкам ID или порядку доставки.

**Проверка:** A04 на реальном импорте и HTTP, затем поздний вход старого цикла
не закрывает точку нового. Смена только `control_cycle_id` не легализует чужой run.

### R1-PR6-03 · P1 · DTO B теряет содержание рассмотренных доказательств

**Где:** `contracts/openapi.yaml:423–472`, UI `frontend/src/App.tsx:132–142,153–158`.

`BasisInput` передаёт raw record/source/event, но не ID/индекс наблюдения признака.
`Basis` не типизирует сохранённый результат анализа; `CheckpointAssessment` не
передаёт компонент/область, метод, run и эффективный результат. В карточке также
нет отображения отдельных признаков/областей. Для raw с двумя дефектами контракт
не позволяет типизированному клиенту объяснить, какое наблюдение относится к
карточке; для старого B нельзя показать прежний результат анализа лишь по списку
record IDs. Произвольные дополнительные JSON-поля не являются общим DTO/codegen.
Это расходится с DP-01 §1.2 и §3.2. P3 уже сохраняет более богатые snapshots.

**Исправление №2:** типизировать ссылки на элементы признаков и сохранённые
результаты анализа, область/метод/run/эффективные результаты полноты; задать
обязательные имена pinned versions. **№1:** построить транспортное представление
из сохранённого B и raw provenance, не из текущих проекций. Не заменять неизвестные
версии вымышленными значениями и не назначать всем входам роль used.

**Проверка:** два признака одного raw, разные области, затем late и смена контекста;
старый B показывает исходные связи и анализ, новый — изменения. Проверять ответы
реального сервера общей JSON Schema, а не только положительные входные fixtures.

### R1-PR6-04 · P1 · ERP-снимок не сохраняет ссылку на решение по изделию

**Где:** `contracts/external-openapi.yaml:54–85`;
`backend/app/domain/quality.py:1117–1176`.

Внешняя схема запрещает дополнительные поля, но ссылки на решения/B разрешает
только внутри `confirmed_nonconformities`. Для выпуска изделия без подтверждённых
дефектов этот массив пуст: нет ссылки ни на disposition decision, ни на его B.
При поздних данных нельзя проследить, какое историческое released осталось в
снимке. P3 сохраняет `disposition_decision`, однако PR отвергает это поле.

Дополнительно доказана текущая несовместимость отправки: реальный payload `_emit`
отклоняется валидатором PR из-за лишних `item_id`, `disposition_decision`,
`disposition_review_required`, `nonconformities`, `kpi` и отсутствующего
`confirmed_nonconformities`. Это ожидаемая работа интеграции №1, не поломка SQLite.

**Исправление №2:** добавить nullable-ссылку/снимок актуального disposition с
decision ID и basis ID; null допустим только до первого решения. **№1:** после
согласования формировать именно внешний payload **до commit outbox**; digest
вычислять от него. Переводить внутренние поля в worker после фиксации digest нельзя.
Уже сохранённые/отправленные сообщения не переписывать под теми же ID; стратегия
совместимости старого draft-outbox должна быть явной до переключения стенда.

**Проверка:** normal released с пустым списком дефектов; late сохраняет ссылку на
старый disposition/B, выставляя текущие blockers; полный HTTP ACK проходит проверку
ядром для байтов, реально сохранённых в outbox.

### R1-PR6-05 · P2 · Гонка polling и отправки бросает исключение в React reducer

**Где:** `frontend/src/App.tsx:68–72,81–84`,
`frontend/src/review-state.ts:35–38`.

Если poll с rev6 уже поставлен в очередь, а обработчик submit ещё использует
отрисованный rev5, предварительная проверка stale может пройти. Затем reducer
обрабатывает poll → prepare и бросает исключение. `dispatch` не является
синхронной проверкой: HTTP-запрос из `send` уже может начаться, а исключение reducer
при рендере не ловится try/catch обработчика. На корне нет ErrorBoundary;
пользователь рискует потерять экран и сохранённое тело незавершённой команды.
Чередование poll → prepare и исключение воспроизведены на reducer; браузерный
crash/E2E в этой сессии не запускался.

**Исправление №2:** допустимые сетевые гонки должны давать управляемое состояние,
не исключение рендера. Запускать запрос после принятого перехода в sending,
сохраняя его исходное тело. **Проверка:** component test с управляемым завершением
poll перед submit; отсутствие запроса либо управляемый stale-ответ, UI остаётся жив.

### R1-PR6-06 · P2 · Windows даёт ложный сигнал дрейфа TypeScript

**Где:** `frontend/scripts/check-generated.mjs:9–12`.

На чистом checkout с CRLF `npm run check:generated` завершается
`Outdated generated TypeScript: api.ts`. `git ls-files --eol` показывает
`i/lf w/crlf` для обоих generated TS. Независимая повторная генерация доказала:
оба файла равны после нормализации CRLF → LF; содержательного дрейфа нет.

**Исправление №2:** закрепить LF для generated через `.gitattributes` либо
нормализовать только переводы строк при сравнении. Генерируемые файлы вручную
не менять. Проверить gate на Windows и Linux и сохранить обнаружение реального
изменения поля схемы.

## 3. Ответ на R2-F01–03

Это позиция владельца ядра по конкретным предложениям №2. Она не объявляет
весь контракт PR согласованным или реализованным.

### R2-F01 — принимаем различение трёх случаев

1. Цикл лишь в объединении исторических связей: конечный обход с visited;
   сам по себе не ошибка одновременного состава и не основание отката.
2. Валидное авторизованное утверждение о конфликтном одновременном составе:
   сохранить исходное утверждение unresolved/conflict, не применять как достоверную
   связь; вместе зафиксировать ограничение области, revision/review/outbox.
   Неизвестный охват ограничивает весь demonstrator, включая будущие изделия.
   Это требование к будущему входу утверждений фактического состава, а не право
   пропускать невалидную схему/неавторизованный источник или создавать новый source
   event без спецификации. Нынешний импорт `ProductionContext` не реализует эту модель.
3. Технический сбой/лимит обхода: полный rollback, без accepted и без утверждения,
   что ограничение сохранено. Производственный регламент деградации остаётся нужен.

Цена — журнал конфликтных утверждений и отдельное разрешение вместо простого отказа
импорта. Проверки исторического цикла, одновременного конфликта и лимита должны иметь
разные исходы. Прежняя общая формулировка в ответе №1 §5 уточнена.

### R2-F02 — принимаем отдельную границу central restore

M0 проверяет A01–A14 и согласованные проверки состава/гонок/rollback. Central
disaster restore из старой копии — отдельный M0-R с backup/WAL/ключами и сверкой ERP.
Restart API/worker/SQLite не доказывает восстановление потерянных B/решений.
Условие остановки исходящей доставки после restore из DP-01 сохраняется.
Цена — отсутствие подтверждённой disaster-recovery гарантии у первого M0.
Прежнее включение central restore в обязательные инъекции №1 §11 исправлено.

### R2-F03 — поддерживаем control_record_ids как внешний тип ссылки

Для resolve ссылка должна указывать на **принятый raw record всего контроля**,
включая `no_defect_signs` / `defects=[]`. Это снимает неоднозначность элемента
массива defects и не требует фиктивного дефекта. Внутренние observation IDs
остаются отдельными; текущий P3 уже создаёт наблюдение и для пустого массива.

№1 реализует разрешение record → контроль внутри guard, после проверки успешного
повтора исходного тела команды. Проверяются тип, права, item, активный цикл,
checkpoint/область/метод, завершённая доработка и её время, отсутствие противоречий,
принадлежность рассмотренному B. В решении сохраняются исходные ссылки и точное
внутреннее отображение. Строка `record_id + ':0'` не является публичным протоколом.
Положительный случай — хороший контроль без признаков; отрицательные — machine_state,
чужое изделие, старый цикл, другая область, контроль до завершения доработки.

Цена — предметный lookup/валидация типа ссылки. Альтернатива с отдельным ID
InspectionObservation допустима позже. При фиксации транспортного контракта
оформить уточнение терминов DP-01 §6 новой версией по его §8, затем регенерировать
DTO. В этой сессии принята позиция review №1; действующая DP-01 v1.0 не переписана.
