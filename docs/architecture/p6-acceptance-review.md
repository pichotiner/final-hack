## Решение до изменения кода

Проблема: серверный A04 и компонентные тесты не доказывают путь человека.
Альтернативы: повторить Python-тест; записать ручной показ; добавить живой
браузерный runner с независимыми ожиданиями. Выбран третий вариант: Chromium,
реальные API/worker, PostgreSQL, отдельный SQLite ERP. Действия контролёра и
мастера выполняются через UI; станок и камера подают события по HTTP.
ERP импортируется штатным CLI. Входы и ожидания PR №8 остаются отдельными.
Цена: браузерная зависимость и изолированный стенд. Отказ: тест проверяет
подменённые ответы или самоутверждающиеся ожидания. Проверка: HTTP-трассы без
credentials, снимки до/после, реальная запись видео и сравнение с исходным JSON
ожиданий. Пересмотр: публичный DTO не позволяет проверить требование — BLOCKED,
а не выдуманное значение или смена ожидаемого результата.

Общий контракт 0.4.0 и транзакционная граница сохраняются. Новые runtime-команды
carry/scope/disputed требуют отдельной согласованной контрактной поставки.
Это не независимое одобрение роли №2: её ожидания исполняет роль №1.

## Фактический эксперимент, 26.09.2026

Команда из `backend/`: `./.venv/Scripts/python.exe scripts/acceptance_demo.py
--publish --slow-ms 250` (Windows 10, Python 3.11.9, Node 24.12.0,
Chromium Playwright 1.56.1, PostgreSQL из `deploy/compose.dev.yaml`).
Опубликованы [18 отдельных результатов](../demo/results-summary.json),
[один непрерывный скринкаст](../demo/walkthrough.webm),
[исходный A04/B/ERP/ACK](../demo/a04.json),
[входной импорт](../demo/import.jsonl), [среда](../demo/environment.json)
и несколько кадров в `docs/demo/`. Полная HTTP-трасса, логи, SQLite ERP
и одноразовые учётные данные находятся в игнорируемом `.local/p6-*/`.
Отдельный выпуск `assembly-002` и A04 `assembly-001` пройдены через настоящий
Chromium; входы источников/worker передавались по HTTP/CLI. Ожидания
`docs/acceptance/role2-m0-expected.json` не редактировались под результат.

Синтетика: `order-001`, две операции/два оператора/три контроля. Нормальный
выпуск — решение с B в ERP и сохранённый ACK. A04: confirmed=1,
resolved=1, open=0, rework=1; три новые записи контроля, старое B сохранилось,
resolved-карточка осталась в ERP, после потери ACK worker получил duplicate,
старые версии superseded и current ERP остался released. В отдельной
браузерной проверке ответ после commit терялся управляемо (Playwright route),
повтор с 403 **инжектирован**; следующий точный retry вернул прежнее решение.
Это проверка клиента на отказ и сервера на дедупликацию, а не управление
реальным реестром прав во время сессии.

Успешные отдельные проверки того же стенда: poor+negative, incoming defect,
missing final, disputed result, duplicate, second observation, two signs,
machine warning + operator action, late event / stale rejection, wrong session
/ run / cycle, запрет решения источнику/чужого B, ERP V2→V1→V2 и два 409
конфликта получателя. PASS отдельного подслучая не повышает всю строку
независимой карты до PASS автоматически.
Вариант `R2-LATE` из входов роли №2 (late после confirm/rework до ремонта)
не выполнялся: текущий поздний факт проверен на **ранее выпущенном**
`assembly-002`; его числа нельзя считать ожиданиями `R2-LATE`.
