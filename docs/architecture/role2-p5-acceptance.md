# Независимая приёмочная карта роли №2

26.09.2026. **Спроектирована; все проверки ниже NOT RUN для общего P5.**
Нормативная база: [DP-01 §7](decision-protocol.md), review,
исходная постановка §2–5 и критерии оценки. [Передача и зависимости](role2-p5-handoff.md).

## Порядок и доказательства

Сначала normal release без дефекта и A04 до ERP ACK, затем негативные сценарии.
Каждый независимый случай запускается на отдельной тестовой БД/потоке либо на
явно описанном чистом наборе изделий. Не менять предметные таблицы вручную для
получения нужного результата. Инъекции технического сбоя допустимы только в
изолированной тестовой среде и описываются в отчёте.

Номера B, record, cycle, decision и message получаем от сервера. Их нельзя
предсказывать по строкам ID. Ожидания задаются до запуска, отдельно от входов.
Проверяются общая JSON Schema, предметный результат и отсутствие лишних эффектов.
Снимки «до/после» получают в момент соответствующего шага, не восстанавливают
позже из текущего состояния. Для UI нужны управляемые завершения запросов, а не
случайные задержки, которые иногда воспроизводят гонку.

## R1-PR6-01–06: закрытие замечаний

| ID | Воздействие | Обязательный результат / свидетельство |
| --- | --- | --- |
| 01 | Commit команды → потеря ответа → отзыв прав → точный retry с 403/401 → восстановление прав → retry | Экран хранит прежние body/key/actor/target и неизвестный исход; нельзя заменить команду новой. После восстановления — прежний decision ID, без прироста решений/версии от повтора. Отдельно первая заведомо отклонённая попытка |
| 02 | Импорт профиля → цикл → контроль с зарегистрированной сессией; затем старый session, чужой run, смена только cycle ID | Правильный контроль закрывает свою точку; три подмены не закрывают новый цикл. Incoming без run, но с session; сервер возвращает принятые bindings |
| 03 | Один raw с двумя признаками/областями → сохранить B1 → late → B2 | Различимы observation ID/индекс, область, метод, run, результат; B1 и его анализ неизменны, B2 отражает новые сведения; неизвестные версии не выдумываются |
| 04 | Normal released без дефектов → late; отдельно resolved defect | В каждом результате после disposition есть decision/B/автор/причина. После late сохраняется старое решение, текущий выпуск запрещён. Resolved карточка не исчезает. Сверить outbox/ERP/digest/ACK |
| 05 | Завершить poll новой revision перед prepare старой команды; также после перехода sending | Нет исключения рендера; либо запрос не начинается, либо сервер управляемо отклоняет stale. Исходная уже отправленная команда не меняется; экран остаётся работоспособным |
| 06 | Чистый checkout LF и CRLF, повторная генерация; затем реальное изменение поля схемы | Переводы строк не дают ложной ошибки, реальное рассогласование обнаруживается. Проверить Linux и Windows; отсутствие Windows отметить BLOCKED, не экстраполировать Linux |

## A01–A14: общий сервер, интерфейс и получатель

| ID | Подготовка / действие | Независимое ожидание | Что сохранить |
| --- | --- | --- | --- |
| A01 | Открыть B1, принять late, отправить новую команду с прежней revision | 409 stale_revision; нет решения/outbox от отклонённой команды | B1/B2, запрос/ответ, число решений до/после |
| A02 | Принять решение, затем late | Старые B/решение прежние; новое review; исторический release не означает текущего разрешения | Оба B, решение, текущие blockers |
| A03 | Успешная команда, потеря ответа, poll, точный retry; потом изменить тело с тем же ключом | 200 с прежним результатом; изменённое тело 409. Повтор после отзыва прав не снимает unknown | Исходное тело/ключ без credentials, оба ответа, UI |
| A04 | Confirm → rework → новый цикл → завершённая доработка → три допустимых повторных контроля → resolve → отдельный released | confirmed=1, open=0, resolved=1, rework=1; старый B прежний; один дефект сохраняется в ERP; финальный ACK сохранён ядром | Все квитанции/решения/B, ERP body и ACK, delivery |
| A05 | Resolve до завершения ремонта; без нового контроля; контроль до ремонта; release до resolve | Каждый отказ без частичного решения/outbox; ранее принятые факты остаются | Отдельный чистый случай для каждого отказа |
| A06 | В новом цикле только старый финальный контроль; затем явный разрешённый перенос другой точки | Финальная точка missing; перенос с правилом и ссылкой закрывает только допустимую точку | B/правило переноса/команда. Нет workflow — BLOCKED |
| A07 | Отдельно missing, poor+negative, unknown route, contradictory observations | Различимые причины запрета выпуска; reject карточки не делает poor пригодным; новый контроль относится к нужной точке | Raw, эффективный результат, blockers и попытка release |
| A08 | Дубль сообщения; второе наблюдение того же полного source/item/component/region/ref | Дубль: 0 новых raw/revision/KPI/outbox. Второе наблюдение сохраняется, кандидат один | Квитанции и счётчики до/после; иной source/ref отдельно не сливать |
| A09 | Отправить V2, V1, повтор V2 одного потока | applied, superseded, duplicate; текущая V2; квитанция повтора равна первоначальной | История приёма и отдельное чтение текущего результата |
| A10 | Тот же message ID с другим телом; та же версия с новым ID; чужой digest в ACK | Два конфликта 409; неверная квитанция не закрывает доставку | Запросы, ответы, состояние очереди |
| A11 | ERP commit → потеря ACK → перезапуск ERP и worker → retry | Прежнее тело/ID, исходная квитанция, одно бизнес-применение; очередь подтверждена | Устойчивое состояние до/после процессов, совпавший digest |
| A12 | Источник вызывает решение; чужой B; stale B; сбой между решением и outbox | Запрет/несоответствие/stale; при техническом сбое rollback всех эффектов команды | Авторизованные ответы, инъекция сбоя и отсутствие частичной записи |
| A13 | Две причины unknown scope → новое изделие → разрешить одну причину | Новое изделие заблокировано; вторая причина остаётся; автоматического release нет | Ограничения, новые изделия, команда снятия. Нет endpoint — BLOCKED |
| A14 | После resolve/released приходит противоречащее событие → новый просмотр | Исторические resolve/released прежние; review и запрет выпуска; нужны новые решения | Старый и новый B, история решений и внешние версии |

Дополнительно G01: поздний факт компонента достигает исторической сборки, но
не исключает другие изделия без подтверждённой полноты. G02: факт до установки
находит сборку после принятия установки без повторной подачи raw. G03: исторический
цикл, одновременный конфликт и технический лимит имеют разные исходы согласно review.
Скрипт поиска без runtime-транзакций не закрывает эти проверки.

## Формат протокола фактического прогона

Для каждой строки: `case_id`, commit ядра/контракта/UI/ERP, ОС и версии,
команда/шаги, отдельный expected, actual, ссылки на обезличенные HTTP-трассы,
снимки B/решения/ERP и screenshot при необходимости, результат и ограничение.
Статусы: NOT RUN (не запускали), BLOCKED (нет зависимости), FAIL (ожидание нарушено),
PASS (проверено с приложенным доказательством). Обход через внутренний Python вместо
публичного API отдельно отмечается и не закрывает сквозную строку.
