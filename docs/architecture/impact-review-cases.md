# Адресный пересмотр: независимые ожидаемые результаты

Дата: 25 сентября 2026. Роль №1. **Статус: спецификация приёмки для review; программные проверки ещё не выполнены.** Входы F0–F12 хранятся отдельно в §6 [Evidence Graph](evidence-graph.md). Это дополнение к сценариям [модели оснований](evidence-model.md), а не замена полного demo.

## 1. Оракул сценариев

«Цель поиска» означает изделие для оценки влияния. Review возникает у актуального решения при изменении его оснований/неопределённости; если решения ещё нет, обновляются анализ и ограничения контроля. Во всех строках исходные B/решения неизменны; поиск влияния не подтверждает причину, не увеличивает число дефектов и не выдаёт released.

| ID / вход | Ожидаемое поведение | Какую ошибку обнаруживает |
| --- | --- | --- |
| T01 / F1 | assembly-001 включена; D1/P1 требуют review, в новом B есть R11; assembly-002 исключена при подтверждённых условиях F0. По полному ключу mark-001 остаётся один подтверждённый дефект и 0 ошибок оператора | Поиск только по ID старых оснований возвращает пустое множество |
| T02 / F2 | Включены insert-001 и assembly-001; причина для сборки содержит M1. Раннее время RC не отсекает сборку. assembly-002 исключена. Автоматическое слияние карточек RC и mark-001 не выполняется | Фильтр по интервалу установки или только равенству item_id теряет влияние |
| T03 / F3 | Точный повтор возвращает исходную квитанцию; число raw, ревизий, review-причин и outbox неизменно. Изменённое тело даёт конфликт, без изменения состояния | Повтор запускает replay/новую задачу или конфликт затирает исходник |
| T04 / F4 | Включены insert-001, assembly-001 и assembly-003; у каждого пути указана историческая/текущая связь. assembly-002 исключена. Это кандидаты оценки, не три установленных дефекта | Обход текущего состава теряет прежнюю сборку; снятие ошибочно считается устранением влияния |
| T05 / F5 | Включены обе сборки: assembly-001 по старому M1/B1, assembly-003 по новому M3. Старые M1/B1 не подменены; исправление видно в diff | Исправление связи удаляет следы ошибочного решения |
| T06 / F6 до разрешения | Обе возможные сборки получают неполноту оценки; текущий результат D-A2 требует review. U1 не становится надёжным наблюдением сразу двух изделий | Неизвестность либо теряется, либо превращается в два достоверных дефекта |
| T07 / F6 после разрешения | Пересчитываются обе прежние кандидатные сборки; assembly-001 получает установленную связь. Для assembly-002 закрывается только кандидатная неопределённость U1 с основанием; старое решение не заменяется новым released автоматически | Разрешение обрабатывает только новую цель и оставляет старую в вечной неопределённости либо очищает все review |
| T08 / F7 | Охват помечен неполным; открыта задача участка S. Команда released для нового assembly-004 не проходит, пока применимость ограничения не разрешена | Одноразовый список известных изделий пропускает будущие изделия |
| T09 / F8 | При появлении M1 пересчитывается assembly-001 с ранее принятым RC; повтор RC для запуска не нужен. Исходная квитанция RC не переписывается | Подписка на компонент видит лишь будущие события |
| T10 / F9 | Включены assembly-001 и module-001, P-M требует review. Пути M1/M4 и зависимость от P1 объяснимы; несколько путей дают одну задачу на цель с несколькими причинами | Одношаговый обход не доходит до верхней сборки или дублирует задачи |
| T11 / F10 цикл | Обход завершается; конфликт состава сохранён как неопределённость, полнота охвата не объявлена доказанной, released недопустим для затронутой области | Цикл зависает или молча превращается в валидное дерево |
| T12 / F10 лимит | Команда полностью откатывается, accepted отсутствует; источник сохраняет событие. Явная ошибка отличается от успешного пустого охвата | Ограничение обхода выдаёт частичный результат как полный |
| T13 / F11 | Только будущая применимость route@2 не меняет B существующих сборок. Явная применимость к обеим сборкам запускает их пересчёт; старые B остаются на route@1 | `latest` меняет прошлое либо замена общей версии не находит всех потребителей |
| T14 / F12 | Сигнал insert-002 не затрагивает assembly-001 лишь из-за одинаковой модели/типа маршрута. Поздний not_assessable по assembly-001 включается в её новый B и вызывает review по изменению оснований | Обход всех рёбер разносит локальный дефект по общей модели; фильтр только defect_signs теряет неопределённость |

T07 не гарантирует автоматическое восстановление применимости D-A2: для первого пилота основание актуального результата рассматривает контролёр. Закрытая техническая причина U1 и подтверждённый человеком выпуск — разные действия.

## 2. Проверки транзакционной границы после реализации

Нужны настоящие независимые соединения PostgreSQL и барьеры выполнения, а не задержки `sleep` с вероятностным исходом. Все writers должны использовать проектный guard. Ожидаемые исходы:

| ID | Управляемое чередование | Результат |
| --- | --- | --- |
| C01 | Зафиксировать R11, затем подать решение с ревизией F0 | stale_revision; новой записи решения нет |
| C02 | Зафиксировать решение, затем R11 | Решение и его B доступны без изменений, review по новой ревизии открыт |
| C03 | RC → установка; отдельно установка → RC | В обоих порядках после двух commit сборка учитывает RC; различаются лишь законные исторические версии |
| C04 | Ошибка после подготовки нового B, до commit | Откат raw/анализа/индекса/review/outbox вместе; повтор способен завершиться |
| C05 | Commit успешен, ответ источнику потерян | Повтор возвращает прежний результат, счётчики и версии не меняются |
| C06 | Открыты две причины review; D2 рассматривает одну либо старую ревизию | Нерассмотренная причина сохраняется; stale-команда отклоняется; review disposition не закрывается автоматически |
| C07 | Новое изделие/решение одновременно с ограничением неизвестной области | Либо ограничение видно команде, либо последующее изменение помечает принятое решение для review; изменение не теряется |

Доставка outbox требует отдельных проверок потери ACK и V2 раньше V1 из модели оснований; прохождение C01–C07 само по себе их не подтверждает.

## 3. Инварианты для будущего эксперимента

- Полный перебор небольшого набора отношений по impact-v1 и индексный поиск дают одинаковые цели и одинаковую оценку полноты. Оракул не должен вызывать проверяемый поиск.
- Перестановка порядка хранения рёбер/входов не меняет множество целей и предметный diff; стабильные ID дают воспроизводимый путь объяснения.
- Добавление применимой исторической связи не уменьшает охват impact-v1. Исправление/разрешение неизвестности отдельно пересчитывает старую и новую области.
- Изъятие доказательства полноты состава не может превратить «возможно затронуто» в «точно независимо».
- Транспортный повтор, несколько путей и повторный неизменный replay не увеличивают число логических дефектов, задач на одну цель и версий результата.
- Для каждого включённого решения существует объяснение: точная зависимость, область ожидания или явная неизвестность. «Алгоритм так решил» не является объяснением.

## 5. Протокол проверки этой поставки

Выполнен авторский ручной разбор контрпримеров: новый факт вне B1, наблюдение до установки, снятый компонент, поздняя связь и ограничение для будущего изделия. По разбору выбраны WATCHES, исторический обход impact-v1, обратная обработка при новой связи и предикат неизвестной области. Это проверка согласованности проектной модели, не выполнение T/C в программе и не взаимное review.

Критерий остановки проектного участка: каждая цель имеет объяснимый путь; независимость имеет условия; неизвестность не равна пустому охвату; сохранены старые основания; указаны транзакционная цена и стык роли №2. До реализации №2 должен оспорить производственные допущения F0/F4/F6/F7 и подтвердить владельцев данных. Проверка исходных файлов: `git diff --check` из корня репозитория (результат запуска фиксируется в отчёте сессии).
