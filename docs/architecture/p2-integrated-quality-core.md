# P2: интегрированное доказательное ядро роли №1

Дата: 26 сентября 2026. Статус P2: **реализовано и проверено во внутреннем Python/PostgreSQL-контуре.** Продолжение — [P3](p3-server-integration.md): HTTP и worker уже подключены; замечания ниже об ожидании транспорта описывают границу предыдущего инкремента.

## Что изменилось

Устранён разрыв между экспериментами журнала и решений. `PostgresProductionJournal` использует один PostgreSQL transaction guard и атомарно сохраняет:

```text
аутентифицированный source event
→ зашифрованный raw
→ traceability projection
→ quality context / observation / review
→ immutable Basis
→ full-snapshot outbox
```

Сбой до commit откатывает все перечисленные эффекты. Старые writers не могут писать в quality-managed item: это исключает одновременное использование несовместимых per-item и общего протоколов.

### Исправленные предметные дефекты

- Выпуск требует импортированного версионированного задания, состава, маршрута, завершённых обязательных операций и пригодного контроля каждой точки.
- `poor/unknown`, ненадёжная идентификация, время, неизвестный метод, отсутствующий record ID и непривязанный цикл не закрывают контроль. `reject` не исправляет плохое наблюдение.
- Старый `control_cycle_id` нельзя открыть снова; одному disposition rework соответствует один новый цикл с новыми плановыми run ID.
- Повторный контроль после ремонта проверяется по `occurred_at` относительно завершённой rework-операции, а не по времени приёма.
- Логический ключ дефекта больше не включает цикл: один `defect_ref` одного источника/изделия/компонента/области остаётся одним дефектом между циклами. Неизвестный ref не сливается автоматически.
- Basis сохраняет версии производственного контекста, историю, точные record ID, решения, blockers и снимок анализа. Старый B читается отдельно от нового.
- Установленная причина требует явного решения и evidence из рассмотренного B. Ошибка оператора требует совпадающих operation/operator/action; одной хронологии недостаточно.
- Неизвестная область создаёт pilot-wide constraint, который блокирует существующие и будущие изделия. Каждая причина снимается отдельной идемпотентной командой по актуальным B всех изделий.
- RFC 8785 используется для команд/outbox. ACK проверяет stream, версию, digest и состояние commit получателя. Тело outbox защищено от UPDATE/DELETE/TRUNCATE в БД.
- Автор команды задаётся `ProductionService` по аутентифицированному principal; источник, контролёр и мастер имеют разные права. Секретный ключ загружается только из обязательного secret-файла без значения по умолчанию.

## Проверки

Из каталога `backend/`:

```powershell
.\.venv\Scripts\python.exe -m pytest -m "not integration"
.\.venv\Scripts\python.exe scripts/test_postgres.py
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m pip check
```

Проверяются, среди прочего: ложный выпуск после poor/reject, повтор цикла, late event, один дефект между циклами, полный B, rollback после уже рассчитанной quality-проекции, общий guard при параллельных событиях, серверный автор/RBAC, unknown scope, явная причина, неизменность outbox и полный ACK.

## Граница доказательства

Это внутренний серверный контур, а не готовый пользовательский MVP. Пока отсутствуют:

- согласованный OpenAPI `0.3.0` для `/api/v2` и `/external/v2`;
- generated Python/TypeScript DTO и contract gate фактического HTTP-сервера;
- отдельный persistent ERP-эмулятор, UI и скринкаст;
- parser конкретных форматов 1С/Галактики/MES/КОМПАС;
- промышленный edge spool, TLS deployment, backup/restore и нагрузочный стенд;
- полная аналитика по линиям, участкам, сменам и сопоставимым работам.

Старая спецификация `origin/codex/role-2-mvp:contracts/openapi.yaml` имеет версию 0.2.0 и пути `/api/v1`; она не подключена, потому что DP-01 требует намеренно несовместимый `/v2`.

## Передача роли №2

Нужны OpenAPI v0.3.0, positive/negative fixtures A01–A14, generated DTO, persistent ERP receiver и минимальный UI. Транспорт вызывает `ProductionService`; `actor_id`/`source_id` не берутся из тела. Условные правила schema, которые генератор не выражает, должны проходить `validate_source_payload()` до commit.

Роль №1 после получения спецификации добавляет тонкий HTTP-адаптер и contract tests, не создавая параллельную схему. До этого внутренние методы не объявляются публичным API.
