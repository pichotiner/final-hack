# DP-01. Правила решений, повторного контроля и обмена с ERP

**Версия: 1.0. Дата: 26 сентября 2026. Статус: принято для ограниченного demonstrator по прямому поручению владельца проекта.** Редактор — роль №1 / GPT Astra. Владелец проекта поручил самостоятельно выбрать и зафиксировать правила для обеих ролей; участие второго разработчика в принятии этого документа не заявляется.

**Этот файл — рабочее задание обеим ролям по пяти вопросам.** Повторного выбора этих правил перед началом указанного эксперимента не требуется. При обнаружении противоречия постановке или невозможности реализации зафиксировать конкретный контрпример и предложить изменение DP-01, а не реализовывать другой смысл молча.

Механизмы ниже **спроектированы**. Их публикация не означает реализацию, успешную программную проверку или промышленный допуск. Это фиксация семантики одного эксперимента, не принятие всей целевой архитектуры предприятия.

## 0. Прочитать сначала: пять решений

| Вопрос | Принятое правило |
| --- | --- |
| Что рассмотрел контролёр? | Неизменяемый набор оснований `basis_id` и закреплённую ревизию контекста изделия. Фоновое обновление не подменяет их в форме |
| Как выпустить после ремонта? | Сохранить подтверждение дефекта; отдельно подтвердить его устранение по новому контролю; затем отдельно разрешить выпуск |
| Когда контроль полный? | Известен применимый маршрут и для каждой обязательной точки текущего цикла есть допустимое основание. Пропуск, неоценимость и неразрешённый конфликт блокируют выпуск |
| Что передавать в ERP? | Полный снимок результата, монотонный номер версии и стабильный ID сообщения. Старая версия не заменяет новую |
| Что означает ACK? | Получатель устойчиво сохранил сообщение и атомарно либо применил его как актуальное, либо признал устаревшим. Это не подтверждение физического удержания/отгрузки изделия |

## 1. Ревизия контекста и неизменяемые основания

### 1.1. Единица конкурентного контроля

Используем **одну монотонную `context_revision` на изделие** для всех команд по его карточкам, устранению, циклам и выпуску. Это не `revision` технического снимка уже существующего traceability-эксперимента.

Ревизия увеличивается один раз за успешно принятую команду/событие, изменяющее предметный контекст: новые релевантные факты, решения, связи, применимый маршрут, полноту, причины review или ограничения. Изменение общей зависимости инвалидирует затронутые изделия; новое изделие проверяет уже открытые ограничения. Транспортный дубль, неизменный replay, polling, попытка доставки и ACK ревизию не меняют.

В DTO чтения `Item` и `Nonconformity` добавить `context_revision`. Если для перехода сохраняется прежнее поле `revision`, оно должно быть явным deprecated-алиасом **этой же** величины, а не независимой ревизией строки карточки.

### 1.2. Что такое B

`basis_id` — серверный идентификатор неизменяемого набора оснований. B хранит:

- цель: изделие и, где применимо, карточку; `context_revision` и `control_cycle_id`;
- точные ссылки на исходники: `record_id`, с доступным отображением в `(source_id,event_id)`; для элемента дефекта — `observation_id`;
- входы, противоречащие сведения и исключённые входы с причинами;
- закреплённые версии задания, маршрута, состава, связей, правил анализа и обработчика; версии анализаторов берутся из наблюдений;
- результаты анализа, полноту, неизвестность и доступность требуемых доказательств;
- использованные предыдущие человеческие решения, например подтверждение дефекта или решение о его устранении.

Набор можно построить заранее при формировании представления для рассмотрения. При сохранении команды сервер проверяет, что B существует, принадлежит указанной цели/циклу, доступен пользователю и относится к актуальной ревизии. Клиент не присылает произвольный список фактов вместо серверного B. Старый B не пересобирается по `latest`, `occurred_at` или времени решения.

**Входная команда человека:** действие, непустой `reason`, `expected_revision`, `expected_basis_id`, `idempotency_key`; автор и время — только из сервера. Сохранённое решение содержит отдельный ID, автора/время, действие, причину, `basis_id`, цикл и ссылку на замещаемое решение при пересмотре. В ответе различать рассмотренную ревизию и новую ревизию контекста после команды.

### 1.3. Правило UI

По явному действию «Начать рассмотрение» / «Рассмотреть обновлённые данные» форма закрепляет пару `(context_revision,basis_id)` и показанный контекст. Polling обновляет индикатор наличия новых данных, но **не заменяет эту пару** и не смешивает новые сведения с закреплённым представлением.

При изменении контекста показать причину и сравнение старых/новых оснований. Новая отправка требует явного повторного просмотра. Старый текст можно сохранить как черновик, но его перенос требует подтверждения пользователя и нового idempotency key. На сервере остаётся обязательная проверка актуальности: кнопка UI не является гарантией.

### 1.4. Идемпотентность и ошибки

Ключ команды уникален в области `(authenticated_actor_id, command_type, target_id, idempotency_key)`. Сравнивать весь канонический JSON команды, включая expected-поля. Сохранить результат успешной команды в одной транзакции с её эффектами.

Порядок: аутентификация/права → поиск ранее успешного ключа → сравнение тела → проверка нового контекста и предметных условий → запись. Повтор успешной команды возвращает её первоначальный результат **до** проверки текущей ревизии и не создаёт новую запись. Недостаточные текущие права не обходятся повтором. Отклонённая до commit команда не резервирует успешный ключ.

| Ситуация | HTTP / публичный код |
| --- | --- |
| Новая успешная команда / точный повтор успешной | `201` / `200` |
| Прежний успешный ключ с другим телом | `409 idempotency_conflict` |
| Новая команда по старой ревизии | `409 stale_revision` |
| B существует, но относится к другой цели/циклу/ревизии | `409 basis_mismatch` |
| Недопустимый переход, например устранение неподтверждённого дефекта | `409 invalid_transition` |
| Выпуск запрещён текущими основаниями | `409 release_blocked`, список `blockers` |
| Неверная схема/обязательные поля | `422 validation_error` либо существующий специализированный код v0.2 |
| Нет аутентификации / прав / сущности | `401` / `403` / `404`, без раскрытия недоступных оснований |
| Сохранение/синхронная обработка невозможны | `503`, без успешной квитанции |

После timeout UI хранит **точное первоначальное тело и ключ**, обозначает исход как неизвестный и предлагает повторить ту же команду. Изменение результата polling не меняет тело повтора. До выяснения исхода нельзя автоматически отправлять изменённое действие как новую команду.

**Альтернативы:** версия только карточки пропускает изменение общего контекста; автоматическая подстановка latest скрывает устаревший просмотр. Выбран общий контекст + B. Цена — дополнительные конфликты при параллельной работе контролёров. Пересмотр выбора нужен, если это мешает измеренной работе; сужение ревизии требует доказательства полноты зависимостей.

## 2. Подтверждение дефекта и подтверждение устранения — разные решения

Сохраняем существующий `Nonconformity.status`: `pending_review | confirmed | rejected | needs_check`. Он отвечает на вопрос об обоснованности сообщения, а не о выполненном ремонте.

Добавляем отдельную проекцию `resolution_status`: `not_applicable | open | resolved`, журнал `ResolutionDecision` и команды `resolve | reopen`. Это уточнение решения человека, не новый публичный source event.

| Событие/команда | Последствие |
| --- | --- |
| `confirm` существования дефекта | Дефект confirmed; если нет применимого решения об устранении, resolution=open |
| `reject` | Сообщение признано необоснованным; resolution=not_applicable; исходник и прежние решения сохраняются |
| Disposition `rework` | Назначает доработку, но не создаёт выполненную операцию и не устраняет дефект |
| `resolve` | Дефект остаётся confirmed; resolution=resolved по отдельному основанию и повторному контролю |
| `reopen` | Новое решение возвращает resolution=open; прежнее устранение остаётся в истории |
| Новый релевантный сигнал после `resolve` | Сохраняет прежнее решение, создаёт review; применимость устранения требует пересмотра и выпуск блокируется |

Первое `resolve` требует: актуальные B/ревизию, ссылку на завершённый новый `operation_run_id` доработки с `previous_operation_run_id`, новый контроль дефекта/области в соответствующем цикле и отсутствие неразрешённых противоречий этому устранению. Событие «признаков нет» само по себе не закрывает дефект. Контролёр подтверждает устранение; причина возникновения может оставаться `unresolved`.

При повторном рассмотрении уже сохранённого устранения команда `resolve` может подтвердить его применимость к новым основаниям, используя ту же доказанную доработку и релевантный повторный контроль. Это новое решение, не UPDATE старого. Если новых оснований недостаточно, остаются review/open и запрос проверки. Повторный `confirm` существования дефекта сам по себе не снимает review устранения.

Для demonstrator повторное использование `reject` со смыслом «исправлено» запрещено. При исторически ошибочном confirm допустим новый мотивированный reject; это исправление оценки существования, которое отличается от resolve и сохраняется в аудите.

**KPI на одной когорте изделий:** `confirmed_defects` и `confirmed_nonconforming_items` v0.2 учитывают актуально подтверждённое существование, включая устранённые дефекты. Добавить `open_confirmed_defects`, `resolved_confirmed_defects`, `open_nonconforming_items` и отдельное число целей, требующих review. После resolve число подтверждённых дефектов не уменьшается; меняется открытость. Исторический отчёт на момент D1 читает прежние версии. Счётчик выполненных доработок растёт только по новым завершённым rework-операциям, не по disposition и не по resolve.

**Альтернативы:** переиспользовать reject — потерять смысл брака; одним статусом mixed confirmed/resolved — смешать существование и устранение. Выбраны две оси и отдельный журнал. Цена — ещё одна команда и проекция. При расширении на ремонт без операции или допустимое отклонение потребуется отдельное правило; в demonstrator таких обходов выпуска нет.

## 3. Полнота контроля и текущий цикл

### 3.1. Источник требований

Технолог владеет утверждённым маршрутом/контрольным планом; ERP/MES передают закреплённую версию. Неизвестный маршрут или область применимости не равны пустому перечню проверок. Типовой синтетический маршрут включает входную, после обработки и финальную точки; конкретные ID/области/методы задаются fixture задания.

`control_cycle_id` — серверный ID экземпляра цикла контроля изделия. Начальный цикл открывается по принятому заданию. После disposition rework мастер отдельной авторизованной идемпотентной командой открывает следующий цикл, указывая основание rework и запланированные run ID; права контролёра/мастера заданы сервером. Открытие цикла не означает фактического выполнения работ. Один активный цикл на изделие; повтор команды не открывает второй. Следующий цикл создаётся только по новой явно назначенной доработке, не по повторному нажатию той же команды. Выполненные операции первого цикла остаются в истории: обязательность повторения каждой операции и проверки определяет закреплённый план следующего цикла.

Привязка наблюдения к циклу хранится отдельно от raw: через однозначные зарегистрированные run/контрольную сессию. Для источника без такой связи приём допустим по v0.2, но закрытие обязательной точки остаётся unresolved до отдельного подтверждения. Запрещено автоматически приписывать поздний сигнал к «текущему циклу» по времени доставки. Если добавляется `control_cycle_id` в payload, это необязательное поле envelope 1.0 и проверяемое заявление источника, не право выбрать цикл без проверки.

### 3.2. Оценка каждой точки

В B/DTO полноты для каждой применимой точки хранить: ID требования и версию, цикл, область/компонент, run при необходимости, разрешённый метод, ссылки на основания, `assessment_status=missing | not_assessable | assessable | disputed`, эффективный результат и причины/ограничения. Оценимость и отсутствие дефекта — разные признаки.

- Нет наблюдения → missing; poor/unknown + no_defect_signs → not_assessable.
- Неизвестная идентичность, применимость метода, времени или требуемого материала не считается выполненной точкой.
- Противоречие сохраняется до отдельного обоснованного разбора; выбор последнего события не решает его.
- Оценимый defect_signs закрывает факт выполнения наблюдения, но блокирует выпуск через открытое несоответствие.
- Отклонённый контролёром ложный признак может быть рассмотренным результатом оценимой точки; reject не исправляет плохое качество/неизвестный метод автоматически.
- Замена неоценимого наблюдения новым допустимым контролем оформляется явной связью повторной проверки той же точки/цикла; старый вход остаётся в B с объяснением. Отсутствие новой съёмки нельзя заменить кнопкой «контроль выполнен».

При доработке все применимые проверки повторяются по умолчанию. Перенос отдельной проверки из прежнего цикла разрешён **только** закреплённым контрольным планом с перечнем сохраняемых точек и условиями (тот же компонент/область/метод, отсутствие влияющей операции и открытых противоречий). В B нового цикла сохраняется ссылка на прежнее основание и правило переноса. Синтетический fixture должен явно выбрать повтор либо перенос; не оставлять это на усмотрение UI.

### 3.3. Единое условие выпуска

Новая команда `released` допустима одновременно при:

1. известных задании, составе, маршруте и активном цикле; завершённых обязательных операциях;
2. всех применимых точках assessable, без неразрешённых противоречий;
3. отсутствии pending_review/needs_check и confirmed с resolution=open; resolved не блокирует сам по себе;
4. отсутствии review_required по текущим основаниям, решениям об устранении и открытых ограничений области;
5. актуальных expected_revision/B и правах контролёра.

Рассмотрение нового disposition может заменить **только прежнее решение по изделию**, для которого этот просмотр и выполняется. Оно не обходит неразобранные review дефектов/устранений/полноты. Поэтому пересмотр старого released возможен после разрешения всех его зависимых причин, а не блокируется навсегда своим собственным маркером review.

Хранить старый disposition и отдельно `release_allowed_now` + `blockers`. После позднего свидетельства старый released остаётся историческим фактом, но `release_allowed_now=false` и review отображаются явно и передаются наружу. Автоматического физического отзыва продукции нет.

Для unknown-области demonstrator контролёр открывает/разрешает отдельную причину ограничения с основанием; старый возможный и новый установленный охват пересчитываются вместе. Разрешение одного ограничения не снимает остальные. Новые изделия также проверяют открытое ограничение всего пилота.

**Альтернативы:** «есть хотя бы хороший сигнал» и «последний сигнал победил» пропускают точки/циклы. Выбран версионированный контрольный план. Цена — данные о маршруте, циклах и ручном разрешении. Правила переноса пересматриваются только технологом с новой версией применимости.

## 4. Результат для ERP — полный версионированный снимок

Один поток результата на `(producer_id, external_system, external_order_id, external_item_id)`; в demonstrator producer_id закреплён конфигурацией, маппинг — данными задания. `result_version` — положительное монотонное целое; не сбрасывается при доработке или рестарте. Новая версия/UUID `message_id` выделяются в транзакции ядра вместе с изменением публикуемого состояния. Повтор и ACK новую версию не создают. На обновление контекста разрешено публиковать новый полный снимок; экономия числа сообщений — последующая оптимизация.

Обязательное содержимое: указанный ключ потока, message_id, result_version, previous_message_id (null для первой), context_revision, control_cycle_id, disposition, release_allowed_now, blockers, review_required, подтверждённые карточки с resolution_status и актуальными decision/resolution ID, статус причины и ссылки на основания решений. Причины сохраняются по карточкам; общий статус не заменяет их. Нет автоматического established/operator при confirm/resolve.

Полный снимок самодостаточен для текущего состояния. previous_message_id служит истории, а не требованию сначала применить все предыдущие версии. Тело outbox после commit неизменно, повторяется с прежними байтами/ID; новые факты создают новое сообщение.

На получателе одной транзакцией: проверить контракт/владельца → проверить message_id и уникальность `(stream,result_version)` → сохранить inbox → применить снимок, если версия выше текущей → commit. Если версия ниже текущей, сохранить её в истории с отметкой superseded, не понижая актуальную. V2 может стать текущей до доставки V1; пробел истории фиксируется отдельно, без выдуманного предыдущего сообщения.

Тот же message_id с другим каноническим телом → `409 message_id_conflict`. Тот же stream/version с новым message_id → `409 result_version_conflict`, даже при похожем теле: отправитель должен повторить прежний ID. Точный повтор ищется до проверки уже изменившегося текущего состояния/справочника. Аутентификация/права выполняются всегда.

Для сверки получатель предоставляет чтение сохранённого сообщения по ID и текущей версии по ключу потока. После восстановления старого backup исходящие сообщения приостановлены до сверки: запрещено генерировать повторно потерянные номера версий или считать новый приём восстановлением прежних B/решений.

**Альтернативы:** дельта требует непрерывной цепочки; полный снимок проще при потерях/перестановке. Цена — больший размер сообщений и хранение истории. Пересмотр нужен при измеренном превышении бюджета сообщения, с отдельным протоколом пропусков/сверки.

## 5. ACK, повтор и граница транзакции

### 5.1. Квитанция ERP

Ответ после commit содержит `message_id`, `result_version`, ключ потока, `content_digest` (SHA-256 RFC 8785 от исходного JSON тела), `status=accepted | duplicate`, `application_status=applied | superseded`, серверное `received_at` и `current_version_at_accept`.

- `201 accepted / applied`: новый снимок стал текущим в транзакции получателя.
- `201 accepted / superseded`: более старая версия записана в историю, текущая не понижена.
- `200 duplicate`: точный повтор; остальные поля возвращаются из исходного результата приёма. `application_status` и `current_version_at_accept` описывают **тот commit**, а не обещают, что версия всё ещё текущая. Актуальность читается отдельным запросом сверки.
- Контрактный отказ: 4xx и стабильный код ошибки; это не подтверждение доставки. Частично принятого сообщения нет.

Ядро помечает delivery=acknowledged только после проверки ID, версии, потока, digest и допустимого application_status, затем устойчиво сохраняет ACK. Ответ HTTP 200/201 с чужой/неполной квитанцией — протокольная ошибка, не успех. Ошибка связи, timeout, 429/5xx → повтор прежнего пакета с backoff; 401/403 → восстановление полномочий; прочий контрактный 4xx → разбор. Ошибки остаются видимыми, данные не удаляются по числу попыток.

Если получатель применил сообщение, но ответ потерян, повтор получает duplicate. Если worker упал после получения ответа до сохранения ACK — тот же порядок. Сетевого вызова ERP внутри транзакции ядра нет. Эмулятор обязан сохранять inbox/актуальную версию/первоначальную квитанцию в SQLite между рестартами и явно закрывать соединения.

**Выбранная граница ACK применима к нашему эмулятору.** Реальная ERP с раздельными received/applied требует адаптера ожидания/сверки применения; её receipt нельзя переименовать в наш applied. Подтверждение физического удержания изделия — отдельное действие мастера/ОТК, не этот ACK.

### 5.2. Согласованность первого demonstrator

Для ограниченного эксперимента выбираем предложенный в [evidence-graph.md](evidence-graph.md) **единый транзакционный guard всех writers** пилота на PostgreSQL READ COMMITTED. Порядок: guard → ключ идемпотентности → предметные чтения/проверки → запись. Guard берётся отдельным SQL-запросом до предметных чтений; все writers контекста, включая импорт, решения, цикл, ограничения и replay, следуют ему. Старый per-item writer нельзя одновременно направлять в те же данные demonstrator.

При событии атомарны raw, проекции, revision, анализ/основания, причины review и необходимые outbox. При человеческой команде атомарны неизменяемое решение со ссылкой на просмотренный B, новая проекция/revision, запись успешного idempotency key и необходимые outbox. B, созданный заранее, остаётся неизменным; транзакция проверяет его применимость.

Команда со старой revision получает stale_revision, если поздний факт коммитился первым. Если первой коммитилась команда человека, она остаётся действительной записью истории, а поздний факт создаёт review. Ошибка/лимит обработки до commit откатывает команду; источник сохраняет прежний пакет для повтора. Accepted источнику означает commit ядра, **не** ACK ERP и **не** независимый backup.

Цена guard — сериализация независимых изделий. Это эталон корректности малого эксперимента; 20 commit/s и горизонтальный рост не обещаются. При измеренном дефиците пропускной способности следующий ADR сравнивает SERIALIZABLE/барьер топологии или фоновый replay; текущая семантика не меняется скрытой оптимизацией.

### Короткий сценарий показа

1. Получить задание и пройти две операции. Показать один дефект с причиной unknown; принять confirm и rework.
2. Открыть старое основание B1. Доставить позднее свидетельство; показать B2, отличия, неизменность B1 и отказ старой команды.
3. Рассмотреть новые сведения, выполнить новый цикл доработки/контроля, отдельно подтвердить устранение и выпуск. Показать: дефект был один и остался в истории, открытых дефектов ноль.
4. Доставить результаты в обратном порядке и потерять один ACK; актуальная версия ERP не понижается, повтор не дублирует действие.

## 8. Условия изменения принятых правил

Изменения DP-01 оформляются новой версией с причиной, затронутыми полями/командами и новыми ожиданиями тестов. Основания пересмотра: контрпример корректности, измеренный предел ресурсов, реально иной workflow предприятия или несовместимый внешний протокол. Удобство отдельного UI/backend не является основанием молча менять семантику. После реализации в отчёте указать commit каждой роли и результаты A01–A14; до этого статус механизмов остаётся «спроектировано».
