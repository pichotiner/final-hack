## 3. Главные замечания

Приоритет **P1** — исправить до уверенного заявления о завершённом MVP; **P2** — следующий инкремент/пилот. Успешный A04 не отменяет этих замечаний. Найденное расхождение карты контроля и blockers само по себе не доказывает выпуск физически дефектного изделия.

### R01 · P1 · Карта полноты и разрешение выпуска вычисляются по разным правилам

Код: `backend/app/domain/quality.py:1244–1312` (`_blockers`) и `:1472–1536` (`_control_assessments`).

**Воспроизведено на действующем доменном коде:**

1. Импортированный контекст и завершённые операции → хороший incoming → poor final → good final без связи замещения. Карта final: `assessable`; blockers: `not_assessable:final`; release_allowed=false.
2. Хороший incoming → хороший положительный final → отрицательный final → контролёр отклоняет ложный признак. Карта final: `disputed`; blockers пуст; release_allowed=true.

Причина: оценка карты берёт пригодное подмножество, а gate блокирует наличие непригодных незамещённых наблюдений; кроме того, только gate исключает отклонённый признак из противоречия.

**Последствие:** контролёр получает несовместимые объяснения одного B. Второй случай может быть допустимым выпуском после reject, но карта обязана объяснять, что противоречие рассмотрено, а не показывать неразрешённый `disputed`.

**Исправление:** единая чистая функция оценки контрольной точки: выбранные, исключённые и противоречащие основания, результат, причины и ссылки на человеческое разрешение. Из неё строить B, UI, blockers и ERP. Проверки: оба контрпримера, poor+reject, явно связанный повтор, другой цикл/метод/область.

### R02 · P1 · Восстановление после плохого контроля/неверной привязки не завершено через публичный API

Код: `quality.py:449–463`, `:1265–1266`, `:1272–1300`, `:1719–1746`; `backend/app/api/shared.py:37–150`; `backend/app/adapters/production.py:304–326,406–479`.

- Домен умеет `replaces_observation_id`, но `project_source_fact()` не передаёт его в `record_observation()`. Публичной команды замещения/разрешения такой проверки нет.
- **Воспроизведено:** source path получает poor, затем good с указанием `payload.replaces_observation_id`; сохранённая связь остаётся null, `not_assessable` сохраняется. Дополнительное поле не является реализованной командой: его приём как неизвестного поля не меняет это поведение.
- Наблюдение с неразрешённым циклом остаётся с `cycle_id=None`; `_blockers()` проверяет такие наблюдения за всю историю. Последующий хороший контроль не разрешает прежнюю привязку. Открытие следующего цикла само по себе также не удаляет этот blocker.
- Неидентифицированный сигнал открывает ограничение всего demonstrator, в том числе будущих изделий. Внутренний `resolve_scope()` существует и проверен тестами, но в общем `/api/v2` нет маршрута для этой команды.

**Последствие:** система умеет остановить выпуск, но часть штатных способов возобновления отсутствует. Для производства это столь же важная часть workflow, как запрет выпуска.

**Исправление:** согласовать минимальные авторизованные команды повторной проверки и разрешения привязки/scope с B/revision/idempotency, затем подключить UI. Каждая команда снимает ровно свою причину, сохраняет raw и остальные ограничения. Carry старых контролей — отдельная возможность; все точки можно повторять, если это явно закреплённое ограничение демонстратора.

### R03 · P1 · Чтение доставок ломается на нормальном состоянии `sending`

Код: `backend/app/application/outbox.py:60–68`; `backend/app/adapters/quality.py:697–706`; `backend/app/api/shared.py:105–109,172–175`; `contracts/openapi.yaml:622–630`.

Worker сохраняет `quality_deliveries.status="sending"` на время аренды. Read query отдаёт именно этот столбец. Схема `Delivery.status` разрешает только `pending | acknowledged | error`.

**Воспроизведено:** реальный валидатор `DeliveryPage` отвергает запись `sending` с `IntegrityViolation`; общий HTTP обработчик отображает эту ошибку в **503**. Таким образом, чтение списка во время отправки либо неистёкшей аренды упавшего worker не проходит собственный контракт. Ни повреждения исходников, ни настоящего отказа БД для этого не требуется.

**Исправление:** явно согласовать транспортное состояние `sending` или отображение lease в `pending` с отдельными полями; регенерировать потребителей. Проверить GET после claim, во время задержанного HTTP, после падения worker и после ACK. Это хороший дополнительный contract test фактического ответа.

### R04 · P1 · Timeline теряет хронологический порядок на API-границе

Код: `backend/app/api/shared.py:94–97`; `backend/app/api/server.py:72–84`; исходный правильный порядок — `backend/app/domain/traceability.py:206–208`.

Reducer упорядочивает по `occurred_at, source_id, event_id`. Endpoint вызывает `_page(..., "record_id")`, которая заново сортирует список по случайному UUID. UI отображает массив как получен (`frontend/src/App.tsx:183–184`).

**Воспроизведено:** событие в 10:00 с record_id=f оказывается после 11:00 с record_id=a. В новом браузерном отчёте список типов событий также не является производственной последовательностью.

**Исправление:** отдельный timeline-cursor по стабильному хронологическому ключу; определить консистентность страниц при поздних вставках, например закреплённой ревизией истории. Проверить несколько страниц и одинаковые timestamps. Показать `received_at` отдельно.

### R05 · P1 · Обязательная аналитика неполна, два счётчика имеют сомнительную семантику

Код: `quality.py:1073–1083,1314–1359`; `shared.py:98–104`; `contracts/openapi.yaml:615–621`.

`analytics` суммирует counts по изделиям. Нет требуемых §2.4 постановки разрезов дефектов по типам/линиям/участкам, длительностей по изделию/участку/оператору/смене и подтверждённых ошибок по сопоставимым работам. Операции и reported/calculated длительности уже существуют внутри истории — это хорошая база, но не готовый аналитический API/экран.

**Воспроизведено:**

- `inspected_items` падает с 1 до 0 при открытии цикла доработки. Сейчас это «есть пригодный контроль активного цикла», а не число уже проверенных изделий выбранной когорты. В `docs/contracts.md:166` и производственном пакете ожидается различение этих смыслов.
- Первое наблюдение с `cycle_id=None` даёт `repeat_controls=1`, потому что `None != initial_cycle_id`. Несколько элементов defects одного raw также считаются отдельными observations; для количества выполненных осмотров это не корректная единица учёта.

**Исправление:** закрепить определения когорты, периода и единиц счёта; разделить lifetime/period inspected и coverage текущего цикла. Повторные осмотры считать по осмотру/исходному событию с установленным циклом, не по элементу дефекта. Добавить один компактный API/экран обязательных разрезов и ссылки на основания числителя/знаменателя.

### R06 · P1/P2 · Read path блокирует writers, а хранение накапливает вложенные полные снимки

Код: `shared_views.py:129–145,147–219`; `adapters/quality.py:271–327,329–395`; `domain/quality.py:170–194,523–546`; `adapters/locks.py:13–14`.

1. GET изделия и B использует `PostgresQualityWorkflow._run()`: общий `production_guard`, SELECT FOR UPDATE, загрузка всего агрегата. При отсутствии B нужной цели чтение ещё и сохраняет новый B/версию состояния.
2. Список изделий сначала загружает все состояния, затем строит каждую карточку с B и проверкой raw; пагинация применяется **после** этого (`shared.py:76–91`). Даже `limit=1` не ограничивает обработку одним изделием.
3. В `quality_items.state` вложены все observations, bases, decisions и outbox. Каждый B копирует историю/анализ. Каждая `quality_state_versions.snapshot` снова содержит весь агрегат со всеми предыдущими B и outbox.
4. `_persist_children()` на каждую мутацию обходит все сохранённые B/решения/сообщения. ACK тоже изменяет агрегат и сохраняет полную версию.

**Архитектурное следствие:** ограничение существенно серьёзнее «у нас общий lock». Чтение истории одного большого изделия конкурирует с записью других изделий; рост данных повышает стоимость каждого GET и ACK. При N событиях, B на каждое событие и линейном размере B, сумма B имеет порядок O(N²), а сохранение всех полных состояний с такими B — O(N³) логического JSON. Это анализ структуры, не измерение физического объёма PostgreSQL/TOAST.

**Исправление по этапам:**

- Для ближайшего демонстратора: оставить принятый guard, измерить полный приём/GET/ACK и его ожидание, ограничить размер страниц на SQL-стороне.
- Затем отделить read-модель от командного пути, подготовку B — от обычного GET; возвращать согласованный snapshot/revision без writer-lock.
- Текущий агрегат хранить компактным: ссылки/текущее состояние. B, решения и outbox — самостоятельные append-only объекты; вставлять только новые дочерние записи. ACK/lease — отдельное техническое состояние доставки.
- После этого измерять необходимость per-item блокировок или иного согласованного протокола для межиздельных изменений.

Проверка: те же предметные результаты на 1/2/4 процессах, длинная история, несколько UI-pollers, медленная ERP, объём записываемых данных и ожидание locks. `docs/architecture/scaling.md` измеряет старый reducer/JSON истории, а не текущую стоимость вложенных quality-state/B/ACK.

### R07 · P1/P2 · Архитектурный рассказ об анализе и адресном пересмотре шире runtime

Код: `quality.py:1374–1425,1644–1663`; `shared_views.py:90–100,192–197`; отдельный эксперимент — `backend/scripts/impact_experiment.py`.

Сохранение контекста и человеческого установления причины есть. Но самостоятельного слоя автоматического сопоставления до/после, альтернативных гипотез и их поддерживающих/опровергающих оснований в текущем ядре не обнаружено. После изменения истории review получают все уже рассмотренные карточки изделия. Межиздельный impact работает в отдельном синтетическом эксперименте; runtime выбирает raw по точному item_id, не обходит фактическое дерево установок. `factual_composition` и `links` в B возвращаются null.

**Последствие:** обещание «адресно найдём все затронутые сборки» не подтверждается общим MVP. Сохранять `unknown` честно и правильно, но для требования разбора обстоятельств одной постоянной неизвестности и raw JSON недостаточно.

**Ближайшее улучшение:** небольшая детерминированная карточка разбора: сопоставимые проверки до/после, область/метод, операция, action/machine events, альтернативы, недостающие сведения. Каждое утверждение с record IDs; established остаётся человеческим решением. В UI сейчас команда confirm не предоставляет выбора основания причины (`App.tsx:121–123`), хотя сервер её поддерживает.

**Следующий пилот:** версия фактических установок/снятий и индекс зависимостей, тест сигнала компонента, затронувшего одну сборку и не затронувшего другую. Необходимость отдельной графовой БД из этого не следует.

### R08 · P1/P2 · Ротация ключа поддержана классом, но не серверной конфигурацией

Код: `backend/app/adapters/protection.py:42–56`; `backend/app/application/bootstrap.py:97–104`; `shared_views.py:57–61`.

`AesGcmProtector` принимает несколько версий ключей, и unit-тесты чтения старой записи проходят. Однако `build_runtime()` загружает **только один** ключ. После смены файла/версии сервер не имеет предыдущего ключа; чтение B и следующий приём по старому изделию требуют проверки старых raw и могут получить `key_unavailable`.

**Исправление:** keyring с отдельным active key и доступными предыдущими версиями либо порт провайдера ключей; воспроизводимый restart между v1/v2 с чтением старого B и новым приёмом. Старый ключ не удаляется, пока нужен истории/backup. Это важнее внедрения PQ ради дополнительных баллов.

Защита raw AES-GCM, роли и SQL append-only реально проверены. TLS в текущем deployment, независимое закрепление полноты архива и disaster restore не продемонстрированы. Открытые проекции/детали наблюдений не получают конфиденциальность от шифрования отдельного raw. Для распределённого пилота нужны защищённые каналы и определённый периметр хранения. AEAD не доказывает полноту журнала или физическую истинность сигнала.

### R09 · P1 · UI не позволяет восстановить credentials, сохранив неизвестную команду

Код: `frontend/src/App.tsx:35,89–98,157`; `frontend/src/review-state.ts:43–48`.

После timeout форма правильно хранит прежние bytes/key. После 401/403 на повторе остаётся `unknown`. Но основной token input отключён при `locked`; его обычный обработчик смены вдобавок очищает рассмотрение. Если credential действительно отозван и выдан новый, пользователь не может заменить его и повторить прежнюю команду в этой форме. Перезагрузка теряет сохранённую в памяти команду.

Это статическое замечание по коду; реальную ротацию credentials в браузере этим ревью не инжектировали. Пройденный сценарий 403 → success использует восстановление ответа/полномочий для прежнего credential и не проверяет новую аутентификацию пользователя.

**Исправление:** отдельная повторная аутентификация того же actor с сохранением pending-команды и её ключа; затем точный retry/сверка. При другой личности явно учитывать, что область idempotency key включает actor. Проверить lost response → новый credential того же actor → одна сохранённая команда.

### R10 · P2 · Зависимости модулей и документация требуют упорядочивания

- `domain/quality.py:1176–1229` знает внешний ERP stream и переключает wire-shape по `erp_result_profile`; `domain/control.py:82–86` ограничивает конкретные ERP-профили. При смене ERP формата сейчас затрагивается домен. Лучше канонический QualityResult + отдельный mapper на интеграционной границе, с фиксацией готового тела outbox в той же транзакции.
- `application/outbox.py` импортирует таблицы SQLAlchemy и locks адаптера; persistence изменяет private `_Item`, а read adapter вызывает private `_run`. Папки слоёв есть, но API границ неполон. Достаточно узких интерфейсов command store/read store/outbox; универсальный framework не нужен.
- README, ADR, contracts.md, plan.md и trust/scaling содержат разные исторические статусы. Например, текущий контракт 0.4.0 и интегрированный A04 сосуществуют с утверждениями «HTTP/решения ещё не реализованы». Читать это как единую инструкцию трудно.
- `compose.server.yaml` не включает frontend и ERP; стандартный worker URL использует host.docker.internal, а эмулятор слушает loopback. Рабочий native-loopback P6 не подтверждает переносимость этого соединения между host и контейнером на Linux. Нужен один проверенный профиль полного запуска для передачи.
- Для остальных 1С/Галактика/MES/КОМПАС есть полезные бумажные mapping-примеры в `enterprise-pilot.md:189–205`; в `data/v2` нет отдельного условного CAD-файла с позициями/количеством/связями и согласованного машинного набора примеров всех адаптеров. Predictive/MobileOps требуют компактного описания входов/выходов/отказов по §3.2, реализация не обязательна.

## 4. Что в архитектуре сделано хорошо

| Решение | Почему оно полезно именно здесь | Подтверждение |
| --- | --- | --- |
| Отдельные raw, observation, nonconformity, cause, resolution, disposition | Отрицание ложного признака не означает ремонт, ремонт не стирает факт дефекта, AI не подменяет ОТК | Код workflow и сквозной A04 |
| Неизменяемый B + optimistic concurrency | После late можно показать знания «тогда», а stale-команда не применится к новому контексту | API/PostgreSQL-тесты и Chromium |
| Одно атомарное ядро raw/history/quality/outbox | Нет окна между сохранением решения и постановкой результата к доставке | Integration tests, rollback и A04 |
| HTTP/outbox + durable inbox ERP | Потеря ACK не удваивает эффект, V1 не заменяет V2, чужой digest не принимается за ACK | Persistent SQLite ERP, worker, тесты версии/потери ответа |
| Привязка source_id к principal, отдельные роли | Источник не становится контролёром; автор команды назначается сервером | Авторизационные отрицательные проверки |
| OpenAPI + генерация Python/TS + runtime validation | Есть машинная граница команды и автоматические проверки изменения потребителей | Оба codegen, shape gate, CI и contract tests |
| PostgreSQL вместо отдельной graph DB/брокера | Атомарность и простая эксплуатация малого demonstrator; типизированные связи возможны в SQL | ADR со сравнением сильной QMS-альтернативы |
| Предметное обследование и камерный проект | Свет, область метода, калибровка, маркировка, ручной режим и владельцы описаны с допущениями | camera-ai-design, enterprise-pilot, source-of-truth |

## 6. Приоритет до финала и после него

### До защиты

1. **R01/R03/R04:** согласовать карту/gate, промежуточный статус доставки и порядок истории. Малые, локальные исправления с адресными регрессиями.
2. **R02:** продемонстрировать завершённый случай poor → новая проверка → разрешение своей блокировки и корректный выход из uncertain/scope. Сохранить прежние основания; не исправлять через SQL.
3. **R05/R07:** добавить минимальный разбор обстоятельств и обязательные аналитические разрезы. Прежде закрепить определения inspected/repeat/error и источник длительности.
4. **R09 и документация:** понятное восстановление доступа, подписи действий и выбор ссылок вместо ручного копирования UUID/JSON; один короткий README с действительным запуском и честным статусом функций.
5. Повторить изменённые сценарии и обновить финальную матрицу. Отдельно показать tamper denial/detection из существующего набора; не подменять его одним слайдом о шифровании.

### Следующий инженерный инкремент

1. R06: компактная persistence-модель, read side и SQL pagination; измерение приёма, GET, ACK, диска и locks.
2. R08: keyring, TLS-профиль и управляемый restart/backup-restore с ERP-сверкой.
3. R07: фактический состав и адресные зависимости; затем осознанное расширение параллелизма.
4. ERP mapper/порты вынести из доменных правил; полный deployment профиль, durable edge spool с проверкой обрыва/переполнения.

Выбор между тремя путями:

- **Укрепить текущий модульный SQL-контур — рекомендовано.** Максимально использует проверенное ядро, локализует реальные дефекты; цена — аккуратная миграция снимков и новые отрицательные проверки.
- Сразу ввести асинхронные проекции — оправдано только после измеренной нехватки скорости. Потребует lag/watermark, durable jobs и запрета решений по отстающей версии.
- Физически дробить на сервисы/добавлять graph DB и брокер — при независимых SLA/командах либо доказанном узком месте. Само по себе не исправляет completeness, семантику KPI, потерю pending-команды или рост snapshots.

## 7. Следующий конкретный результат каждой роли

**№1, ядро:** одна оценка контрольной точки для B/gate, корректные KPI и timeline, публичные recovery-команды по согласованному контракту; после этого — read/store разграничение и runtime-keyring. Для каждой правки дать отрицательный пример, API-результат и проверку неизменности старых B/решений.

**№2, производственный контур/контракт/UI:** формализовать sending/recovery/analytics DTO, регенерировать потребителей; подготовить независимые good+poor/reject-dispute/new credential fixtures; показать карточку разбора и обязательные разрезы без ручного JSON. Довести единый пакет запуска, примеры остальных систем и финальную презентацию.
