# Backend-инкремент: воспроизводимая история изделия

Рабочее решение роли №1, 25.09.2026. Основание — `contracts.md` v0.2 и новый документ `docs/architecture-hypothesis.md` из `origin/main` (`5e88e7a`). Цель инкремента: проверить свойство Evidence Ledger → Digital Thread → replay на PostgreSQL. Это часть архитектурного демонстратора; полный Evidence Graph, решения и UI этим инкрементом не объявляются реализованными.

Набор роли №2 подтверждает ожидаемый минимальный расчёт: две операции по 120 секунд. Внешние компоненты остаются отдельной веткой; совместимость всего пути пока не подтверждена.

## Контекст и границы доверия

```text
Источник/edge (будущий адаптер, не доверяем payload без проверки)
  → аутентификация и DTO (будущий HTTP)
  → внутренний IngestEvent
  → PostgreSQL: защищённые факты + отдельная проекция истории
  → внутреннее чтение истории → будущий API/UI

Ключи → EventProtector; ключи не хранятся в проекции или журнале.
```

Источник владеет заявленным фактом; ядро назначает время приёма и проверяет хранение. `work_order_id` и `component_ids` из поступления остаются ссылками источника: импорт задания/справочника не подменяется этими строками. Состояние поступления имеет причину `work_order_not_resolved` до подключения импорта. Для компонентов выдаются ID, без выдуманных типов и дерева вложенных сборок.

## ADR: способ построения истории

1. **Изменять текущие строки операций при каждом событии.** Дёшево, но отдельная сложная логика для перестановок, конфликтов границ и восстановления.
2. **Каждый раз читать весь журнал системы.** Простая семантика, но общая блокировка и стоимость, растущая со всеми изделиями.
3. **Перестраивать затронутое изделие из его проверенных событий под блокировкой изделия. Выбрано.** Детерминированный доменный reducer, одна транзакция, неизменяемые снимки версий и возможность независимого replay.

Компромисс: каждый пересчёт читает все n событий изделия, сортировка — O(n log n), проверка цепочек доработки в текущем простом алгоритме — до O(m²) для m операций. Состояния обновляются отдельными SQL-запросами по событиям; полные JSONB-снимки увеличивают объём хранения. Для демонстратора это проверяемая база, не обещание промышленной пропускной способности. Следующее развитие — инкрементальные проекции/контрольные точки с проверкой эквивалентности reducer, пакетные обновления, нормализованные индексы и измерение на реальной нагрузке.

## Компоненты и модель доказательств

- Домен: типизированные факты поступления и границ операции, reducer истории, длительности и причины неизвестности. Без SQL/HTTP.
- Адаптер: аутентификация сохранённых записей AEAD, загрузка фактов изделия, транзакционные блокировки и запись снимков.
- `raw_events`: неизменяемые зашифрованные исходники; первоначальная квитанция защищена вместе с ними.
- `event_projections`: текущее состояние обработки, отдельно от первоначальной квитанции.
- `item_projections`: текущая история и номер ревизии.
- `item_projection_versions`: append-only снимки прошлых ревизий с версией обработчика. Это версии истории, не версии анализа причин или решения контролёра.

Связи этого среза: изделие → ID компонента; изделие → операция; операция → границы с серверными ID фактов; история → `(source_id, event_id, record_id)` и оба времени. Связи `SUPPORTED_BY`, гипотезы и решения добавляются следующим срезом. Автоматической причинной атрибуции нет.

## Последовательности и отказы

```text
Новый факт:
IngestEvent → проверить конверт/источник → защитить кандидат
  → journal: блокировка ключа события, затем изделия
  → проверить исходники → reducer → защитить первоначальную квитанцию
  → INSERT raw + состояния + текущая история + версия → COMMIT → accepted

Одновременный повтор:
A → блокировка ключа → INSERT/COMMIT
B → ожидание того же ключа → исходная запись → AEAD/сравнение → duplicate/conflict
Проекция B повторно не выполняется.

Поздняя граница:
finish → incomplete, duration=null → версия 1
start (occurred_at раньше) → replay обоих фактов → completed → версия 2
Первоначальная квитанция finish и версия 1 остаются неизменными.

Ошибка/повреждение:
невалидный типовой факт / нарушение AEAD / ошибка INSERT версии
  → исключение → ROLLBACK всех записей текущей команды → нет accepted
Повтор после устранения ошибки → обычный новый приём.
```

Блокировки PostgreSQL транзакционные и общие между процессами. Режим изоляции — READ COMMITTED; после ожидания видны зафиксированные факты предшественника. Legacy-журнал без производственной обработки не следует параллельно использовать для тех же изделий; отдельный replay позволяет построить историю уже сохранённых фактов.

Ненадёжная идентификация не попадает автоматически в историю конкретного изделия. Неизвестная граница, сомнительные часы, конфликт параметров и несколько границ сохраняют неизвестность/проблему, а не выбирают удобный факт. Порядок при равных временах стабилен для отображения и не является доказательством причинности.

## Проверка и граница инкремента

Предметные проверки: порядок доставки, две операции, отдельные reported/calculated, пропуски, отрицательный интервал, несовместимые границы и неопределённость. PostgreSQL: конкурентные разные события и повторы, неизменная квитанция после replay, откат ошибки снимка, append-only версии, вмешательство в факт и соответствие миграции.

Снимки содержат открытые производные метаданные. Их чтение не означает повторную AEAD-проверку всего журнала; replay проверяет использованные исходники. Привилегированное удаление/перепривязка фактов требует внешних контрольных точек полноты, как и в первом инкременте.

Остаются: согласование DTO, публичное API/RBAC, импорт справочников, разрешение неопределённых связей, глобальная проверка ID операций между изделиями, карточки/решения/KPI, outbox/ACK, edge store-and-forward и полный комплект архитектурной приёмки из документа эксперта. Числа нагрузочной ёмкости пока не измерены.
