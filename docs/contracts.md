# Проект контракта данных и API (v0.1)

**Статус: согласовать командой перед кодом.** Поля событий основаны на постановке, точные имена типов, статусы, маршруты API и правила ниже — проектное предложение. Версия сообщения не равна версии анализатора или приложения. Не заводить несовместимые копии модели на backend и frontend.

## Событие

```json
{
  "event_id": "evt-001",
  "event_type": "inspection_observed",
  "schema_version": "1.0",
  "occurred_at": "2026-09-25T10:00:00Z",
  "source_id": "vision-emulator-1",
  "item_id": "part-001",
  "item_type_id": "bracket-demo",
  "line_id": "line-1",
  "station_id": "incoming",
  "operation_run_id": null,
  "operator_id": null,
  "equipment_id": null,
  "payload": {
    "inspection_result": "defect_signs",
    "observation_quality": "good",
    "confidence": 0.91,
    "defects": [{"type": "surface-mark", "description": "Условный признак", "component_id": "part-001"}],
    "evidence_refs": [],
    "analyzer_version": "emulator-1"
  }
}
```

Приёмник добавляет `received_at` и не переписывает `occurred_at`. Обязательные поля базового конверта: event_id, event_type, schema_version, occurred_at, source_id, item_id. Остальные обязательные поля определяются схемой конкретного типа; неизвестные значения не подменяются придуманными. При плохом сигнале `inspection_result=not_assessable`, а не `no_defect_signs`.

### Типы событий для стартового MVP

| Тип (проектный) | Смысл / основные поля |
| --- | --- |
| `item_received` | Экземпляр изделия/компонента, связи с заказом и сборкой |
| `operation_started`, `operation_finished` | `operation_run_id`, тип операции, участок, оператор, станок, время; у повторной операции `previous_operation_run_id` |
| `operator_action` | Тип действия, операция, участок |
| `machine_state` | Состояние или отклонение станка, операция |
| `inspection_observed` | `inspection_result`: `defect_signs` / `no_defect_signs` / `not_assessable`; список признаков, качество, уверенность, необязательные ссылки |
| `controller_decision` | Автор, момент, решение, причина, ссылки на наблюдения; новая запись, а не правка сигнала |

Отдельно хранить внешнее задание, исходящий результат и подтверждение интеграции. Один сигнал может включать несколько признаков дефекта; повторные наблюдения связываются с одной логической карточкой по документированным правилам. Способ сопоставления ещё предстоит утвердить: не склеивать автоматически все признаки одинакового типа на изделии.

## Сущности и статусы

- **RawEvent:** исходный конверт и payload, источник, occurred_at, received_at, хеш/проверка целостности; исходник не редактируется.
- **Item/Component:** экземпляр, тип, состав сборки, версия сборки.
- **OperationRun:** конкретное исполнение, время начала/конца, статус, ссылка на повтор.
- **Observation:** результат внешнего контроля; он сам по себе не является решением человека.
- **Nonconformity:** логическая карточка, наблюдения, основания, гипотезы и степень неопределённости.
- **ControllerDecision:** отдельная запись автора, времени, подтверждения/отклонения/дополнительной проверки и причины.
- **ItemDisposition:** производный итоговый статус; пересчитывается из фактов и решений, не затирает исходники.

Нужны явные состояния `unknown` / `not_assessable`. Причины различать как `hypothesis`, `established` или `unresolved`; входной брак, отклонение станка и подтверждённую ошибку оператора не объединять.

## Обработка доставки

1. Валидировать версию и поля. Несовместимую версию/некорректное событие отклонять с понятной ошибкой и журналом; необязательное новое поле допустимо при совместимом изменении.
2. Идемпотентность по паре `source_id + event_id` (проектное решение); тот же ID с иным содержимым — конфликт, а не молчаливое игнорирование.
3. Хранить исходный порядок поступления и логический порядок по `occurred_at`; позднее событие обновляет производные представления и аналитику.
4. Правило при конфликте времени источников и ненадёжной привязке фиксировать отдельно: не делать категоричных выводов при неполной последовательности.
5. Коррекции, решения и подтверждения добавлять новыми событиями. Метрики должны быть воспроизводимы из истории.
6. Для сравнения до/после учитывать контрольную точку, экземпляр операции и качество наблюдения. Дефект «после» создаёт гипотезу, не доказательство причины.

## Предлагаемый минимальный API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST | `/api/v1/events` | Приём события; статус accepted/duplicate/conflict/invalid |
| GET | `/api/v1/items/{item_id}/timeline` | История и связи изделия |
| GET | `/api/v1/nonconformities/{id}` | Сигналы, обстоятельства, гипотезы, решения |
| POST | `/api/v1/nonconformities/{id}/decisions` | Новое решение контролёра |
| GET | `/api/v1/lines/{id}/status` | Состояние линии |
| GET | `/api/v1/analytics` | Раздельные показатели и фильтры |
| POST/GET | `/api/v1/integration/emulator/...` | Двусторонний обмен с эмулятором |

Маршруты — стартовая договорённость, подлежат уточнению до реализации. Создайте формальную OpenAPI/JSON Schema спецификацию как источник истины и проверяйте её согласованность с реализацией.
