# Семантика контракта данных и API (v0.2)

**Статус: рабочая база P0 для реализации.** Версия v0.2 уточняет прежний эскиз v0.1. Это проектные решения, а не дословные требования организаторов и не заявление о готовых endpoints. Изменения общей семантики согласуют обе роли. Следующий артефакт роли №2 — формальная `contracts/openapi.yaml` и генерация по [technical-decisions.md](technical-decisions.md).

Версии различаются: версия этого документа `0.2`, версия конверта события `1.0`, путь API `/api/v1`, версия внешнего анализатора и версия приложения. Одна версия не заменяет другую.

## 1. Конверт события

```json
{
  "event_id": "evt-001",
  "event_type": "inspection_observed",
  "schema_version": "1.0",
  "occurred_at": "2026-09-25T10:00:00Z",
  "source_id": "vision-emulator-1",
  "item_id": "part-001",
  "item_type_id": "bracket-demo",
  "line_id": "line-1",
  "station_id": "incoming",
  "operation_run_id": null,
  "operator_id": null,
  "equipment_id": null,
  "identification_status": "reliable",
  "time_quality": "synchronized",
  "payload": {
    "inspection_result": "defect_signs",
    "checkpoint_id": "incoming-surface",
    "inspection_phase": "incoming",
    "observation_quality": "good",
    "confidence": 0.91,
    "defects": [
      {
        "defect_ref": "mark-001",
        "type": "surface-mark",
        "description": "Условный признак",
        "component_id": "part-001",
        "region_id": "face-A"
      }
    ],
    "evidence_refs": [],
    "analyzer_version": "emulator-1"
  }
}
```

Обязательны `event_id`, `event_type`, `schema_version`, `occurred_at`, `source_id`, `item_id`, `payload`. ID — непустые строки длиной до 128 символов; они не обязаны быть UUID. UUID серверных карточек/решений не подменяют внешние ID.

`occurred_at` — RFC 3339 с часовым поясом, внутри ядра UTC. `received_at` задаёт только сервер и хранит отдельно. Неизвестные необязательные связи передаются как `null` или отсутствуют. Неизвестный экземпляр может иметь `item_id=null` при `identification_status=uncertain`; событие сохраняется без автоматического включения в историю конкретного изделия.

`identification_status`: `reliable | uncertain`, по умолчанию `uncertain`. `time_quality`: `synchronized | uncertain`, по умолчанию `uncertain`. Отсутствие этих полей не трактуется как надёжность. `confidence` — число от 0 до 1 или `null`; отсутствие уверенности не равно нулю.

## 2. Типы событий источников

| Тип | Обязательное содержимое и связи |
| --- | --- |
| `item_received` | Известный `item_id`, `item_type_id`; `payload.work_order_id`, массив `component_ids` (может быть пустым для детали), `assembly_version` для сборки |
| `operation_started` | `operation_run_id`, `station_id`; в payload: `operation_type_id`, `shift_id`, необязательный `previous_operation_run_id` |
| `operation_finished` | `operation_run_id`, `station_id`; в payload: `operation_type_id`, `shift_id`, необязательный `reported_duration` |
| `operator_action` | `station_id`, `payload.action_type`; операция, оператор и оборудование при известности, `payload.details` |
| `machine_state` | `equipment_id`, `station_id`; `payload.state`: `normal`, `warning` или `stopped`; `payload.parameters`, `payload.description`; операция при известности |
| `inspection_observed` | `station_id`; `inspection_result`, `checkpoint_id`, `inspection_phase`, `observation_quality`, `defects`; версия анализатора и материалы при наличии |

Событие станка может иметь `item_id=null`: позднее связывание по оборудованию/интервалу создаёт обстоятельство, а не выдуманную точную идентификацию. Начало/конец операции без известного изделия сохраняются, но остаются `unresolved` до разрешения связи.

`inspection_result`: `defect_signs | no_defect_signs | not_assessable`.
`observation_quality`: `good | poor | unknown`.
`inspection_phase`: `incoming | before_operation | after_operation | final`.

Для `before_operation`/`after_operation` требуется `operation_run_id`. Для `defect_signs` список `defects` непустой; у каждого элемента обязателен `type`. Для `no_defect_signs` список пустой. При `not_assessable` допустимы предварительные признаки, но они не означают подтверждённое несоответствие.

Если источник прислал `no_defect_signs` при `poor/unknown`, исходник сохраняется без исправления, а **эффективный результат** становится `not_assessable` с причиной. Внешний анализатор рекомендуется настраивать на прямую передачу `not_assessable`. Признаки при плохом наблюдении требуют проверки, не отбрасываются молча.

`reported_duration`: `{ "value": 120, "unit": "s", "kind": "active_processing" }`; `value >= 0`, единица MVP — секунды, виды `active_processing | station_elapsed`. Переданное и вычисленное значения хранятся отдельно с `origin=reported | calculated`. Из начала/конца вычисляется только `station_elapsed`; отрицательное время, ненадёжные часы или отсутствие границы дают `null` и причину. Незавершённая операция не получает нулевую длительность. Активное время без достаточных данных не выводится из полного интервала.

## 3. Идентичность дефекта

- Идемпотентность доставки действует по `(source_id, event_id)` и не решает задачу связывания разных наблюдений одного дефекта.
- Каждый элемент `defects` получает собственный `observation_id`, связанный с исходным событием и индексом элемента.
- Если источник передал стабильный `defect_ref`, ключ кандидата — `(source_id, item_id, component_id, region_id, defect_ref)`. Источник обязан сохранять его при повторном наблюдении того же дефекта. Изменившаяся классификация сохраняется отдельным наблюдением того же кандидата.
- Пустые/неизвестные `component_id` и `region_id` не являются wildcard для связывания с известными значениями.
- При отсутствии `defect_ref` создаётся отдельный кандидат со статусом неопределённой связи. Совпадения одного `type` недостаточно для автоматического объединения.
- Для разных источников автоматического объединения нет. Контролёр может связать кандидатов отдельным решением с основанием; исходные наблюдения сохраняются, а проекция выбирает один логический дефект. Это отдельная задача после первого среза.
- Неподтверждённые кандидаты отображаются отдельным показателем; в число подтверждённых дефектов входят уникальные подтверждённые логические карточки, а изделия считаются через distinct `item_id`.

## 4. Сущности, решения и статусы

| Сущность | Смысл / состояния |
| --- | --- |
| `RawEvent` | Неизменяемый исходник, время возникновения/приёма, идентификатор источника и защищённый пакет |
| `EventProjection` | `applied`, `unresolved`; причины неполной привязки и версия обработки отдельно от исходника |
| `Item/Component` | Экземпляр и тип; версия и состав сборки, связи с внешним заданием |
| `OperationRun` | `in_progress`, `completed`, `incomplete`, `invalid`; повторная операция имеет новый ID и ссылку на предыдущую |
| `Observation` | Исходный результат, эффективный результат, качество и связь с логическим дефектом |
| `Nonconformity` | `pending_review`, `confirmed`, `rejected`, `needs_check`; исходные наблюдения, версия карточки, основания |
| `CauseAssessment` | `unresolved`, `hypothesis`, `established`; категория `incoming`, `equipment`, `operator`, `other`, `unknown`; evidence и ограничения |
| `ControllerDecision` | Неизменяемое решение `confirm`, `reject`, `request_check`; основание, автор и время сервера |
| `ItemDisposition` | Решение по изделию `pending`, `released`, `rework`, `rejected`; отдельно от наличия признаков и причины |

`controller_decision` исключён из публичного входа источников: запись создаётся **сервером** через авторизованный endpoint решений, затем попадает в аудит и историю. Служебный источник не может прислать произвольного автора и принять решение за человека.

Запрос решения содержит `decision`, непустой `reason`, `expected_revision` и `idempotency_key`. Автор берётся из аутентификации. При совпадении ключа, автора, цели и тела возвращается исходный результат; изменение тела с тем же ключом даёт конфликт. Проверка повтора выполняется до проверки ревизии, чтобы повтор успешно принятой команды не был ошибочно отклонён как устаревший.

Решение допускает уточнение причины: `cause_status`, `cause_category`, ссылки на конкретные основания и, для подтверждённой ошибки, соответствующие операцию/оператора/действие. `established` требует явного решения человека и оснований. Автоматический анализ создаёт лишь `hypothesis` или `unresolved`. Подтверждение существования дефекта не подтверждает автоматически его причину.

При новой команде с устаревшей `expected_revision` ответ `409 stale_revision`: контролёр перечитывает карточку. Ранее принятое решение меняется новым решением, не UPDATE исходной записи. Последнее решение и вся история доступны вместе.

Решение по изделию принимается отдельно через endpoint `dispositions` с теми же правилами автора, ревизии и идемпотентности. `released` допустим только после обязательных проверок из задания, при отсутствии открытых/подтверждённых несоответствий и неразрешённой неопределённости. Отсутствие сигналов само по себе не создаёт выпуск.

Поздние новые основания не меняют решение человека задним числом. Создаётся новая версия анализа и `review_required=true`; предыдущий выпуск остаётся в истории, а текущее состояние показывается как требующее пересмотра и передаётся во внешнюю систему новой версией результата.

## 5. Доставка, время и версии

1. Права источника проверяются до приёма; `source_id` обязан соответствовать служебной учётной записи.
2. Валидация различает неизвестную версию (`unsupported_schema_version`), неизвестный enum (`invalid_enum`), отсутствие обязательного поля и неправильный тип (`validation_error`). Ошибки не маскируются успехом.
3. База P1 принимает `schema_version=1.0`. Неизвестная версия явно отклоняется. Добавленные необязательные поля при известной версии сохраняются в исходнике и не влияют на бизнес-логику до поддержки; недостающие обязательные поля и неизвестные enum отклоняются. Несовместимое изменение требует новой major-версии и адаптера миграции.
4. Дубликат сравнивается по каноническому JSON исходного сообщения, без серверных полей. Использовать RFC 8785 и отклонять неоднозначный JSON с повторяющимися ключами/нечисловыми NaN/Infinity. Массивы сохраняют порядок; смысловую эквивалентность разных timestamp-строк не угадывать. Сохранять также исходный принятый payload.
5. Успешный приём фиксирует raw event, изменения проекции и outbox атомарно. При отсутствии связей квитанция содержит `projection_status=unresolved` и причины; такое событие не считается полностью обработанным в метриках полноты.
6. Логический порядок: `occurred_at`, затем `source_id`, `event_id` для детерминированного отображения. Порядок поступления доступен отдельно. При равном/ненадёжном времени причинный порядок не выводится из tie-breaker.
7. Сравнение до/после требует надёжной идентификации, сопоставимой области контроля, хорошего качества и согласованной операции. Большой сдвиг часов или неизвестная точность источника отмечаются как неопределённость. В MVP нет автоматической коррекции времени источника; временные пороги — конфигурация и проектные предположения.
8. Позднее событие сохраняется независимо от задержки, пересчитывает затронутую историю и показатели. Старые решения и версии анализа не удаляются. Событие завершения до начала по доставке может сначала создать `incomplete`, затем после прихода начала перейти в `completed`.

## 6. API ядра

Все маршруты ниже — контракт для будущей реализации. Списки возвращают `items` и `next_cursor`; `limit` по умолчанию 50, максимум 200. Фильтры KPI возвращаются вместе с результатом; сортировка списков стабильна.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST | `/api/v1/events` | Одно событие; `201 accepted`, `200 duplicate`, `409 conflict`, `422 invalid` |
| GET | `/api/v1/work-orders` | Полученные задания с внешними ID и состоянием импорта |
| GET | `/api/v1/work-orders/{id}` | Маршрут, версия и обязательные контрольные точки задания |
| GET | `/api/v1/items` | Изделия, фильтры по линии, участку, статусу |
| GET | `/api/v1/items/{item_id}` | Паспорт и состав изделия |
| GET | `/api/v1/items/{item_id}/timeline` | История, связи, решения; оба времени и статус проекции |
| GET | `/api/v1/nonconformities` | Очередь рассмотрения с фильтрами |
| GET | `/api/v1/nonconformities/{id}` | Наблюдения, гипотезы, решения, revision и review_required |
| POST | `/api/v1/nonconformities/{id}/decisions` | Авторизованное решение; `201` новое, `200` повтор |
| POST | `/api/v1/items/{item_id}/dispositions` | Отдельное решение о выпуске/доработке/отклонении |
| GET | `/api/v1/lines/{id}/status` | Состояние линии и активных операций |
| GET | `/api/v1/analytics` | Показатели, фильтры, время расчёта и версия проекции |
| GET | `/api/v1/integrations/deliveries` | Исходящие сообщения, попытки, ACK/ошибки; права по роли |
| GET | `/health/live`, `/health/ready` | Живость процесса и готовность зависимостей без раскрытия секретов |

Квитанция события: `event_id`, `source_id`, `status=accepted | duplicate`, исходный `received_at`, `projection_status`, список `issues`. У дубля возвращается квитанция исходного приёма, а не повторно выполненный расчёт.

Ошибка: `{ "error": { "code": "validation_error", "message": "...", "details": [] }, "request_id": "..." }`. Также используются HTTP `401/403`, `404` для отсутствующей сущности и `503` при невозможности надёжного сохранения. Подробности ошибки не содержат секретов и полного исходного payload.

## 7. Граница внешней системы

Внешний эмулятор является отдельным процессом. Его формат не совпадает автоматически с моделью ядра. HTTP-маршруты эмулятора:

- `GET /external/v1/work-orders?cursor=...` — задания и `next_cursor`.
- `POST /external/v1/quality-results` — приём результата и квитанция `accepted | duplicate | rejected` с `message_id`.

Внешнее задание содержит `message_id`, `external_order_id`, `revision`, тип/экземпляры изделий, маршрут и обязательные контрольные точки. Адаптер сохраняет соответствия `(external_system, entity_type, external_id) -> internal_id`. ERP владеет заданием, MES — фактом выполнения при реальном подключении, CAD — версией состава, ядро — наблюдениями, рассмотрениями и аудитом. Правила конфликта владельцев описываются в каждом адаптере.

Исходящий результат содержит стабильный `message_id`, внешние ID задания/изделия, версию результата, статус изделия, подтверждённые несоответствия, статус причины и `review_required`. Повтор той же версии использует тот же ID; пересмотр после новых данных создаёт новую версию и новый ID со ссылкой на предыдущий результат.

ACK принимается только для ожидаемого ID. Сетевые ошибки, timeout, HTTP 429/5xx повторяются с ограниченным backoff и тем же ID. HTTP 4xx по контракту переводит сообщение в состояние ошибки для разбора; ошибка не считается подтверждением доставки. Получатель обнаруживает тот же ID с другим телом как конфликт.

Условный импорт КОМПАС-3D содержит ID и версию сборки, компоненты, количества и связи; отсутствие геометрии обозначается явно. Переход к прямому CAD API описывается адаптером, не требует изменения производственных правил.

## 8. Правила показателей

- `inspected_items`: уникальные надёжно идентифицированные изделия с оценимым наблюдением `good` в выбранном интервале; невозможность оценки считается отдельно.
- `confirmed_nonconforming_items`: уникальные изделия с актуальными подтверждёнными несоответствиями; `confirmed_defects`: уникальные подтверждённые логические дефекты. Сравнивать эти величины только на одинаковой когорте изделий.
- Гипотезы причины, установленный входной брак, проблемы оборудования и подтверждённые ошибки операторов показываются раздельно. Решение по существованию дефекта не увеличивает автоматически счётчик ошибок.
- В аналитике длительностей указывать единицы, вид интервала, происхождение, число завершённых/незавершённых/некорректных измерений. Неизвестное не подменяется нулём.
- Сопоставимые работы группируются по типу изделия, типу операции и версии маршрута; при недостатке этих полей не строится рейтинг операторов.
- KPI пересчитываются после подтверждения, отклонения, связывания дефектов и позднего события. Проекция содержит `computed_at` и `revision`; возможная задержка обновления показывается явно.

## 9. Что осталось формализовать в OpenAPI

Полные DTO каждого события, чтения и ошибки; ограничения полей; security schemes; формат cursor; параметры фильтрации; отдельные схемы внешнего обмена и примеры. Это задача роли №2 с проверкой роли №1 до подключения клиента и сервера. Список выше не означает готовность генерации или завершение P0.
