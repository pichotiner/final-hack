## 4. Основные замечания с доказательствами

Приоритеты: **P0** — исправить до заявления о готовом сквозном demonstrator; **P1** — следующий обязательный инкремент; **P2** — усиление/дополнительные критерии. Владельцы указаны по зонам ответственности, а не как персональная оценка участников.

### F01 · P0 · Нет общей транзакции от raw до решения и результата

**Владелец: №1; поставка контракта и внешнего контура — №2.**

`PostgresTraceabilityJournal.append_if_absent()` сохраняет raw и историю (`backend/app/adapters/traceability.py:81–117`), но не вызывает quality workflow. `PostgresQualityWorkflow.record_observation()` работает отдельно (`backend/app/adapters/quality.py:305–308`). В traceability нет предметного разбора inspection/operator/machine payload (`backend/app/domain/traceability.py:56–117`).

Следствие: принятый исходный JSON сам по себе не создаёт карточку, B, review и outbox. Доказательство «исходное событие → именно это решение → именно этот KPI» разорвано. Общий guard из DP-01 §5.2 заменён разными per-item namespace `item` и `quality-item`; это не реализует принятый общий протокол.

**Закрытие:** один прикладной сценарий/транзакция по DP-01; фактический source event через сервер создаёт защищённый raw, проекции, контекст, review и необходимый outbox. Сбой между записями откатывает все эффекты. Проверить обе очередности late event/решение, общий контекст и ограничение на будущее изделие (A12–A13).

### F02 · P0 · Полнота контроля позволяет ложный выпуск

**Владелец: №1; №2 предоставляет независимые отрицательные сценарии.**

`_blockers()` проверяет список checkpoint ID, но не импортированное задание, состав, обязательные первоначальные операции, допустимый метод и идентичность источника (`backend/app/domain/quality.py:791–838`). `route_known=True` по умолчанию (`:161–183`) подменяет проверяемый контекст флагом.

**R1, воспроизведено:** `open_item` → хорошие наблюдения всех переданных checkpoints → `create_basis` → `dispose(released)` успешно. Ни задания, ни состава, ни завершённых производственных операций нет. Это допустимое упрощение изолированного reference-среза, но недостаточный gate выпуска demonstrator по DP-01 §3.3.

**R2, воспроизведено:** единственная точка `final` → `defect_signs, quality=poor` → решение `reject` → `released` успешно. Плохой контроль стал достаточным после отклонения признака. Причина: в `record_observation()` качество понижает оценимость только для `no_defect_signs` (`:247–254`), а blockers не проверяет качество остальных наблюдений. Это прямо расходится с DP-01 §3.2: reject не исправляет плохое качество.

**Закрытие:** полнота опирается на версию требований, метод/область/run/цикл и достоверную привязку. У каждого отказа свой blocker; `poor/unknown` не закрывает обязательный оценимый контроль после одного reject. Новое пригодное основание связывается явно.

### F03 · P0 · Повторный цикл можно вернуть к старому и использовать прежний контроль

**Владелец: №1.**

`start_cycle()` проверяет только отличие от текущего ID и наличие последнего disposition=rework (`backend/app/domain/quality.py:209–220`). Реестр ранее использованных циклов и связь «одно назначение доработки → один новый цикл» отсутствуют.

**R3, воспроизведено:** хороший контроль `cycle-1` → disposition rework → открыть `cycle-2` → снова открыть `cycle-1` новыми командами по актуальным B → released. Ни одной выполненной доработки нет. Старый контроль снова покрывает точки, а проверка rework-operation не применяется к initial cycle.

Дополнительно **R5:** наблюдение без cycle/run автоматически получает текущий цикл (`:289`), вопреки запрету DP-01 §3.1 привязывать поздний сигнал по времени доставки. `resolve` сравнивает серверные `created_at` (`:544–548`), а не доказанный порядок фактической операции и наблюдения: запоздавший приём не доказывает повторный контроль после ремонта.

**Закрытие:** неизменяемый реестр циклов, новое назначение для следующего цикла, серверная проверка связи run/контрольной сессии; непривязанный сигнал остаётся unresolved. Старый контроль и поздно доставленный сигнал о состоянии до доработки не закрывают новый цикл. Проверить A06 и возврат к старому ID.

### F04 · P0 · Ключ логического дефекта отличается от принятого контракта

**Владелец: №1; №2 проверяет согласованность DTO и сценариев.**

В коде ключ `(item_id, cycle_id, defect_ref)` (`backend/app/domain/quality.py:303–315`). В контракте — `(source_id, item_id, component_id, region_id, defect_ref)` (`docs/contracts.md:77–85`), и DP-01 A08 требует полный ключ. Observation не содержит source/component/region; отсутствие defect_ref вообще запрещено reference-срезом (`:247–250`), хотя v0.2 допускает отдельного uncertain-кандидата.

**R4, воспроизведено:** два наблюдения того же `mark` на одном изделии в разных циклах → два кандидата → после подтверждения обоих `confirmed_defects=2`. Физический дефект не обязан становиться новым из-за повторного контроля. В обратную сторону одинаковый ref разных источников/областей не может корректно различаться данной моделью.

**Закрытие:** один логический дефект и отдельные наблюдения/циклы; полный согласованный ключ, явный uncertain-кандидат без ref, отсутствие автоматического межисточникового слияния. Fixtures: несколько дефектов в одном событии, повторные наблюдения, одинаковые ref разных областей/источников, повторный контроль без удвоения.

### F05 · P0 · B пока не восстанавливает полный контекст решения «тогда»

**Владелец: №1; №2 показывает закреплённый контекст в UI.**

`Basis` содержит ID наблюдений/карточек, revision, цикл и blockers (`backend/app/domain/quality.py:73–83,328–343`). Нет версий задания, маршрута, состава, правил/обработчика, ссылок на использованные предыдущие решения, разделения противоречащих/исключённых входов. Observation содержит необязательный `source_event_id`, но не проверенную ссылку `record_id` на защищённый журнал.

Сохранённый объект неизменяем по структуре dataclass, но не реализует состав оснований DP-01 §1.2. Один список ID изменяемых карточек не фиксирует их состояние на момент решения.

**Закрытие:** точный манифест исходников/версий/решений и сохранённые результаты анализа; открыть B1 после B2 и восстановить именно показанные тогда основания. Не требовать повторного запуска CV для обычного replay.

### F06 · P0 · ERP reference-получатель и ACK расходятся с DP-01

**Владелец текущих ошибок reference-кода: №1. Владелец отдельного ERP-эмулятора и внешней схемы: №2.**

- **R6:** передать V2, V1, затем V1 с новым message_id. Последнее принимается вместо конфликта. Уникальность версии проверяется только при равенстве текущей версии (`backend/app/domain/quality.py:943–949`).
- **R7:** изменить payload сохранённого сообщения, оставив прежний digest и ID. Получатель возвращает duplicate: он доверяет переданному digest и не пересчитывает его (`:936–942`).
- **R8:** `_digest()` использует `json.dumps`, не RFC 8785 (`:36–38`); для `{"number":1.0}` хеш отличается от предписанного канонического JSON. На текущих простых сообщениях проблема может не проявляться, но контракт не обеспечен.
- Outbox не содержит полного внешнего ключа потока, внешних ID задания/изделия и статусов причин; `message_id` находится в обёртке, не в payload (`:758–789`). ACK не проверяет весь stream, получатель не возвращает предписанные digest/received_at/current_version_at_accept (`:643–666,950–965`).
- Получатель хранит состояние только в памяти; рестарт теряет inbox/версии/квитанции. Отдельного HTTP-процесса и настоящей входящей поставки задания нет.

**Закрытие:** единый внешний контракт, самостоятельный persistent-эмулятор, вычисление digest на стороне получателя, уникальность любой пары stream/version, полная проверка ACK, рестарт и потеря ответа (A09–A11). Не переносить ошибки reference-кода в новый эмулятор.

### F07 · P1 · Заявленная неизменяемость outbox нарушается через чтение in-memory состояния

**Владелец: №1.**

`_outbox_view()` возвращает поверхностную копию `__dict__`, а payload/ack остаются теми же вложенными объектами (`backend/app/domain/quality.py:923–925`).

**R9:** изменить `workflow.state(item)["outbox"][0]["payload"]["disposition"]`; повторный `state()` показывает изменённое тело, digest остался старым. Frozen dataclass не делает словарь внутри immutable. Это доказано для in-memory workflow; через `PostgresQualityWorkflow.state()` такое последующее изменение возвращённого объекта само по себе не сохраняется в БД.

**Закрытие:** снимки чтения отделены глубоким копированием/неизменяемым представлением, байты отправки фиксируются на commit; изменение полученного представления не меняет сохранённый результат.

### F08 · P0 · Не поставлены API, RBAC и единый запуск; владелец HTTP размыт

**Владелец HTTP/прав/общей композиции: №1 по DP-01. №2 — OpenAPI, generated-типы, UI и эмулятор.**

В текущих отслеживаемых файлах нет API приложения, frontend, транспортной спецификации, generated-компонентов и CI. `deploy/compose.dev.yaml:3–22` запускает только PostgreSQL. `actor_id` передаётся аргументом внутреннего метода; это не пользовательская аутентификация. `authenticated_source_id` сравнивается с входом, но сам не аутентифицирует клиента.

В `backend/README.md:142` и `docs/architecture/p0-quality-slice.md:43–46` HTTP/авторизация фактически переданы №2, тогда как DP-01 §6 поручает сервер/права №1. Из-за этого общий стык рискует остаться без исполнителя.

**Закрытие:** восстановить одного владельца серверной композиции; команда запуска БД+API+эмулятор+минимальный UI, роли источника/контролёра/мастера, серверный автор, запрет неразрешённых команд, сохранность данных после рестарта. Generated DTO не заменяет runtime-проверку прав и условных бизнес-правил.

### F09 · P1 · Разбор обстоятельств и обязательная аналитика реализованы не полностью

**Владелец предметных расчётов: №1; независимые ожидания и представление: №2.**

История операций и reported/calculated длительности реализованы. Но `QualityWorkflow` не содержит модели cause_status/cause_category и правил сопоставления до/после с действиями/оборудованием. `analytics()` суммирует ограниченный список счётчиков по item ID (`backend/app/domain/quality.py:696–706,840–881`). Нет обязательных разбивок по типам/линиям/участкам, установленным/неустановленным причинам, сменам/операторам и сопоставимым работам (постановка §2.4).

Необоснованных обвинений оператора код не создаёт, но отсутствие самой модели причин не выполняет требование обоснованного разбора. Отдельный impact-experiment не подключён к review живых решений. Область неизвестности и её действие на будущие изделия, принятые в DP-01 A13, отсутствуют в quality runtime.

**Закрытие:** трассируемый разбор одного дефекта с альтернативами и явным unknown; отдельное человеческое установление причины; KPI на одной когорте с происхождением и фильтрами. Подключить консервативные ограничения области; адресность расширять по мере доказательства полноты связей.

### F10 · P1 · Финальная доказательная поставка и документация расходятся с кодом

**Владелец актуального README/статусов: №1. Матрица, входы/expected и комплект защиты: №2.**

- Корневой `README.md:205` говорит, что решения и KPI не реализованы; P0/P1 уже существуют. Это устаревший статус, а не основание обнулить сделанную работу.
- `backend/README.md:39` приводит старые 100 тестов; P1-документ ожидает Docker-прогон, который в этом ревью успешно выполнен.
- `docs/plan.md` и `docs/ai-prompts.md` сохраняют задания «не кодировать / дождаться freeze» без столь же заметного актуального маршрута DP-01. Принятый демонстрационный протокол и исторический backlog трудно различить.
- A01–A14 — хорошая таблица ожиданий, но не полный исполняемый acceptance-набор. Существующие unit-тесты задают входы непосредственно в тестах; отдельные impact inputs/expected покрывают только impact-эксперимент.
- Нет общей поставки презентации/скринкаста, а в `docs/demo.md` часть формулировок описывает будущий обмен как фразу для защиты. Её допустимо произносить после реально работающего обмена.

**Закрытие:** один статус на конкретный commit, ссылка на реальную команду для каждой заявленной возможности, артефакты A01–A14 с независимыми ожиданиями, короткий README и записанный сквозной сценарий.

## 6. Распределение по двум ролям

### Роль №1 — доказательная модель, ядро и серверная композиция

**Сильная сторона:** обоснованный выбор SQL-журнала/проекций, сравнение с сильной QMS, строгий приём и AEAD, настоящие транзакционные тесты, измерение цены replay, сохранение решений отдельно от фактов.

**Основная проблема роли:** опубликованная семантика заметно сильнее последнего reference-кода. Недостаточно наличия классов Basis/Outbox/QualityWorkflow: их состав и инварианты должны соответствовать DP-01 и реальному исходному журналу.

Порядок работы:

1. **P0:** закрыть ложный выпуск и циклы (F02–F03), исправить идентичность дефекта (F04).
2. **P0:** соединить raw/traceability/quality/B/outbox в принятую атомарную границу, реализовать ограничение неизвестной области (F01/F05/F09).
3. **P0:** сервер по общей спецификации, аутентификация/права, автор из доверенного контекста, загрузка конфигурации и единый запуск (F08).
4. **P0/P1:** согласовать и исправить outbox/ACK, неизменяемость payload; не использовать reference receiver как доказательство внешней интеграции (F06–F07).
5. **P1:** причины, обязательные KPI, актуальные статусы; затем измерение общего commit-path и восстановление.

**Ближайшая поставка:** один серверный путь «валидный raw → точный B → решение → outbox», с отрицательными проверками выпуска/циклов и PostgreSQL rollback. Готовность принимает №2 по независимым fixtures и PDF.

### Роль №2 — производственный контур, контракт, внешняя система и доказательство для пользователя

**Сильная сторона:** реалистичный пилот, свет/идентификация/пределы камеры, конечный буфер, владельцы ERP/MES/CAD, MLOps закрытого контура, ручной режим и сильные производственные контрпримеры.

**Основная проблема роли в общей поставке:** эти решения не доведены до согласованного машинного контракта, воспроизводимых данных и отдельного работающего внешнего контура. Документы уже достаточно подробны; следующая ценная поставка — проверяемый вертикальный сценарий.

Порядок работы:

1. **P0:** передать OpenAPI v0.3.0 для `/api/v2` и `/external/v2`, generated Python/TS и негативные fixtures, включая полный ключ дефекта и цикл; №1 рецензирует семантику.
2. **P0:** отдельный ERP-эмулятор с устойчивыми заданием/inbox/state/ACK; V2→V1, конфликт старой версии, потеря ACK и рестарт.
3. **P0:** минимальный UI — линия/история/карточка/показатели; закрепление B/revision, видимые blockers, отдельные confirm/resolve/release и неизменное повторение команды после timeout.
4. **P0/P1:** общий набор нескольких изделий, двух участков/операторов, исходные события и отдельные expected; дополнить A01–A14 контрпримерами F02–F06.
5. **P1:** matrix «PDF → решение → реализация → команда → результат», финальные слайды и скринкаст. Компактно закрыть оставшиеся архитектурные компоненты и примеры интеграций.

**Ближайшая поставка:** контракт + входы/expected + отдельный persistent-эмулятор на одном маршруте. Это разблокирует подключение ядра и пользовательский показ; расширять UI сверх доказательного сценария не требуется.

### Общие проблемы, которым нужен один ведущий владелец

| Стык | Ведущий | Рецензент / вклад второй роли | Критерий закрытия |
| --- | --- | --- | --- |

## 7. Условие следующей общей приёмки

Один синтетический маршрут: ERP-задание → изделие/компоненты → две операции с двумя операторами → входной/промежуточный/финальный контроль → кандидат и обстоятельства → confirm/rework → поздний факт и B1/B2 → новый цикл/выполненная доработка/повторный контроль → resolve → отдельный release → версия ERP и ACK.

Параллельно показать нормальное изделие, неполный контроль и неизвестность. Повтор не меняет дефекты/ревизию, один физический дефект не раздваивается между циклами, плохой контроль не становится годным после reject, старый цикл не переиспользуется. Проверить потерю ответа, рестарт, обратный порядок внешних версий и вмешательство в защищённую запись. Все результаты имеют ссылку на вход/expected и сохранённые основания.

**Критерий остановки:** команда проходит этот путь на общем сервере и БД из чистого состояния, с минимальным UI и отдельным ERP-процессом, без ручного редактирования таблиц. Затем обновляет оценку критериев по фактическим доказательствам.
