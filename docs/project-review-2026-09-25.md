Дата начала проверки: 25 сентября 2026. Проверена рабочая ветка `feat/backend-event-journal@034063e` и сохранённая remote-tracking ветка `origin/codex/role-2-mvp@b169089`. Сеть GitHub для обновления веток не использовалась. Выводы относятся к этим версиям.

Исходные основания: PDF постановки, особенно §2–5, §6.2, §7.2, и PDF критериев, стр. 2–3. Текущие обязанности взяты из `AGENTS.md` и `docs/roles.md`: роль №1 / GPT Astra — доказательная модель; роль №2 — производственный контур и внедрение. Существующая реализация оценена дополнительно, включая прежнее разделение backend / frontend / контракты / эмулятор.

## 1. Итог

**Это сильный архитектурный проект с проверенным экспериментом хранения и истории, но пока не законченная система контроля качества.** Главная проблема — разрыв между хорошо описанными решениями и единым воспроизводимым результатом.

- Качество архитектурной проработки: ориентировочно **8/10**.
- Готовность интегрированного MVP: ориентировочно **4/10**.
- Конкурсный потенциал текущего набора материалов: **около 45–55/100 по условной шкале неповторяющихся критериев**, если предъявить обе проверенные ветки и честно показать границы. При предъявлении только текущей ветки теряются дополнительные основания по интерфейсу, адаптерам, генерации и CI.

Это экспертная оценка, не расчёт официального результата. В PDF сквозной процесс и сбор данных повторены в двух блоках. Правило их суммирования не установлено: здесь каждый такой пункт учтён один раз. Выступление и ответы команды не оценивались.

Постановка §7.1 действительно допускает архитектурное описание без полного MVP. Поэтому отсутствие большого приложения не делает архитектурную поставку несоответствующей формату. Но критерии приёма сигналов, интеграций, ИБ, генерации и автоматизации явно оценивают реализацию; наличие текста не заменяет её.

## 3. Приоритетные проблемы

P1 — закрыть до заявления о готовом сквозном результате или фиксации соответствующей семантики. P2 — ограничение, которое нужно исправить либо явно ограничить областью demonstrator.

### R01 — P1: OpenAPI, generated DTO и штатные события расходятся

**Владелец:** роль №2; роль №1 принимает семантику.

В `b169089:contracts/openapi.yaml:209–215` только item_id допускает null; прочие необязательные связи ссылаются на строковый Id. При этом `docs/contracts.md:48–50` разрешает null для неизвестных необязательных связей. Независимая проверка отклонила 17/32 событий собственного набора.

Есть обратное расхождение: OpenAPI требует station_id и operation_run_id через allOf (`:227–242`), но generated `OperationStartedEvent` наследует необязательные поля базы (`contracts/generated/models.py:114–127,392`). Удаление station_id проходит Pydantic. Smoke-test `contracts/test_generated.py:15–20` проверяет только Pydantic, поэтому зелёный CI скрывает несовместимость.

Кроме того, нет условных ограничений defects/inspection_phase/identification_status (`openapi.yaml:199–306`). Backend общего конверта тоже не является полной заменой: `backend/app/adapters/json_events.py:38–43`, `backend/app/domain/traceability.py:56–61` явно оставляют проверку большинства payload будущему адаптеру.

**Последствие:** один и тот же пакет принимается одним потребителем и отклоняется другим; некорректные данные могут пройти будущую транспортную границу.

**Приёмка исправления:** согласовать nullable и условные правила в спецификации; проверить все положительные и отрицательные случаи одновременно исходной схемой, regenerated DTO и реальным входом сервера. Сгенерированные файлы вручную не править. Если правило проверяется доменом, это должно быть явно отражено и проверено в общем входном сценарии.

### R02 — P1: проверка совместимости пропускает реальные breaking changes

**Владелец:** роль №2.

`b169089:frontend/scripts/check-contract.mjs:10–21` снимает только плоские свойства. Не учитывает items, вложенные anyOf и ряд других ограничений; `:23–27` для маршрута сохраняет только HTTP-коды, без схем request/response и параметров. Проверка allOf (`:62`) обнаруживает удалённые элементы, но не новое ограничивающее дополнение.

Воспроизведено: замена элементов массива string на integer и удаление null из anyOf дали `detected=[]`. Штатный self-test (`:72–78`) упражняет лишь добавление required и удаление enum.

**Последствие:** формально есть CI против рассинхронизации, но он не обеспечивает заявляемую границу совместимости.

**Приёмка:** зрелый OpenAPI-diff либо явно ограниченный рекурсивный checker с негативными проверками items, composition, nullable, request/response, параметров. Добавить проверку серверных ответов против схемы; совпадение двух generated-файлов само по себе не доказывает совместимость runtime.

### R03 — P1: ревизия решения в UI не закреплена за просмотренными основаниями

**Владелец:** роль №2, совместно с ролью №1 по протоколу B/revision.

Статически установлено: polling каждые 10 секунд включён в `b169089:frontend/src/main.tsx:7–9`. Форма сохраняет выбранное действие/текст, но при отправке берёт текущую `item.data.revision` / `card.revision`: `frontend/src/App.tsx:104–125,249–272`.

**Контрпример:** контролёр начал писать решение по revision=5; пришёл поздний факт; polling обновил карточку до 6; форма отправляет expected_revision=6 со старым рассуждением. Сервер не может отличить осознанное рассмотрение новой версии от фонового обновления. Отдельный вариант: ответ на успешно принятую команду потерян; polling меняет revision, а повтор с тем же idempotency_key уже содержит другое тело и может получить conflict вместо исходного результата.

**Приёмка:** закреплять базовую ревизию/основания при начале рассмотрения; новые данные требуют явного повторного просмотра. Сохранить полный неизменяемый command payload для повторной отправки после неопределённого сетевого исхода. Проверить оба случая через UI + сервер, включая уже выполненный commit и потерянный ответ. Browser-проверка этой проблемы в ревью не выполнялась.

### R04 — P1: не замкнут производственный цикл устранения подтверждённого дефекта

**Владельцы:** обе роли; №1 — состояния и KPI, №2 — маршрут повторного контроля.

В `docs/contracts.md:94–107` есть confirmed/rejected/needs_check и confirm/reject/request_check, а released запрещён при подтверждённом несоответствии. В `docs/architecture/evidence-model.md:197` правильно требуется новый цикл контроля, но не определены состояние устранения, решение о закрытии и влияние на исторический/текущий показатель брака.

**Контрпример:** дефект действительно подтверждён → назначена доработка → выполнен новый run → повторный контроль успешен. Как разрешить выпуск, сохранив истинность прежнего подтверждения? Использовать reject как «устранено» нельзя: это смешивает ложный исходный сигнал с исправленным реальным дефектом.

Это обнаруженный пробел модели, а не доказанный runtime-баг: соответствующего runtime ещё нет.

**Приёмка:** отдельная семантика устранения/закрытия и применимости к циклу, основание повторного контроля, новое решение о выпуске. Проверка «confirmed → rework → повторный контроль → закрытие → released», сохранение старых решений и раздельных исторических/актуальных KPI.

### R05 — P1: основной сквозной путь и отличительный сценарий не исполняются

**Владелец:** №1 — ядро/запуск; №2 — подключение клиента, эмулятора и проверочных данных.

`backend/app/domain/traceability.py:322–327` оставляет контроль, действия и станок в `event_domain_processing_not_implemented`; поступление имеет work_order_not_resolved. Таблицы в `backend/app/adapters/postgres.py` покрывают raw/state/history/versions, но не решения, несоответствия, основания B и outbox. Ветка роли №2 содержит отдельный эмулятор и интерфейс, но не добавляет отсутствующее предметное ядро.

**Последствие:** нельзя показать целиком «задание → дефект → решение → KPI → результат ERP → ACK», а также главное отличие «D1/B1 → поздний факт → B2/review → D2». Отдельный поиск влияния по составу проверяет другой, более узкий механизм.

**Приёмка после согласования архитектуры:** один интеграционный маршрут на реальной БД, отдельном эмуляторе, с постоянными решениями/основаниями и независимыми expected. Воспроизводимый запуск всей поставки; показать duplicate, late, stale revision и вмешательство. Большая CV-модель для этого не требуется.

### R06 — P1 для полного ТЗ: обязательная аналитика не доведена до контракта и интерфейса

**Владельцы:** №1 — расчёты; №2 — DTO, фильтры и отображение.

Постановка §2.4 требует распределения дефектов по типам/линиям/участкам, установленной и неизвестной причины, подтверждённых ошибок по сопоставимым работам. Сейчас расчётов нет. Дополнительно в `b169089:contracts/openapi.yaml:490–515` заданы только общие счётчики и durations; отдельных срезов по дефектам/причинам нет. Форма решения всегда отправляет cause_status=unresolved, cause_category=unknown и пустые основания (`frontend/src/App.tsx:263–265`).

**Последствие:** даже подключение нынешнего UI к будущему backend не даст полного обязательного аналитического сценария; установленную причину через эту форму не задать.

**Приёмка:** согласовать когорту, период, тип/маршрут сопоставимой работы, числитель/знаменатель, источник возникновения vs обнаружения. Дать путь от показателя к основаниям. Проверить confirm/reject/установленную причину/доработку/late и различие числа наблюдений, дефектов и изделий.

### R07 — P2: синхронный replay и полные версии ограничивают рост

**Владелец:** роль №1; №2 проверяет соответствие профилю пилота.

`backend/app/adapters/traceability.py:72–79,103–105` читает и расшифровывает все факты изделия на новом входе. `:119–175` создаёт полный снимок и делает запрос состояния каждого события. `backend/app/domain/traceability.py:295–311` повторно обходит цепочки предков. Полные версии дают квадратичный рост суммарного объёма по числу фактов.

Слабое место честно измерено в `docs/architecture/scaling.md:73–83`: 161 версия занимает 10 792 103 байта JSON при последнем снимке 132 981 байт. Это не размер БД и не RPS. Предложенный общий guard (`evidence-graph.md:148–156`) дополнительно сериализует независимые изделия.

Буфер роли №2 рассчитывается при 20 commit/s (`edge-deployment.md:296,324–328`), но такая скорость реального пути не проверена. Ошибка старого исходника или недоступный ключ также блокирует новый приём по изделию; очередь может расти и при исправной сети.

**Приёмка:** небольшой замер полного commit-path с длинной историей/поздними фактами и продолжающимся потоком. Затем выбирать пакетные запросы, сокращение копирования/общие фрагменты или отдельное решение асинхронного replay. Kafka сама это не исправляет.

### R08 — P2: защита записи реализована, защита всей системы — частично

**Владелец:** роль №1; №2 — edge/каналы/эксплуатация.

AES-GCM и SQL-запреты работают, проверены тестами. Но get_history читает открытый snapshot без проверки оснований (`backend/app/adapters/traceability.py:186–198`); отбор raw по изменяемым индексным метаданным предшествует AEAD (`:72–79`). При привилегированном удалении/перепривязке факта replay старого изделия может вообще не проверить эту строку. Это корректно признано в `docs/architecture/trust-model.md:72–74`.

Нет пользовательского RBAC, сетевой аутентификации, TLS-контура, штатной загрузки/восстановления ключей и работающего аудита решений. Параметр authenticated_source_id — внутренняя доверенная граница, не аутентификация клиента; отсутствие HTTP сейчас не является обнаруженной открытой сетевой уязвимостью.

**Приёмка:** для минимального MVP реализовать серверные права, отдельные источники/контролёра, защищённый запуск и воспроизводимое вмешательство. Для заявлений о защите от DBA — независимый контроль полноты. Не выдавать AES и ротацию ключа за реализованный постквантовый/гибридный профиль.

### R09 — P2: SQLite-соединения эмулятора не закрываются явно

**Владелец:** роль №2.

`b169089:emulator/server.py:59,99,122` использует `with open_db(...) as db`. Контекст sqlite3 управляет commit/rollback, но не закрывает connection. Воспроизведено на Windows: штатный HTTP-тест прошёл свои проверки, затем упал с WinError 32 при удалении state.sqlite (`emulator/test_emulator.py:26`).

**Приёмка:** явное закрытие через finally/closing, повтор теста на Windows и Linux, проверка перезапуска с сохранённым состоянием. Это дефект воспроизводимости и управления ресурсами, не доказанная потеря данных.

### R10 — P2: протокол ERP версии/применения пока существует лишь в проекте

**Владельцы:** №2 — получатель/адаптер; №1 — outbox и версия результата.

Пилот правильно различает receipt/application/локализацию (`enterprise-pilot.md:205–217`). Эмулятор `b169089:emulator/server.py:99–108` дедуплицирует только по message_id; не проверяет конфликт пары изделие/версия и не ведёт актуальный результат изделия. Поэтому V2→V1 и два разных message_id с одной противоречащей версией нельзя считать проверенными даже при успешных ACK-тестах.

**Приёмка:** выбрать самодостаточный snapshot либо дельту, реализовать ожидаемое применение версий в эмуляторе, проверить обратный порядок, lost ACK и restore. Сохранение сообщения и физическое удержание изделия остаются разными результатами.

### R11 — P2: документация и поставка разошлись по актуальности

**Владельцы:** №1 — редактор общего состояния; №2 — материалы демонстрации.

README описывает объединение архитектурных документов; backend/UI/contracts/CI остаются в разных ветках. Нет общей команды запуска приложения. `docs/status.md:105` всё ещё говорит об отсутствии проекта камер, хотя актуальный enterprise-pilot уже его содержит. `docs/contracts.md:3` отправляет роль №2 к прежнему заданию OpenAPI, а текущие роли требуют сначала архитектурного review. Чек-лист freeze в plan не показывает, какие материалы уже написаны, а какие не приняты.

В `b169089` есть HTML-презентация и план скринкаста; в текущей ветке их нет. Записанный скринкаст работоспособности в исследованных деревьях не найден. Требование §7.2 этим не закрыто.

**Приёмка:** один delivery baseline с матрицей «требование → решение → commit → команда → результат», короткой точкой входа, согласованными ADR и открытыми рисками. Архитектурный freeze отделить от промышленного допуска: реальное обследование не является условием участия, допущения допустимы и должны быть явно зафиксированы.

## 5. Оценка по ролям и следующий результат

### Роль №1 — разработчик с GPT Astra / архитектор доказательной модели

**Сильное:** реальное проверенное ядро; настоящие PostgreSQL-проверки транзакций и конкуренции; разделение домена/портов/адаптеров; строгий JSON и сохранение исходных байтов; AES-GCM с аутентификацией метаданных; сильные альтернативы SQL/QMS; честная оценка replay и отсутствия промышленной готовности.

**Слабое:** главная ценность EFQA — неизменные основания человеческого решения и их пересмотр — пока не реализована; исследовательские эксперименты обгоняют замыкание пользовательского сценария. Не закрыты CP и ответное review роли №2. Пробел устранения дефекта затрагивает саму модель. Полный replay/снимки плохо переносят длинный жизненный цикл.

**Оценка:** архитектурная поставка примерно 8/10; реализация своего ограниченного ядра качественная; полнота backend относительно ТЗ низкая. Это оценка артефактов, не личной компетентности участника.

**Следующая поставка:**

1. Ответить по R2-02–10 и CP-01–08: принять, отклонить либо ограничить demonstrator; зафиксировать единый протокол ревизии/B, release/rework, ACK и неизвестности.
2. После согласования построить одну вертикаль: задание → наблюдение → карточка → D1/B1 → поздний факт → B2/review → D2 → outbox/ACK; включить минимальные обязательные KPI и серверные права.
3. Проверить гонку решения с поздним фактом, неизменность B1, duplicate/conflict, запрет выпуска при пропуске и выпуск после подтверждённого устранения.
4. Предъявить общую команду запуска и один отчёт приёмки. Оптимизировать commit-path по измерению, если он препятствует сценарию.

### Роль №2 — производственный контур / интерфейс, контракты, эмулятор

**Сильное:** ближайшее документационное поручение практически выполнено: конкретный маршрут, физические ограничения, владельцы, конечный буфер, ручные действия, восстановление и метрики. Рецензия ядра содержательна. В отдельной ветке действительно есть UI, детерминированные сценарии, отдельные expected, SQLite-эмулятор, адаптеры и кодогенерация.

**Слабое:** проверка generated DTO принята за проверку самого контракта; несовместимость известна, но остаётся. CI не ловит существенные изменения. UI не закрепляет рассмотренную ревизию, всегда оставляет причину unknown и не показывает весь обязательный аналитический состав. Edge остаётся проектом; ACK-эмулятор уже описанной семантике версий не соответствует.

**Оценка:** архитектура производственного пилота примерно 8/10; готовность реализационных артефактов к подключению — около 5/10.

**Следующая поставка:**

1. Исправить R01/R02 и передать согласованную спецификацию с положительными/отрицательными проверками схемы, DTO и backend.
2. Исправить фиксацию контекста решения и повторы команд; добавить минимальное отображение B1/B2, причины review, полноты и установленной причины без большого UI.
3. Довести эмулятор: явное закрытие SQLite, версии результата и ACK; подключить его к реальному outbox роли №1.
4. Собрать проверку expected против ответов работающей системы и затем записать скринкаст. Для edge выбрать один маленький эксперимент durable ACK + потерянный ответ + restart; физические параметры пока оставлять проектными.

## 6. Общий приоритет

Наибольший прирост качества сейчас даст **согласованный минимальный контракт и одна воспроизводимая цепочка от события до решения и внешнего результата**. Архитектурных материалов уже достаточно для предметного совместного решения; следующий десяток похожих документов принесёт меньше пользы, чем закрытие найденных противоречий.

До большой реализации требуется короткий совместный review существующих предложений, как предписывает AGENTS. Завершать его нужно выбранными правилами и ограниченной областью эксперимента, а не ожиданием всех ответов будущего предприятия. Для конкурсного demonstrator реальные камеры, собственная нейросеть, Kafka и промышленный пилот не обязательны.

В рабочем проекте в ходе ревью добавлен только этот отчёт. Исходники, контракты и чужие ветки не изменялись; исследовательские пробы выполнялись во временной копии. Коммиты и push не выполнялись.
