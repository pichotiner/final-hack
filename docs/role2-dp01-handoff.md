# Поставка роли №2: контракт v2, ERP-получатель и закреплённое рассмотрение

Дата: 26 сентября 2026. База — `main@83edbdf` + документационный PR #5. **Статус: транспорт предложен для review, компоненты роли №2 реализованы и проверены отдельно. Сквозной M0 через backend/PostgreSQL не выполнен.** Это реализация выбранного эксперимента DP-01, а не возвращение к старому заданию большого frontend.

## 2. Что утверждено и что остаётся предложением

DP-01 задаёт B/revision, отдельные существование/устранение/выпуск, полноту цикла, полный snapshot и семантику ACK. Их не переизбираем. Поля DTO чтения и новые вспомогательные идентификаторы — формализация роли №2 на review №1, не доказательство, что reference backend уже отдаёт их.

**R2-F03:** `ResolveCommand.control_record_ids` — временное транспортное предложение: ссылки на принятые записи **контроля целиком**, включая `defects=[]`, а не на элементы дефектов. Оно явно помечено в схеме и UI. До ответа №1 нельзя объявлять этот DTO замороженным или заменить смысл одной стороной. В reference-срезе Observation существует для каждого контроля; ядро должно определить маппинг raw record → InspectionObservation и проверки типа/изделия/области/цикла/метода. Клиент не выбирает «последний хороший» результат автоматически.

**R2-F01/02:** semantics конфликтов состава/scope и граница central restore остаются у роли №1. Эмуляторный restart/lost ACK проверен, central restore — нет. Команды изменения состава, разрешения scope, переноса контроля и разбора disputed-точки не изобретаются как новые source event. Входные сценарии A06/A13/M0-END указывают эти операции как задачи ядру, а их транспорт требует отдельного согласования. Прочие схемы и внешнюю границу можно проверять независимо.

Старые v1 материалы находятся в `codex/role-2-mvp@4ff69a8`; они не скопированы поверх main и не объявляются совместимыми. Новые DTO нужно генерировать из новых источников, а не вручную редактировать старые generated. Чужая ветка сохранена. Основной маршрут остаётся кронштейном со вставкой, без незаметной добавки сварки.

## 3. Стык с текущим backend роли №1

| Reference backend на 83edbdf | Транспорт DP-01 / требуемое действие №1 |
| --- | --- |
| `cycle_id` | `control_cycle_id`; явный маппинг, сервер выделяет цикл. UI отправляет rework-disposition и планируемые run, не произвольный новый ID цикла |
| `create_basis` хранит observation IDs, blockers и revision | DTO Basis дополнительно требует raw record/source/event IDs, роли входов, pinned_versions, completeness и previous decisions. Заполнить реальными данными; не создавать фиктивный манифест |
| `record_observation` имеет одну запись/один дефект и сокращённый candidate key | Envelope допускает несколько признаков, неизвестный ref и разные источники. Адаптер должен сохранить отдельные уровни InspectionObservation/DefectObservation и полный ключ v0.2; ID источника не выводить из текста |
| `source_event_id` без source/record отображения | Внешние ссылки B должны однозначно разрешаться по record ID или составному source/event ID |
| `Decision` имеет actor и reviewed/new revision | DTO чтения добавляет control_cycle_id; автор из серверной аутентификации. Входные команды не принимают actor ID |
| Reference resolve принимает `observation_ids`, `rework_operation_id` | Транспорт использует `control_record_ids` (provisional R2-F03) и `rework_operation_run_id`; проверка существующего завершённого run и соответствия области обязательна |
| `_emit` содержит internal item_id и сокращённые карточки | Нужны внешние ID из постоянного маппинга, полный ключ потока, актуальные decision/resolution/basis и причина по каждой confirmed-карточке |
| `_digest(payload)` использует обычный JSON и не включает внешний message/stream | Внешний digest — SHA-256 RFC 8785 **всего QualityResult JSON**. Сериализованное тело и digest надо сохранить в outbox при выделении версии; не переименовать internal digest в transport digest |
| `acknowledge` проверяет часть полей; InMemoryErpReceiver — reference | Проверять также stream, body digest и исходную квитанцию; worker использует внешний SQLite-эмулятор. Нельзя выдавать reference dict за durable ERP применение |
| PostgreSQL quality boundary имеет per-item lock | DP-01 требует общий протокол всех writers; межиздельные зависимости/импорт/scope не покрываются нынешним per-item lock |
| `route_known` и список checkpoints | Полная оценка метода/состава/операций/неизвестности/циклов должна приходить от ядра. UI лишь отображает серверные blockers |
| HTTP API пока отсутствует | №1 подключает transport/security/import/outbox. Эти components не означают сквозной запуск |

Это список конкретных адаптаций, не новая параллельная доменная модель. Нельзя сделать mock HTTP, который заранее возвращает expected-результаты, и назвать его реализацией архитектуры.

## 4. Входы и оракулы

`data/v2/source-events.json`: 23 фиксированных source события. `base_order` — поступление, вход, две завершённые операции по 120 s, предупреждение станка, действие, четыре уникальных события контроля. `late_order` — входной сигнал с occurred_at 10:02:30, доставляемый после решения. `rework_order` отправлять **только после авторизованного открытия нового цикла**; ID cycle-2 в fixture должен соответствовать серверному маппингу, а не подменять server-owned цикл. Если сервер выделяет иной ID, сохранить явное соответствие при подготовке входа с новым event ID; не менять ранее принятый raw.

Контекст задания включает три различных экземпляра, два участка/оператора и явные компоненты; фактическую установку и подтверждение полноты требуется оформить отдельно авторизованным владельцем, а не выводить из компонента в карточке. Для полного приёмочного набора normal/poor-изделия дополняются фактическими операциями/составом при подключении core runner. Текущие дополнительные сигналы проверяют валидность/неоценимость, не полный производственный путь этих экземпляров.

`acceptance.json` содержит A01–A14 и M0-END. Операции, требующие server-generated ID/B/revision, обозначены символическими шагами: runner должен явно получить и закрепить их. Для retry сохраняются **те же байты и ключ**, не последний контекст polling. Для следующего решения нужен новый B и ключ. Основной путь после late требует отдельного рассмотрения всех противоречий, доработки, resolve и disposition; confirm не устраняет disputed автоматически.

`erp-results.json` — **отдельные синтетические полные snapshots внешней границы**, не фактические результаты backend. A09 сначала выполняется на изолированной базе, а после полного маршрута все новые версии доставляются и сверяется финальное состояние. «V2 стала текущей» не заменяет проверку финального released после последующих версий.

## 5. Запуск компонентов и проверки

Из корня, Python 3.11 или 3.12 (локальный прогон — 3.12.3), Node **24.12.0**, npm 11.6.2:

```bash
python -m venv .venv-role2
.venv-role2/bin/python -m pip install -r contracts/requirements.lock.txt
.venv-role2/bin/python -m contracts.generate --check
.venv-role2/bin/python -m contracts.compatibility contracts/openapi.yaml contracts/compat-baseline.json
.venv-role2/bin/python -m contracts.compatibility contracts/external-openapi.yaml contracts/external-compat-baseline.json
.venv-role2/bin/python -m pytest contracts emulator -q
.venv-role2/bin/python -m emulator.generate
.venv-role2/bin/python -m emulator.replay base_order --duplicate --dry-run
```

На Windows путь интерпретатора — `.venv-role2\Scripts\python.exe`; активация не обязательна. `.venv-role2` не коммитить. CLI команды написаны для установки в обычную venv; локальная harness-среда использовала окружение вне репозитория `/tmp/opencode/role2-dp01-venv`.

```bash
cd frontend
npm ci
npm run check:generated
npm test
npm run build
npm run dev
```

UI через Vite проксирует `/api` на локальный порт 8000, реальный HTTP API подключает №1. Токен UI хранится только в памяти вкладки, не в git/localStorage; при неизвестном исходе команды смена цели/токена заблокирована и повторяет сохранённое тело/ключ. Перезагрузка предупреждается; восстановление незавершённой команды после принудительного закрытия вкладки не реализовано и требует серверной сверки, не автоматической новой команды.

Перед запуском эмулятора задать **внешний локальный секрет** `ERP_EMULATOR_TOKEN`, без значения по умолчанию и без добавления в git:

```bash
.venv-role2/bin/python -m emulator.server --port 8090 --state /path/to/local/state-v2.sqlite
```

HTTP только loopback. Флаг `--allow-faults` включает тестовые before-commit/lost-ack воздействия после авторизации; они выключены по умолчанию. SQLite с synchronous FULL проверен для рестарта процесса на исправном носителе, не для уничтожения диска/промышленного RPO. Аутентификация эмулятора — одна служебная учётная запись, не RBAC предприятия. Ключ потока/config заранее закрепляет producer=efqa-demo и system=erp-demo; реальный ID-маппинг задаётся интеграцией, не названием продукта.

## 6. Границы доказательства и приёмка №1

**Фактический локальный результат этой поставки:** `python -m pytest contracts emulator -q` — **27 passed**; `npm test` — **8 passed**, TypeScript/Vite build прошёл. Обе OpenAPI проверены валидатором; повторная генерация Python и TS совпала с сохранёнными файлами; оба shape baseline совпали. Прогон генератора сохранил входной файл побайтно и не изменил SHA-256 отдельного acceptance.json. `ruff check` и `pip check` прошли. `emulator.replay base_order --duplicate --dry-run` показал фиксированный порядок и повтор последнего ID. Это 35 компонентных проверок, не 35 интеграционных сценариев core и не выполнение всех A01–A14. Node 24.12.0/npm 11.6.2 установлены вне репозитория для этого прогона.

- Проверки Python покрывают OpenAPI/DTO, source validation, негативные структуры/межполевые условия, persistent receiver и HTTP-потерю ответа/рестарт. Ожидания core A01–A14 не объявляются выполненными через PostgreSQL.
- Generated DTO не выражает все межполевые правила и правила, зависящие от состояния: проверка phase/run, reliable/null, дефекты/result, assembly_version и RFC3339 timezone явно выполняется boundary validator. Клиентские ограничения не заменяют серверные проверки прав/B/revision/выпуска.
- Совместимость — консервативный recursive shape gate: учитывает arrays/items, nullable/anyOf, request/response, enum и required. Он обнаруживает дрейф и требует review, но не доказывает семантическую совместимость всех JSON Schema. Переход /v1→/v2 — намеренно breaking; не скрытая миграция.
- Генерация Python/TS проверяется сравнением с временно сгенерированным файлом, не только отсутствием git diff: stale/untracked generated тоже обнаруживаются.
- Core HTTP, целостность БД на новом сквозном пути, общий guard, внешняя 1С, CV и запись скринкаста не выполнены этой поставкой.
