## 2. Целевой README

README должен за 3 минуты отвечать на вопросы:

1. Какую проблему расследования качества решаем и для какого участка?
2. Что происходит с одним изделием от наблюдения до решения?
3. Какие три особенности дают пользу и как их проверить?
4. Где проходят логические и физические границы? Одна читаемая блок-схема.
5. Почему этого достаточно: сравнение с QMS + аудит, цена выбранной модели.
6. Как внедрить в существующее предприятие и кто принимает результат?
7. Что спроектировано, что существует в ветках, что действительно проверено?
8. Куда идти каждой роли и где первоисточники?

Подробности ADR и протоколов вынести по ссылкам; количество технологий и объём кода не использовать как аргумент.

## 4. Приоритеты критериев

| Глубина | Что включить | Что предъявить |
| --- | --- | --- |
| Глубоко | История изделия, основание решения, неопределённость, дубль/позднее событие, интеграционные границы | Схема + трассируемый пример + ожидаемые результаты; позднее минимальный эксперимент |
| Достаточно для архитектурной защиты | Камеры/edge, малые данные, внедрение, безопасность и восстановление | Deployment, отказовый разбор, роли, ограничения и метод проверки |
| Обзорно на текущем этапе | Второй и последующие адаптеры, брокер, OpenTelemetry, горизонтальный рост, расширенная криптография, генерация | Порт подключения, причина появления, цена и запланированная проверка |

«Обзорно» — глубина текущей проработки, а не изменение PDF или обещание баллов. Если критерий требует работающий обмен, генерацию или проверку целостности, одна схема его не закрывает. В итоговой матрице обязательно отдельные колонки: требуется / спроектировано / реализовано / проверено / отложено.

## 5. Протокол следующей сессии ИИ

Работать над одним решением: вопрос → 2–3 жизнеспособных варианта → таблица компромиссов → предварительный выбор → контрпример → изменение схемы → открытый вопрос второй роли. Не производить пачку почти одинаковых документов. Источник прикладывать к конкретному тезису, а не только в список литературы.

У каждого задания есть конечный артефакт и критерий остановки. Готовность этапа измеряется тем, способен ли технолог восстановить основания решения и понять действия при отказе, а не числом диаграмм.
