# Две роли команды — архитектурный этап

Дата: 25 сентября 2026 года.

Этот документ заменяет прежний фокус «backend vs frontend». После консультации с экспертом две роли разделяются по **архитектурным зонам ответственности**, а не по количеству кода.

До архитектурного freeze обе роли работают прежде всего с постановкой, критериями, альтернативами, диаграммами, ADR, сценариями отказов и доказательствами. Небольшой код допустим только как эксперимент для проверки конкретной архитектурной гипотезы.

Главный документ: [architecture-hypothesis.md](architecture-hypothesis.md).

---

## Общее правило для обеих ролей

На каждое существенное решение ответить шестью пунктами:

1. Какую проблему производства решаем?
2. Какие есть минимум 2–3 альтернативы?
3. Почему выбрали именно этот вариант?
4. Каковы его минусы и цена?
5. Как он ломается?
6. Как это свойство можно проверить на демонстрации?

Нельзя принимать решение в стиле:
- «микросервисы потому что масштабируемо»;
- «Kafka потому что много данных»;
- «PostgreSQL потому что удобно»;
- «нейросеть потому что интеллектуальный контроль».

Любое такое утверждение нужно раскрыть через конкретную проблему кейса.

# Роль №1 — архитектор доказательной модели и ядра

## Цель роли

Спроектировать **логическое ядро EFQA**, которое умеет хранить проверяемые факты, строить историю изделия, связывать основания, переживать непорядок событий и отделять машинную гипотезу от решения человека.

Это не задача «написать FastAPI».

## Главный вопрос роли

> Как сделать так, чтобы спустя день, месяц или после позднего события можно было доказать, почему система показала именно такой статус, какие сведения были известны на тот момент и что изменилось позже?

## Задача 1. Сравнить архитектурные альтернативы

Подготовить ADR: `docs/adr/001-core-architecture.md`.

Обязательно сравнить минимум:

### A. CRUD + relational state
Обычная БД с текущим состоянием.

### B. Event Sourcing
Append-only журнал + projections.

### C. Event Sourcing + Evidence Graph
Журнал фактов + отдельная семантическая модель связей.

### D. При желании — полноценный event-driven microservices вариант
Например брокер + отдельные сервисы.

Сравнить по критериям:

| Критерий | Что проверить |
| --- | --- |
| Доказуемость | Можно ли восстановить основания решения |
| Поздние события | Что происходит при событии из прошлого |
| Повторы | Как обеспечивается идемпотентность |
| Неопределённость | Можно ли не делать категоричный вывод |
| Аудит | Сохраняется ли старое решение |
| Закрытый контур | Сколько инфраструктуры нужно |
| Масштабирование | Что является общей точкой состояния |
| Развитие | Можно ли добавить Kafka/новый анализатор |
| Сложность | Что реально поддержит команда/предприятие |

В конце — **не рекламный**, а честный вывод с недостатками выбранного варианта.

### Done
Есть таблица, ADR и устный ответ на вопрос «почему не CRUD / не чистые микросервисы?».

---

## Задача 2. Спроектировать Evidence Ledger

Нужно определить:

- что является исходным фактом;
- что запрещено менять;
- что можно вычислить заново;
- что является исправлением, а что новой версией;
- что происходит с повторным событием;
- что происходит с одинаковым ID и другим телом;
- как связываются `occurred_at` и `received_at`;
- как фиксируется `source_id`;
- как фиксируется `schema_version`;
- как фиксируется `analyzer_version`;
- как обнаруживается вмешательство.

Результат:
- диаграмма жизненного цикла события;
- список архитектурных invariants.

Пример invariant:

> Если исходный сигнал был принят, последующее решение контролёра не может изменить его payload; решение создаёт новую сущность.

### Done
Можно взять любой KPI/статус и показать путь назад до raw evidence.

---

## Задача 3. Спроектировать Evidence Graph

Не выбирать графовую БД заранее.

Сначала определить **семантику**.

Минимальные узлы:

- Item;
- Component;
- WorkOrder;
- OperationRun;
- InspectionObservation;
- DefectCandidate;
- EquipmentState;
- OperatorAction;
- AnalyzerVersion;
- ControllerDecision;
- ItemDisposition.

Минимальные связи:

- PART_OF;
- OBSERVED_ON;
- BEFORE / AFTER;
- DURING_OPERATION;
- PRODUCED_BY_ANALYZER;
- SUPPORTED_BY;
- CONTRADICTED_BY;
- REVIEWED_BY;
- SUPERSEDES.

Ответить:

- какие связи являются фактами;
- какие являются вычисленными;
- какие выражают только гипотезу;
- что происходит при конфликтующих наблюдениях;
- как связать несколько наблюдений одного дефекта;
- как не превратить несколько наблюдений в несколько дефектов.

### Done
Есть схема graph meta-model и 2 примера:
1. дефект после операции;
2. позднее наблюдение, которое меняет гипотезу.

---

## Задача 4. Спроектировать replay

Нарисовать sequence diagram:

### Сценарий
Контролёр уже подтвердил дефект после сборки.

Позже приходит наблюдение с `occurred_at` до сборки.

Нужно показать:

- куда записывается новое событие;
- что пересчитывается;
- что **не изменяется**;
- как меняются гипотезы;
- почему старое решение не удаляется;
- откуда появляется `review_required`;
- что отправляется во внешнюю систему после пересмотра.

### Done
Команда способна за 60 секунд объяснить разницу между:
- immutable fact;
- projection;
- hypothesis;
- human decision.

---

## Задача 5. Модель консистентности и масштабирования

Не писать «можно поднять несколько экземпляров».

Определить:

- какой порядок событий реально нужен;
- глобальный порядок нужен или только per item/per source;
- где находится authoritative state;
- как обрабатываются два события одного изделия одновременно;
- как избежать double count;
- что блокируется;
- что можно обрабатывать параллельно;
- где узкое место;
- что меняется при добавлении Kafka;
- что меняется при нескольких workers;
- что происходит после падения worker.

Подготовить:

- `docs/architecture/scaling.md`;
- диаграмму одного и нескольких обработчиков;
- один failure scenario.

### Done
Можно объяснить масштабирование без фразы «просто добавляем контейнеры».

---

## Задача 6. Security / trust architecture

Определить зоны доверия:

- edge;
- центральное ядро;
- пользователь;
- источник VisionQC;
- станок;
- ERP/MES/CAD.

Ответить:

- кому разрешено создавать raw observation;
- кто может принимать decision;
- почему источник не может притвориться контролёром;
- где лежат ключи;
- что шифруется;
- что подписывается/проверяется;
- как обнаруживается tampering;
- что происходит при неизвестном ключе;
- как сохраняется старая история после ротации.

### Done
Есть threat/trust diagram и отдельное объяснение:
**encryption ≠ integrity ≠ immutability**.

---

## Задача 7. Подготовить архитектурную защиту роли №1

Подготовить ответы:

- Почему Evidence Graph вообще нужен?
- Почему обычный timeline недостаточен?
- Почему graph не означает, что нужна Neo4j?
- Чем correlation отличается от cause?
- Почему решение контролёра нельзя хранить прямо в observation?
- Зачем replay?
- Как система ведёт себя при плохих часах источника?
- Что является source of truth?
- Как позже подключить Kafka?
- Где архитектура реально масштабируется, а где упирается в БД?

Сделать:
- 30 секунд;
- 2 минуты;
- 5 минут.

# Роль №2 — архитектор производственного, AI и интеграционного контура

## Цель роли

Спроектировать, **как EFQA физически живёт на предприятии**: от камеры и станка до edge-агента, ядра и ERP.

Это не задача «сделать красивый frontend».

## Главный вопрос роли

> Какие реальные источники производят свидетельства, где проходит граница интеллектуального анализа и как подключать их в закрытом производстве без зависимости ядра от конкретной камеры, модели, ERP или CAD?

---

## Задача 1. Выбрать маленький AI-сценарий

Нельзя начинать с «сделаем универсальную нейросеть контроля деталей».

Нужно выбрать **очень маленький демонстратор**, например:

- один тип поверхности;
- один объект;
- 1–2 визуальных класса;
- либо anomaly / no-anomaly;
- хорошее / плохое качество наблюдения.

Главная цель — не accuracy leaderboard.

Нужно определить контракт результата:

```text
item/component
control_point
inspection_result
defect_type
region
confidence
observation_quality
occurred_at
analyzer_version
evidence_ref
```

Обязательно определить:

- что AI знает;
- чего AI **не знает**;
- какой вывод AI не имеет права делать;
- когда ответ должен быть `cannot_assess`;
- что меняется при версии v2.

### Done
VisionQC можно заменить эмулятором с тем же контрактом, и целевая архитектура не меняется.

---

## Задача 2. Спроектировать физический контур «камера → edge → ядро»

Нарисовать deployment diagram.

Нужно ответить:

- где камера;
- какая контрольная точка;
- кто идентифицирует изделие;
- откуда известно, какая сейчас операция;
- где запускается CV;
- где создаётся event_id;
- кто хранит очередь при обрыве;
- сколько времени edge способен жить без центра;
- что будет при восстановлении;
- как избежать дублей;
- что делать при плохом свете;
- что делать при ненадёжной идентификации изделия;
- как синхронизируется время.

Числа, которых нет у заказчика, маркировать как **проектные предположения**.

### Done
Есть схема online и offline/store-and-forward режима.

---

## Задача 3. Ограниченные данные и жизненный цикл AI

Спроектировать процесс:

```text
локальные данные
→ отбор
→ подтверждение специалистом
→ разметка
→ настройка/обучение
→ validation
→ версия
→ допуск
→ monitoring
→ rollback
```

Ответить:

- как стартовать при маленьком датасете;
- где человек обязателен;
- как хранится версия модели;
- как сравнить v1/v2;
- кто допускает новую версию;
- как откатить;
- что происходит со старыми событиями после смены модели;
- нужно ли переанализировать старые материалы и как не подменить исходную историю.

### Done
Есть схема MLOps именно для **закрытого производства**, а не облачный generic pipeline.

---

## Задача 4. Source-of-truth matrix

Сделать таблицу:

| Сущность | Авторитетный источник | Что хранит EFQA | Конфликт |
| --- | --- | --- | --- |
| Work order | ERP | snapshot + mapping | ... |
| Факт операции | MES | event/reference | ... |
| Состав изделия | CAD/PLM | version + structure | ... |
| Observation | VisionQC / source | immutable evidence | ... |
| Review | EFQA | human decision | ... |
| Equipment state | machine/SCADA source | evidence | ... |

Для 1С, Галактика:ERP, MES и КОМПАС-3D описать:

- направление обмена;
- внешний ID;
- внутренний ID;
- version/revision;
- повтор;
- ошибка;
- кто считается владельцем факта.

### Done
Можно заменить формат внешней системы без изменения предметных правил EFQA.

---

## Задача 5. Anti-corruption adapters

Для каждого внешнего класса системы описать:

```text
external model
        ↓
adapter
        ↓
canonical EFQA event/model
```

Не нужно писать все интеграции.

Нужно доказать границу.

Подготовить один реальный эмуляторный пример:

```text
ERP work order
→ adapter
→ internal work order

internal quality result
→ adapter
→ external result
→ ACK
```

И один бумажный пример для другой системы.

### Done
Понятно, какой код меняется, если завтра Галактику меняют на другую ERP.

---

## Задача 6. Архитектура деградации

Нарисовать сценарии:

1. центральное ядро недоступно;
2. ERP недоступна;
3. AI не может оценить изображение;
4. камера недоступна;
5. часы источника ушли;
6. пришёл неизвестный analyzer_version;
7. edge прислал накопившиеся события не по порядку.

Для каждого:

- что теряется;
- что продолжает работать;
- что буферизуется;
- какой статус видит оператор;
- что требует ручного вмешательства;
- как система восстанавливается.

### Done
Есть degradation matrix. Ни один сбой не маскируется как «всё хорошо».

## Задача 7. Проверка уникальности архитектуры

Найти 3 типичных подхода к подобным системам:

- классическая machine vision station;
- MES/QMS dashboard;
- event-driven industrial platform.

Не копировать их.

Для каждого сформулировать:

- что он умеет;
- чего не хватает для нашего кейса;
- какой элемент EFQA закрывает этот разрыв.

Результат — таблица **«существующий подход → gap → наше архитектурное решение»**.

### Done
На вопрос «а что здесь уникального?» есть конкретный ответ без слов «у нас AI».

---

## Задача 8. Доказательный MVP и демо

MVP проектируется **после** архитектуры.

Он должен минимально показать:

- входное задание;
- изделие + две операции;
- observation от маленького VisionQC/эмулятора;
- Evidence Graph/основания;
- решение контролёра;
- повтор события;
- позднее событие;
- ACK внешней системы;
- желательно store-and-forward edge.

UI — средство демонстрации этих свойств.

Нельзя тратить время на:
- сложный дизайн;
- 20 dashboard-страниц;
- универсальный редактор;
- собственный огромный CV dataset.

# Совместные контрольные точки

## Gate A — понимание

Оба участника одинаково отвечают:

- что является fact;
- что является hypothesis;
- что является decision;
- что является disposition;
- зачем нужен Evidence Graph;
- почему AI — источник, а не судья.

Если ответы расходятся — код не начинается.

## Gate B — архитектурные альтернативы

Есть:
- минимум 3 альтернативы;
- ADR;
- trade-offs;
- failure modes.

## Gate C — архитектурный freeze

Есть:
- system context;
- component diagram;
- deployment diagram;
- Evidence Graph;
- replay sequence;
- offline sequence;
- source-of-truth matrix;
- trust model;
- AI contract.

После этого разрешается минимальный demonstrator.

## Gate D — MVP как доказательство

Каждая реализованная функция должна иметь ссылку на архитектурное свойство, которое она подтверждает.

Формат:

| Демонстрация | Какое свойство доказывает |
| --- | --- |
| Duplicate event | Idempotent evidence ingestion |
| Late event | Replayable projections |
| v2 analyzer | Replaceable AI |
| Offline edge | Closed-production resilience |
| Controller decision | Human/AI separation |

# Как использовать ИИ в обеих ролях

ИИ не должен получать задачу «сделай весь проект».

Правильная работа с ИИ:

1. Дать одну архитектурную проблему.
2. Попросить минимум 3 альтернативы.
3. Попросить ИИ **раскритиковать собственный фаворит**.
4. Проверить альтернативы по требованиям PDF.
5. Сформировать ADR.
6. Нарисовать sequence/deployment/data-flow.
7. Только потом при необходимости сделать мини-прототип свойства.

Каждый участник обязан уметь объяснить результат без ИИ.

# Что сейчас не делать

До Gate C не приоритетны:

- полный backend;
- полный frontend;
- десятки endpoints;
- production Kafka;
- сложный Kubernetes;
- большая CV-модель;
- много экранов;
- оптимизация FPS/latency без реальных измерений;
- «архитектурные» заявления только через названия технологий.

Сначала — система аргументов и архитектурная модель.
