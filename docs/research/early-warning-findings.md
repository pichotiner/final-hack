# Открытые данные: где искать предвестники брака

26.09.2026. Роль №2. **Данные SECOM скачаны и пересчитаны; датчики предприятия и
прогнозирование будущего дефекта не проверены.** Проект применения —
[схема раннего предупреждения](../architecture/early-warning-design.md).

## 1. Короткий вывод для защиты

Открытые данные подтверждают полезность контроля параметров процесса и качество
данных как отдельную проблему. Они **не устанавливают, на каком этапе чаще возникает
брак нашего предприятия**. Для такой частоты нужны и подтверждённые причины, и число
изделий, прошедших каждую операцию. Публикации об авариях описывают выбранные тяжёлые
случаи, а не репрезентативную выборку всех операций.

Для пилота выбираем **механическую обработку и сборку**: на них можно наблюдать
процесс до итогового контроля и привязать сигнал к конкретному run. Это инженерный
выбор по наблюдаемости и возможности вмешательства, не найденный мировой рейтинг.
Входной материал остаётся отдельной зоной контроля: датчик станка не выявляет все
внутренние дефекты заготовки.

## 2. Реальный открытый набор SECOM: собственный пересчёт

**Источник EW-S1:** Michael McCann, Adrian Johnston, *SECOM*, UCI Machine Learning
Repository, 2008, [DOI 10.24432/C54305](https://doi.org/10.24432/C54305),
[карточка](https://archive.ics.uci.edu/dataset/179/secom), CC BY 4.0.
Прочитаны Dataset Information, Variable Information и опубликованные baseline
результаты; обработаны полные `secom.data` и `secom_labels.data`.
Это данные полупроводникового производства, не космической механообработки.
Метка −1 = pass, +1 = fail; время относится к тесту, часовой пояс не указан.

| Экземпляров с меткой результата | 1 567 |

| Доля fail | 6,6369% |

В карточке UCI написано **591 feature**, но в скачанном числовом файле **590**
колонок. Расхождение явно сохраняем; не придумываем отсутствующий датчик.
Пропуск здесь не доказывает физический отказ сенсора: причина отсутствия неизвестна.
Постоянство на этой выборке тоже не доказывает бесполезность канала на предприятии.

### Разрез по месяцу теста, не по этапу возникновения

| Месяц | Экземпляры | Fail | Доля |
| --- | ---: | ---: | ---: |
| 2008-07, неполный месяц | 63 | 14 | 22,2222% |

Это описательная статистика данной выборки. Причины различий, партии и режимы не
известны; нельзя объявить июль «худшей сменой» или сделать причинный вывод. Различия
обосновывают проверку устойчивости модели во времени вместо одного случайного split.

### Что из этого следует для EFQA

1. Классификатор «всегда pass» имеет accuracy **93,3631%**, recall отказов **0%**.
   Одной accuracy для защиты недостаточно. Нужны полнота выявления отказов,
   точность предупреждений, ложные тревоги на станко-час и запас времени до события.
2. Удаление всех неполных строк уничтожило бы выборку. Для каждого обязательного
   канала нужны правила пропусков и отдельное состояние «не могу оценить»;
   подстановка нуля меняет смысл физического измерения.
3. Много датчиков не гарантирует полезность. Выбор каналов начинают с механизма
   отказа, метрологии и доступности до решения, затем проверяют добавочную пользу.
4. По SECOM нельзя измерить **опережение**: нет времени доступности каждого признака
   и истории развития конкретного отказа. Классификация результата теста не равна
   прогнозу до изготовления брака. Модель и топ «причинных сенсоров» здесь не обучали.

## 4. Как действительно получить ответ «где чаще»

Собрать локальную когорту за согласованный период, включая годные изделия:
item/component, партия, тип изделия, route revision, run, станок/инструмент,
начало/конец, контроль до/после с областью/качеством/методом, предупреждение и время
его доставки, решение ОТК, подтверждённая причина либо unknown. Неизвестные причины
показывать отдельно, не распределять автоматически на последний участок.

- **Где обнаружили:** distinct изделий с первым подтверждённым обнаружением на этапе /
  distinct сопоставимых изделий с оценимым контролем на этапе. Рядом — покрытие контроля.
- **Где возникло:** distinct изделий с обоснованно установленным возникновением на этапе /
  distinct сопоставимых изделий, прошедших этап. Отдельно число unknown и критерий причинного вывода.
- **Где ломается оборудование:** число подтверждённых отказов / станко-часы при
  сопоставимом режиме. Не смешивать с долей негодных изделий.
- **Где целесообразнее датчик:** тяжесть последствия × возможность обнаружить до
  необратимой операции × время реакции; затем стоимость монтажа/калибровки/тревог.
  При отсутствии оценок частоты не выдумывать числовой рейтинг FMEA.

Разделять обучение/настройку/проверку по времени и партиям; все окна одного run
держать в одной части. Нормализацию, выбор признаков и пороги обучать только на
прошлом. В признаки не допускать финальное решение, будущие измерения и действия
после тревоги. Для редких отказов давать числители/знаменатели и интервалы
неопределённости, не обещать точность по нескольким случаям.

**Приёмка пилота:** положительный запас времени на реальную реакцию, приемлемая
нагрузка ложных тревог, контроль пропусков и подтверждённая привязка к изделиям.
Численные пороги утверждают технолог и ОТК после базовых измерений. Если действие
предотвратило отказ, отсутствие брака не доказывает ложную тревогу: результат
интервенции оценивается отдельно, причинную экономию не выводим из корреляции.
